### Function

它是 Java 8 引入的 **函数式接口 (Functional Interface)** 之一，位于 `java.util.function` 包中。

**1. 它是干嘛的？**

**核心作用**：代表一个**“有输入、有返回”**的函数。

- **输入**：接受 **1 个** 参数。
- **输出**：返回 **1 个** 结果。
- **转换**：通常用于将一种类型的数据**转换**为另一种类型的数据（例如：把 `String` 转成 `Integer`，或者把 `User` 对象转成 `String` 名字）。

**2. 基本语法与定义**

```
// 泛型定义：<输入类型, 返回类型>
Function<T, R>
```

- `T`: 输入参数的类型。
- `R`: 返回结果的类型 (Result)。

**核心方法**：

- `R apply(T t)`: 执行函数逻辑，传入参数 `t`，返回结果 `R`。

**3. 代码示例**

#### **场景 A：最简单的类型转换 (String -> Integer)**

```
import java.util.function.Function;

public class Main {
    public static void main(String[] args) {
        // 定义一个 Function：输入 String，返回 Integer (计算长度)
        Function<String, Integer> stringToLength = s -> s.length();

        // 使用 apply 方法执行
        int length = stringToLength.apply("Hello"); 
        System.out.println(length); // 输出: 5
    }
}
```

#### **场景 B：对象属性提取 (User -> String)**

```
import java.util.function.Function;
import java.util.Arrays;
import java.util.List;
import java.util.stream.Collectors;

class User {
    String name;
    int age;
    public User(String name, int age) { this.name = name; this.age = age; }
    public String getName() { return name; }
}

public class Main {
    public static void main(String[] args) {
        List<User> users = Arrays.asList(
            new User("Alice", 20),
            new User("Bob", 25)
        );

        // 定义一个 Function：从 User 对象中提取 name (String)
        Function<User, String> getNameFunc = user -> user.getName();

        // 在 Stream 中使用
        List<String> names = users.stream()
                .map(getNameFunc) // 这里直接传入 Function
                .collect(Collectors.toList());

        System.out.println(names); // 输出: [Alice, Bob]
        
        // 也可以直接用 Lambda 写法，效果一样
        // .map(user -> user.getName())
    }
}
```

#### **场景 C：链式调用 (andThen / compose)**

`Function` 支持将多个函数串联起来，像流水线一样处理数据。

- **`andThen`**: 先执行当前函数，再执行后面的函数 (顺序：A -> B)。
- **`compose`**: 先执行后面的函数，再执行当前函数 (顺序：B -> A)。

```
import java.util.function.Function;

public class Main {
    public static void main(String[] args) {
        // 函数 1: String -> Integer (转长度)
        Function<String, Integer> toLength = s -> s.length();
        
        // 函数 2: Integer -> String (长度加 " 个字")
        Function<Integer, String> toDesc = i -> i + " 个字";

        // 链式调用：先算长度，再加后缀
        Function<String, String> combined = toLength.andThen(toDesc);

        String result = combined.apply("Java"); 
        // 过程："Java" -> 4 -> "4 个字"
        
        System.out.println(result); // 输出: 4 个字
    }
}
```

**4. 常见变体 (针对基本数据类型)**

为了避免自动装箱/拆箱的性能损耗，Java 提供了针对 `int`, `long`, `double` 的特化版本：

| 接口                   | 输入类型 | 返回类型 | 用途                                                         |
| :--------------------- | :------- | :------- | :----------------------------------------------------------- |
| **`Function<T,R>`**    | 对象 T   | 对象 R   | 通用                                                         |
| **`ToIntFunction<T>`** | 对象 T   | `int`    | 例如：计算集合中每个元素的某个 int 属性                      |
| **`IntFunction<R>`**   | `int`    | 对象 R   | 例如：根据 int 索引创建数组 `String[] arr = IntFunction.apply(5)` |
| **`IntUnaryOperator`** | `int`    | `int`    | 输入 int 返回 int (如：x * 2)                                |

**5. 它和 Consumer, Supplier, Predicate 的区别**

这是面试和实战中容易混淆的点：

| 接口                | 方法签名            | 含义           | 记忆口诀                      |
| :------------------ | :------------------ | :------------- | :---------------------------- |
| **`Function<T,R>`** | `R apply(T t)`      | **有进有出**   | 加工厂 (原料进，成品出)       |
| **`Consumer<T>`**   | `void accept(T t)`  | **有进无出**   | 消费者 (只消费，不返回)       |
| **`Supplier<T>`**   | `T get()`           | **无进有出**   | 供应商 (不需要参数，直接生产) |
| **`Predicate<T>`**  | `boolean test(T t)` | **有进布尔出** | 判断器 (返回 true/false)      |

**总结**

- **什么时候用？** 当你需要传递一段逻辑，这段逻辑**接收一个参数并返回一个结果**时（特别是在 Stream 流的 `.map()` 操作中）。
- **怎么写？** 通常直接用 Lambda 表达式：`(x) -> x.doSomething()`。
- **核心方法：** `apply()`。

### 接口幂等性

**在涉及“状态变更”或“资源增减”的写操作（INSERT/UPDATE/DELETE）中，原则上都应该考虑幂等性**

**1. 天然幂等的更新操作 (Natural Idempotency)**

如果业务逻辑是 **“将状态设置为 X"**，而不是 **“将状态从 A 变为 B"**，那么它天然就是幂等的。

- 场景举例

  - ```
    UPDATE user SET status = 'DISABLED' WHERE id = 100;
    ```

    - 执行 1 次：状态变 DISABLED。
    - 执行 100 次：状态依然是 DISABLED。结果一致，无副作用。

  - ```
    UPDATE product SET price = 99.9 WHERE id = 5;
    ```

    - 无论重试多少次，价格最终都是 99.9。

- 为什么不用处理？

  - SQL 本身保证了最终一致性。只要你的业务允许“覆盖写”，就不需要防重逻辑。
  - **注意**：如果业务要求“只能由 ENABLED 变为 DISABLED"，那就需要加 `WHERE status = 'ENABLED'` 条件（乐观锁思想），这属于业务规则校验，不算纯粹的幂等性处理。

**决策矩阵**

| 场景类型                      | 是否需要代码级幂等处理？ | 推荐策略                             |
| :---------------------------- | :----------------------- | :----------------------------------- |
| **资金/库存/订单创建**        | **必须** (高危)          | Redis Token + DB 唯一索引 + 分布式锁 |
| **状态覆盖写 (Set Status=X)** | **不需要** (天然幂等)    | 直接执行 SQL                         |
| **状态流转 (A->B)**           | **必须**                 | 乐观锁 (`WHERE status=A`)            |
| **日志/非关键通知**           | **可选** (低危)          | 容忍重复 / MQ 去重 / 事后清洗        |
| **UPSERT (存在即更新)**       | **不需要** (DB 层解决)   | `ON DUPLICATE KEY UPDATE`            |
| **不可控的第三方调用**        | **必须** (但需变通)      | 本地事务表记录状态 (TCC 模式变种)    |

**怎么处理的？（实战方案）**

在 Java 开发中，通常根据**业务场景**和**性能要求**，组合使用以下 4 种方案：

#### **方案一：数据库唯一索引（最兜底、最可靠）**

**适用场景**：业务上有自然唯一键（如订单号、流水号、身份证号）。
**原理**：利用数据库的 `UNIQUE KEY` 约束，让第二次插入直接报错。

- 实现步骤

  1. 建表时给关键字段加唯一索引。

     ```
     ALTER TABLE orders ADD UNIQUE INDEX uk_order_no (order_no);
     ```

  2. 代码中捕获 

     ```
     DuplicateKeyException
     ```

     ```
     try {
         orderMapper.insert(order);
     } catch (DuplicateKeyException e) {
         // 幂等处理：查询已存在的订单返回成功，或者抛出自定义异常提示“请勿重复提交”
         log.warn("重复提交订单: {}", order.getOrderNo());
         return Result.success("订单已存在"); 
     }
     ```

- **优点**：绝对安全，哪怕 Redis 挂了、代码逻辑漏了，数据库是最后一道防线。

- **缺点**：性能一般（依赖 DB），无法在拦截器层直接拦截，会进入 Service 层。

#### **方案二：Redis Token 机制（最通用、防重提交）**

**适用场景**：表单提交、非自然唯一键的业务（如“点击领取”）。
**原理**：**“先拿令牌，再消费令牌”**。

- **流程**：

  1. **前端/上游**：在进入页面前，先调用 `GET /token` 接口获取一个唯一的 UUID。

  2. 后端

     ```
     redisTemplate.opsForValue().set("token:" + uuid, "1", 30, TimeUnit.SECONDS);
     ```

  3. **提交请求**：前端携带这个 UUID 调用业务接口。

  4. 后端校验

     - 使用 Lua 脚本执行 `get + del` 原子操作。
     - 如果 Redis 里有这个 Key，说明是第一次，删除 Key 并放行。
     - 如果 Redis 里没 Key，说明是重复请求（或过期），直接拦截。

- **Lua 脚本示例**（保证原子性）：

  ```
  if redis.call('get', KEYS[1]) == ARGV[1] then
      return redis.call('del', KEYS[1])
  else
      return 0
  end
  ```

- **Java 封装（自定义注解 + AOP）**：
  为了不让业务代码杂乱，我会写一个 `@Idempotent` 注解。

  ```
  @Target(ElementType.METHOD)
  @Retention(RetentionPolicy.RUNTIME)
  public @interface Idempotent {
      String key() default ""; // SpEL 表达式，如 #request.orderNo
      long expireTime() default 5000; // 毫秒
  }
  ```

  **AOP 切面逻辑**：

  ```
  @Around("@annotation(idempotent)")
  public Object around(ProceedingJoinPoint joinPoint, Idempotent idempotent) {
      // 1. 解析 SpEL 获取唯一键 (如从参数中取 orderNo)
      String uniqueKey = parseKey(idempotent.key(), joinPoint); 
      
      // 2. 尝试删除 Redis Key (Lua 脚本)
      Long result = redisTemplate.execute(luaScript, Collections.singletonList(uniqueKey), "1");
      
      if (result == null || result == 0) {
          throw new BusinessException("重复提交，请勿频繁操作！");
      }
      
      // 3. 执行目标方法
      return joinPoint.proceed();
  }
  ```

- **优点**：高性能（内存操作），拦截早（不进 DB），灵活。

- **缺点**：依赖 Redis 高可用；需要前端配合传 Token（或者从 Header 获取）。

#### **方案三：状态机版本号（乐观锁）**

**适用场景**：更新操作（Update），特别是涉及状态流转（如：待支付->已支付）。
**原理**：利用 `version` 字段或状态字段本身作为条件。

- SQL 写法

  ```
  UPDATE orders 
  SET status = 'PAID', version = version + 1 
  WHERE id = 123 AND status = 'UNPAID' AND version = 1;
  ```

- **判断**：检查 `updateCount`。如果返回 0，说明状态已经变了（被别人改过或重复提交了），视为幂等失败。

- **优点**：无需额外组件，利用 DB 行锁，逻辑严密。

- **缺点**：只适用于更新场景，不适用于新增。

#### **方案四：分布式锁（极端并发场景）**

**适用场景**：超高并发下的库存扣减、秒杀。
**原理**：对同一个资源（如 userId 或 productId）加锁，串行化处理。

- 实现

  ：使用 Redisson。

  ```
  RLock lock = redissonClient.getLock("lock:order:" + orderId);
  if (lock.tryLock(0, 10, TimeUnit.SECONDS)) {
      try {
          // 1. 再次检查数据库是否已存在（双重检查）
          if (orderService.exists(orderId)) {
              return Result.success("已处理");
          }
          // 2. 执行业务
          orderService.create(order);
      } finally {
          lock.unlock();
      }
  } else {
      throw new BusinessException("系统繁忙，请稍后重试");
  }
  ```

- **优点**：能解决复杂的竞争条件。

- **缺点**：性能损耗大，容易成为瓶颈，慎用。

**如果幂等性失效了，出现了两笔订单**

#### **1. 每日财务对账（Reconciliation）**

- **做法**：每天凌晨，将**内部订单系统**的数据与**支付渠道**（微信/支付宝/银行）的账单进行比对。
- 发现
  - 内部系统显示下了 2 单，扣了 2 次钱。
  - 但业务规则判定这应该是 1 单。
- **处理**：生成“差异报表”，由财务人员或自动脚本发起退款。

#### **2. 用户投诉与客服通道**

- **现状**：用户发现被扣了两笔钱，一定会找客服。
- 流程
  - 客服后台必须有**“一键查重复”**和**“一键退款”**的功能。
  - 一旦确认为系统 Bug 导致的重复扣款，优先退款安抚用户，再提工单给技术部修 Bug。

#### **3. 资金安全险**

- 对于像淘宝、京东这样的巨头，他们甚至购买了保险。如果因为系统故障导致用户资金损失，由保险公司赔付，确保用户体验不受损。

### 数据库问题排查思路

1. **App Log**: `grep "Timeout" app.log` （应用层确认报错类型)
2. **DB Process**: `SELECT * FROM info_schema.processlist WHERE time > 5 ORDER BY time DESC;` (看谁在跑)
3. **DB Locks**: `SELECT * FROM sys.innodb_lock_waits;` (看谁在等)
4. **DB Long Trx**: `SELECT * FROM info_schema.INNODB_TRX WHERE ...` (抓长事务)
5. **Explain**: `EXPLAIN <慢SQL>` (分析索引)
6. **Kill**: `KILL <id>` (必要时止损)
7. **Fix**: 加索引 / 改代码 / 调配置。

### 响应式编程

#### 1. 什么是响应式编程？

响应式编程是一种**基于数据流和变化传播**的编程范式。简单来说，就是把程序中的一切都看作是**异步的数据流**（例如变量变化、用户点击、网络请求等），然后用**声明式**的操作符（如 `map`、`filter`）来处理这些流。

传统的编程模型（比如 Servlet）是**阻塞**的：一个线程处理一个请求，如果遇到 I/O（数据库、网络），线程就会一直等待，导致资源浪费。响应式编程则是**非阻塞**的：当线程发起 I/O 操作后，可以立即去处理其他任务，等到数据准备好再回来处理，从而用更少的线程支撑更高的并发。

**Reactive Streams** 是一个规范，定义了响应式流之间的交互标准，包含四个接口：`Publisher`、`Subscriber`、`Subscription`、`Processor`。Java 9 已经把它纳入了 `java.util.concurrent.Flow` 中。

而 **Reactor** 就是基于 Reactive Streams 规范的响应式库，也是 Spring WebFlux 的底层依赖。它提供了两个最核心的发布者（Publisher）：`Mono` 和 `Flux`。

#### 2. 核心概念：Mono 与 Flux

- **Mono**：表示一个**包含 0 或 1 个元素**的异步序列。类似于 `Optional` 或 `CompletableFuture`，但功能更丰富。
- **Flux**：表示一个**包含 0 到 N 个元素**的异步序列。可以看作是无限或有限的流。

两者都实现了 `Publisher` 接口，可以触发数据或信号的发射。

#### 3. 订阅与消费

流本身只是定义，必须通过**订阅（subscribe）**才能触发数据流动。

```
Flux.just("A", "B", "C")
    .subscribe(
        data -> System.out.println("onNext: " + data),    // 数据到达时
        error -> System.err.println("onError: " + error), // 发生错误时
        () -> System.out.println("onComplete")            // 完成时
    );
```

输出：

```
onNext: A
onNext: B
onNext: C
onComplete
```

#### 4. 常用操作符（Operators）

操作符是响应式编程的精髓，可以让我们用声明式的方式组合和处理流。Reactor 提供了非常丰富的操作符，这里列举最常用的几类。

##### 4.1 转换操作符

- **map**：同步地将元素转换为另一种形式。

  ```java
  Flux.just(1, 2, 3)
      .map(i -> i * 2)
      .subscribe(System.out::println); // 2,4,6
  ```

- **flatMap**：将每个元素映射为一个新的 `Publisher`，然后将这些 Publisher 发出的元素合并成一个新的 Flux（顺序可能交错）。常用于异步非阻塞调用。

  ```java
  Flux.just("user1", "user2")
      .flatMap(user -> Mono.just("Hello " + user))
      .subscribe(System.out::println);
  ```

  注意：`flatMap` 默认并发执行，可以通过参数控制并发度。

- **concatMap**：与 flatMap 类似，但会保持元素的原始顺序（串行处理）。

  ```java
  Flux.just("a", "b")
      .concatMap(s -> Flux.just(s + "1", s + "2"))
      .subscribe(System.out::println); // a1, a2, b1, b2
  ```

##### 4.2 过滤操作符

- **filter**：根据条件过滤元素。

  ```java
  Flux.range(1, 10)
      .filter(i -> i % 2 == 0)
      .subscribe(System.out::println); // 2,4,6,8,10
  ```

- **take**：只取前 N 个元素。

  ```java
  Flux.range(1, 100).take(3).subscribe(); // 1,2,3
  ```

- **distinct**：去重。

##### 4.3 组合操作符

- **zip**：将多个流的元素一一合并。

  ```java
  Flux<String> names = Flux.just("A", "B", "C");
  Flux<Integer> ages = Flux.just(20, 30, 40);
  Flux.zip(names, ages, (name, age) -> name + " is " + age)
      .subscribe(System.out::println); // A is 20, B is 30, C is 40
  ```

- **merge**：将多个流合并成一个，按时间顺序发射（交叉）。

  ```java
  Flux.merge(Flux.just(1,2), Flux.just(3,4))
      .subscribe(System.out::print); // 1324 或 3142（取决于时间）
  ```

##### 4.4 错误处理

- **onErrorReturn**：发生错误时返回一个默认值。
- **onErrorResume**：发生错误时切换到另一个流。
- **retry**：发生错误时重试。

```java
Flux.just(1,2,0,4)
    .map(i -> 10 / i)
    .onErrorReturn(0)
    .subscribe(System.out::println, error -> System.out.println("Error: " + error));
// 输出 10, 5, 0（发生除零错误，返回 0，且流完成）
```

#### 5. 背压（Backpressure）

背压是指**下游处理速度跟不上上游时，如何通知上游控制流速**的机制。Reactor 天然支持背压，订阅者可以通过 `Subscription` 请求指定数量的元素，避免被数据淹没。

例如，用 `limitRate` 限制上游一次发送的元素数量：

```java
Flux.range(1, 1000)
    .log()
    .limitRate(10) // 每次请求10个
    .subscribe();
```

在传统阻塞式编程中，线程在读取数据时如果数据没准备好，线程会阻塞等待。这种阻塞天然地起到了“调节”作用：生产者和消费者之间通过等待来平衡速度。

但在响应式编程中，一切都是**异步非阻塞**的，生产者可以源源不断地快速发出数据，而消费者可能因为处理能力有限或系统资源紧张而无法及时处理。如果没有背压，可能会出现：

- 数据堆积在内存中，导致内存溢出（OOM）。
- 消费者被迫丢弃数据，造成数据丢失。
- 系统整体不稳定。

背压提供了一种**优雅的应对方式**，让系统在过载时仍然保持可控。

#### 6. 调度器（Schedulers）与线程模型

默认情况下，操作符会沿用上游的线程。我们可以通过 `publishOn` 和 `subscribeOn` 来切换执行的线程。

- **publishOn**：影响下游操作符执行的线程。
- **subscribeOn**：影响整个流（源头）的线程，即使放在链条后面也有效。

```java
Flux.just("hello")
    .map(s -> {
        System.out.println("map: " + Thread.currentThread().getName());
        return s.toUpperCase();
    })
    .publishOn(Schedulers.boundedElastic())
    .map(s -> {
        System.out.println("map2: " + Thread.currentThread().getName());
        return s + "!";
    })
    .subscribeOn(Schedulers.parallel())
    .subscribe(v -> System.out.println("subscribe: " + v));

Thread.sleep(1000); // 防止主线程退出
```

输出会显示 map 在 parallel 线程，map2 在 boundedElastic 线程。

常用调度器：

- `Schedulers.immediate()`：当前线程。
- `Schedulers.single()`：单个可复用的线程。
- `Schedulers.parallel()`：固定大小的线程池（适合 CPU 密集型）。
- `Schedulers.boundedElastic()`：弹性线程池（适合 I/O 密集型，如数据库、网络调用）。

### CUP与线程

#### 1. 什么是 CPU 核心？

CPU 核心可以理解为**一个物理的处理单元**，它能够独立执行指令。

- 单核 CPU：一次只能处理一个任务（严格来说是只能执行一个线程的指令）。
- 多核 CPU：拥有多个核心，可以同时处理多个任务（真正的并行执行）。

#### 2. 什么是线程？

线程是**操作系统能够进行运算调度的最小单位**，它被包含在进程之中，是进程中的实际运作单位。

- 一个进程可以有多个线程，它们共享进程的资源（内存等）。
- 线程是代码的执行路径，CPU 实际执行的就是线程的指令。

#### 3. 线程与 CPU 核心的关系

##### 3.1 单核 CPU 上的线程

在单核 CPU 上，同一时刻只能有一个线程在运行。操作系统通过**快速切换**（时间片轮转）让多个线程交替使用 CPU，造成“同时运行”的假象。这种**并发**（concurrency）是宏观上的并行，微观上仍是串行。

##### 3.2 多核 CPU 上的线程

多核 CPU 可以真正**并行**（parallelism）执行多个线程：

- 如果有 4 个核心，那么同一时刻最多可以有 4 个线程同时运行（不考虑超线程）。
- 其他等待的线程会被操作系统调度，在后续的时间片中运行。

##### 3.3 超线程（Hyper-Threading）

现代 CPU 常常支持超线程技术：一个物理核心可以模拟成两个**逻辑核心**，让一个核心同时处理两个线程的指令（利用核心内部闲置资源）。

- 操作系统看到的 CPU 核心数是逻辑核心数（通常物理核心数 × 2）。
- 超线程能提高并行度，但两个逻辑核心共享物理核心的执行资源，性能提升通常远不如两个独立物理核心。

#### 4. 如何设置线程数？

在设计程序时，线程数量的设置与任务类型紧密相关：

- **CPU 密集型任务**（计算为主，很少等待）：
  线程数不宜超过 CPU 核心数（或逻辑核心数）。因为更多的线程会导致频繁的上下文切换，反而降低效率。
  公式参考：`线程数 = CPU 核心数 + 1`（+1 是为了应对偶尔的缺页中断等）。
- **I/O 密集型任务**（大量等待网络、磁盘等）：
  线程在执行 I/O 时会被阻塞，CPU 可以切换去执行其他线程。因此线程数可以远大于核心数，以提高资源利用率。
  公式参考：`线程数 = CPU 核心数 * (1 + 平均等待时间 / 平均计算时间)`。
  例如，如果计算时间 1ms，等待时间 10ms，那么一个核心可以同时处理约 11 个线程的任务。

#### 5. 示例理解

假设有一个 4 核 CPU（无超线程）：

- 运行 CPU 密集型程序（如视频编码），启动 4 个线程：它们可以同时在 4 个核心上运行，几乎满负荷。
- 如果启动 8 个线程，每个线程仍会分配到 CPU 时间，但需要频繁切换（每个线程运行一小段时间后被迫让出 CPU），切换本身消耗资源，总吞吐量可能反而下降。

对于 I/O 密集型程序（如 Web 服务器），一个线程可能大部分时间在等待数据库返回数据，这时 CPU 可以处理其他请求线程。因此线程数可以设为几百甚至上千（只要内存允许），让 CPU 始终忙碌。

#### 6. 在响应式编程中的体现

响应式编程（如 Reactor）采用非阻塞模型，一个线程可以处理大量并发的 I/O 操作，而不会被阻塞。因此：

- 它可以用很少的线程（通常与 CPU 核心数相近）支撑极高的并发量。
- 这正是利用了“I/O 等待时不占用线程”的特性，让每个线程持续做有用的事，而不是阻塞空等。

例如，Netty 的 EventLoop 线程数通常设置为 CPU 核心数的两倍（考虑超线程），每个 EventLoop 可以管理成千上万个连接。

#### 7. 查看cpu核心信息

1. **看整体CPU忙闲**：运行 `top` 命令，然后按 `1` 键。
   - 你会看到CPU使用率的列表（如 `Cpu0`, `Cpu1`...）。
   - **关键判断**：如果所有核心的 `%id`（空闲）都很高，说明CPU很闲，核心不是瓶颈。如果某个核心的 `%us`（用户态）或 `%sy`（内核态）长期接近100%，而其他核心很闲，说明程序是**单线程**或未优化，只能跑满一个核。
2. **锁定你的程序**：在 `top` 界面中，按下 `P` 键（大写P），进程会按CPU使用率从高到低排序。
   - 找到你的Java进程（如 `java`），记下它的 **PID**。看它的 `%CPU` 一列。
   - **关键判断**：如果 `%CPU` 显示为 `100%` 或 `200%`，这通常意味着它占用了1个或2个逻辑核心。如果远低于 `100% * 核心数`，说明程序没把CPU用满。
3. **精细化追踪**：如果想看你的程序里具体哪个线程在忙，可以用 `top -H -p <PID>` 查看这个进程内部所有线程的CPU占用。这能帮你判断是代码里的哪个部分在消耗CPU。

#### 9. 线程分配的最佳实践

1. **明确任务类型**：是 CPU 密集型还是 I/O 密集型？
2. **获取物理核心数**：从 `lscpu` 的 `Core(s) per socket × Socket(s)` 得出。
3. **作为基准**：
   - CPU 密集型：线程数 ≤ 物理核心数。
   - I/O 密集型：线程数可以远超物理核心数，但建议通过压测找到最优值，同时考虑超线程带来的额外并发能力。
4. **考虑超线程**：如果任务类型能从超线程受益（例如混合型），可以适当增加线程数，但一般不超过逻辑核心数。
5. **监控与调整**：在真实负载下用 `top` 观察 CPU 使用率，如果 CPU 使用率长期低于 70%~80%，可以适当增加线程数；如果上下文切换过高（`vmstat` 的 `cs` 列），则需要减少线程数。
6. **容器环境**：注意容器限制的 CPU 核心数，确保 JVM 能正确识别（通过 `-XX:ActiveProcessorCount` 或使用 JDK 10+ 自动适配）。
