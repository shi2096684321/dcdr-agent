## 1. 版本概述

### 1.1 V2.0 定位

V2.0 是 V1.0 / V1.1 的**企业化升级版本**，在保持多模态对话能力的基础上，增加三大核心能力：

| 能力 | 价值 | 适用场景 |
|------|------|---------|
| **RAG 知识库** | 让 Agent 能基于私有文档回答问题 | 企业知识问答、文档助手 |
| **用户认证** | 多用户隔离，数据安全 | 团队使用、SaaS 化 |
| **多 Agent 协作** | 多个专业 Agent 分工合作 | 复杂任务、自动化工作流 |

### 1.2 版本目标

```
V1.0/V1.1 (已完成/规划中)      V2.0 (规划中)
────────────────────────       ──────────────
单用户                          多用户(认证隔离)
无知识库                        RAG知识库(文档问答)
单Agent                         多Agent协作
内存/H2存储                     PostgreSQL + 向量库
本地部署                        容器化部署(Docker)
```

### 1.3 与 V1.0 / V1.1 的兼容性

| 兼容项 | 说明 |
|--------|------|
| API 兼容 | V1.0 / V1.1 所有 API 保持兼容，V2.0 新增 API |
| 配置兼容 | V1.0 / V1.1 配置项保留，V2.0 新增配置项 |
| 数据迁移 | 提供从 H2 迁移到 PostgreSQL 的脚本 |
| 功能开关 | V2.0 新功能可通过配置开关启用/禁用 |

## 3. RAG 知识库

### 3.1 功能概述

让 Agent 能够基于用户上传的私有文档（PDF、Word、TXT、Markdown）回答问题，解决 LLM "不知道你私有数据" 的问题。

### 3.2 RAG 工作原理

```
┌─────────────────────────────────────────────────────────────┐
│                     RAG 完整流程                              │
│                                                             │
│  ════════════ 离线阶段 (文档入库) ════════════               │
│                                                             │
│  上传文档 → 文档解析 → 文本分块 → 向量化 → 存入向量库        │
│  (PDF)     (提取文本)  (Chunking) (Embedding) (Vector Store) │
│                                                             │
│  ════════════ 在线阶段 (检索问答) ════════════               │
│                                                             │
│  用户提问 → 问题向量化 → 相似度检索 → 拼接上下文 → LLM回答   │
│  "报销流程"  (Embedding)  (Top-K)    (Prompt)    (生成)     │
│                       │                                     │
│                       ▼                                     │
│              ┌────────────────┐                             │
│              │ 找到相关文档片段 │                             │
│              │ "报销流程: 1..."│                             │
│              │ "审批层级: ..." │                             │
│              └────────────────┘                             │
└─────────────────────────────────────────────────────────────┘
```

### 3.3 详细需求

#### F-20: RAG 知识库核心

| 需求编号 | F-20-001 |
|---------|----------|
| **需求名称** | 文档上传与解析 |
| **描述** | 支持上传多种格式文档，自动解析提取文本 |
| **支持格式** | PDF、Word(.docx)、TXT、Markdown、HTML |
| **限制** | 单文件最大 20MB，单知识库最大 100 个文档 |
| **验收标准** | 1. PDF 支持文字版和扫描版(OCR)<br>2. 保留文档结构(标题、段落)<br>3. 解析失败时提示具体原因 |

| 需求编号 | F-20-002 |
|---------|----------|
| **需求名称** | 文本分块 |
| **描述** | 将长文档切分为合适大小的文本块 |
| **分块策略** | 1. 固定长度分块(默认 500 字符)<br>2. 按段落分块<br>3. 递归分块(保留语义) |
| **验收标准** | 1. 分块大小可配置<br>2. 支持重叠(overlap)避免语义断裂<br>3. 记录每个块的来源位置 |

| 需求编号 | F-20-003 |
|---------|----------|
| **需求名称** | 向量化与存储 |
| **描述** | 将文本块转为向量并存储 |
| **Embedding 模型** | OpenAI text-embedding-3-small / 智谱 embedding-2 |
| **验收标准** | 1. 向量化异步执行，不阻塞上传<br>2. 支持批量向量化<br>3. 向量库支持相似度检索 |

| 需求编号 | F-20-004 |
|---------|----------|
| **需求名称** | 检索增强问答 |
| **描述** | 用户提问时，先检索知识库，再结合检索结果生成回答 |
| **检索策略** | 1. 纯向量检索(语义相似)<br>2. 混合检索(向量 + 关键词)<br>3. 重排序(Rerank) |
| **验收标准** | 1. 检索 Top-K 结果可配置(默认 5)<br>2. 回答中标注引用来源<br>3. 可切换"仅知识库"和"知识库+通用"模式 |

#### F-21: 知识库管理

| 需求编号 | F-21-001 |
|---------|----------|
| **需求名称** | 多知识库管理 |
| **描述** | 支持创建多个独立的知识库 |
| **验收标准** | 1. 每个知识库独立管理文档<br>2. 对话时可选择关联的知识库<br>3. 支持知识库的增删改查 |

| 需求编号 | F-21-002 |
|---------|----------|
| **需求名称** | 文档管理 |
| **描述** | 管理知识库中的文档 |
| **验收标准** | 1. 查看文档列表(名称、大小、状态、分块数)<br>2. 删除文档(同步删除向量)<br>3. 重新解析/向量化文档<br>4. 文档状态: 待解析/解析中/已就绪/失败 |

| 需求编号 | F-21-003 |
|---------|----------|
| **需求名称** | 检索测试 |
| **描述** | 提供检索调试工具，测试检索效果 |
| **验收标准** | 1. 输入问题，查看检索到的文档块<br>2. 显示相似度分数<br>3. 可调整 Top-K 参数 |

### 3.5 RAG 与 Agent 的集成

```
对话流程 (开启知识库时):

  用户: "公司报销流程是什么？"
         │
         ▼
  ┌──────────────────────────┐
  │ AgentOrchestrator        │
  │  1. 检测到关联了知识库    │
  │  2. 调用 RAG 检索         │
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │ RetrievalService         │
  │  问题向量化               │
  │  向量检索 Top-5           │

  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │ AgentOrchestrator        │
  │  拼接 Prompt:             │
  │  "基于以下资料回答:       │
  │   [文档片段1]             │
  │   [文档片段2]             │
  │   问题: 报销流程?"        │
  └──────────┬───────────────┘
             │
             ▼
  ┌──────────────────────────┐
  │ ChatModelProvider        │
  │  调用 LLM 生成回答        │
  │  (引用来源标注)           │
  └──────────────────────────┘
```

### 3.6 RAG 配置设计

```yaml
agent:
  rag:
    enabled: true
    
    # 文档解析
    document:
      max-file-size: 20MB
      supported-formats: [pdf, docx, txt, md, html]
    
    # 文本分块
    splitter:
      strategy: recursive        # fixed | paragraph | recursive
      chunk-size: 500            # 每块字符数
      chunk-overlap: 50          # 块间重叠字符数
    
    # 向量化
    embedding:
      provider: openai           # openai | zhipu | local
      model: text-embedding-3-small
      dimensions: 1536
    
    # 向量存储
    vector-store:
      type: pgvector             # pgvector | redis | milvus | chroma
      pgvector:
        host: localhost
        port: 5432
        database: agent
        table: vectors
    
    # 检索
    retrieval:
      top-k: 5                   # 检索数量
      min-score: 0.7             # 最小相似度
      rerank: true               # 是否重排序
      rerank-model: cohere-rerank
```

## 4. 用户认证与权限管理

### 4.1 功能概述

实现多用户支持，每个用户的数据（会话、知识库、Agent 配置）相互隔离，并通过 RBAC 模型管理权限。

### 4.2 认证方案

```
┌─────────────────────────────────────────────────────────────┐
│                     认证架构 (JWT)                           │
│                                                             │
│  登录流程:                                                   │
│  ┌──────┐  POST /auth/login  ┌──────────┐  验证  ┌───────┐ │
│  │ 用户  │──────────────────►│AuthFilter│──────►│ DB    │ │
│  │      │◄──────────────────│          │       │(用户表)│ │
│  │      │  返回 JWT Token    └──────────┘       └───────┘ │
│  └──────┘                                                   │
│                                                             │
│  请求鉴权:                                                   │
│  ┌──────┐  GET /api/chat  ┌──────────┐  解析  ┌───────┐   │
│  │ 用户  │  +Bearer Token │JwtFilter │──Token─│Security│  │
│  │      │────────────────►│          │  验证  │Context │  │
│  │      │                 └──────────┘       └───────┘   │
│  └──────┘                       │                          │
│                          注入用户ID到请求                    │
│                          所有查询按用户ID过滤                 │
└─────────────────────────────────────────────────────────────┘
```

### 4.3 详细需求

#### F-22: 用户认证

| 需求编号 | F-22-001 |
|---------|----------|
| **需求名称** | 用户注册 |
| **描述** | 新用户注册账号 |
| **验收标准** | 1. 用户名(3-20字符) + 密码(8位以上,含大小写数字)<br>2. 密码 BCrypt 加密存储<br>3. 用户名唯一校验 |

| 需求编号 | F-22-002 |
|---------|----------|
| **需求名称** | 用户登录 |
| **描述** | 用户登录获取 JWT Token |
| **验收标准** | 1. 登录成功返回 JWT(有效期 24 小时)<br>2. Token 包含 userId、username、role<br>3. 支持 Refresh Token(7 天)<br>4. 登录失败 5 次锁定 30 分钟 |

| 需求编号 | F-22-003 |
|---------|----------|
| **需求名称** | 请求鉴权 |
| **描述** | 所有 API 请求需携带 Token 鉴权 |
| **验收标准** | 1. JWT Filter 统一拦截<br>2. 无效 Token 返回 401<br>3. Token 过期返回 419<br>4. 白名单: /auth/**, /api/models |

#### F-23: 权限管理 (RBAC)

```
RBAC 模型:

  用户(User) ──┬── 角色(Role) ──┬── 权限(Permission)
               │                │
               │                ├── chat:chat        (对话)
               │                ├── session:*        (会话管理)
               │                ├── kb:read          (知识库读取)
               │                ├── kb:write         (知识库写入)
               │                ├── agent:create     (创建Agent)
               │                ├── model:manage     (模型管理)
               │                └── user:manage      (用户管理)
               │
               ├── admin        (管理员,全部权限)
               ├── user         (普通用户,基础权限)
               └── guest        (访客,只读权限)
```

### 4.4 数据隔离设计

```
所有业务表新增 user_id 字段:

  sessions    → WHERE user_id = ?
  messages    → JOIN sessions ON ... WHERE sessions.user_id = ?
  knowledge_base → WHERE user_id = ?
  documents   → JOIN knowledge_base ON ... WHERE kb.user_id = ?
  agents      → WHERE user_id = ?

  全局拦截: MyBatis/JPA 拦截器自动追加 user_id 条件
```

## 5. 多 Agent 协作

### 5.1 功能概述

支持用户自定义多个 Agent 角色（不同人格、不同工具集、不同知识库），并支持多 Agent 编排协作完成复杂任务。

### 5.2 自定义 Agent

#### F-24: Agent 定义

| 需求编号 | F-24-001 |
|---------|----------|
| **需求名称** | 创建自定义 Agent |
| **描述** | 用户可创建具有不同角色设定的 Agent |
| **配置项** | 名称、头像、System Prompt、关联模型、关联工具、关联知识库、温度参数 |
| **验收标准** | 1. 可视化配置界面<br>2. 支持克隆预设模板(翻译助手、代码助手等)<br>3. 配置实时生效 |

### 5.3 Agent 工作流编排

#### F-25: 多 Agent 协作

```
工作流示例: "帮我写一篇关于AI的技术博客"

┌─────────────────────────────────────────────────────────┐
│                   Agent 工作流                           │
│                                                         │
│  ┌──────────┐                                           │
│  │ Planner  │ "分析需求,制定写作计划"                    │
│  │ (规划)   │ → 输出: 文章大纲                           │
│  └────┬─────┘                                           │
│       │                                                 │
│       ▼                                                 │
│  ┌──────────┐                                           │
│  │ Writer   │ "根据大纲撰写正文"                         │
│  │ (写作)   │ → 输出: 文章初稿                           │
│  └────┬─────┘                                           │
│       │                                                 │
│       ▼                                                 │
│  ┌──────────┐                                           │
│  │ Reviewer │ "审校文章,修改错误"                        │
│  │ (审校)   │ → 输出: 终稿                              │
│  └────┬─────┘                                           │
│       │                                                 │
│       ▼                                                 │
│  ┌──────────┐                                           │
│  │ Publisher│ "格式化输出,发布"                          │
│  │ (发布)   │ → 输出: 最终结果                           │
│  └──────────┘                                           │
└─────────────────────────────────────────────────────────┘
```

#### 工作流编排模式

```
支持 3 种编排模式:

1. 串行模式 (Sequential):
   Agent A → Agent B → Agent C
   适用: 流程固定的任务

2. 并行模式 (Parallel):
   ┌→ Agent A ─┐
   │           ├→ 汇总
   └→ Agent B ─┘
   适用: 可并行的子任务

3. 条件模式 (Conditional):
   Agent A → 判断 → True  → Agent B
                   → False → Agent C
   适用: 需要决策分支的任务
```

### 5.4 Agent 工作流配置

```yaml
agent:
  workflows:
    - name: "内容创作流"
      steps:
        - name: "规划"
          agent: "planner"
          input: "${user_message}"
          output: "outline"
        
        - name: "写作"
          agent: "writer"
          input: "根据大纲撰写: ${outline}"
          output: "draft"
          depends_on: ["规划"]
        
        - name: "审校"
          agent: "reviewer"
          input: "审校文章: ${draft}"
          output: "final"
          depends_on: ["写作"]
```

## 附录: 技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 向量库性能瓶颈 | 检索慢 | PgVector 索引优化，必要时迁移 Milvus |
| 文档解析兼容性 | 部分文档解析失败 | 多解析器兜底，失败记录原因 |
| JWT Token 安全 | Token 被盗用 | 短有效期 + Refresh Token + Redis 黑名单 |
| 多用户并发 | 性能下降 | Redis 缓存 + 数据库连接池优化 |
| 工作流编排复杂 | 难以维护 | 先支持简单串行，逐步增强 |
