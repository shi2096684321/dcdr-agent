## 1. 现状（单实例 dev）

- 应用：Spring Boot WebFlux，单个进程即可承载（无本地有状态限制）。
- 数据库：**PostgreSQL + PgVector**（`pg` profile，`application-pg.yml`）—— 开发与生产唯一选择；H2 仅测试替身。

- 可观测：应用自身 `/api/monitor/*`（内置面板）+ Actuator/Prometheus + Zipkin（默认 localhost:9411）。

生产建议一律走 `--spring.profiles.active=pg`（`ddl-auto: update`，启动时由 JPA 自动补齐新增的表/列/索引；表结构的规范来源仍为 `docs/sql/*.sql`）。

## 2. 生产拓扑（目标）

```
                    ┌──────────────────────┐
     客户端 ──► LB ──┤  app-1  (只读副本)   │
  (HTTPS/Nginx)     │  app-2  (只读副本)   │   ← 水平扩展, 实例间无状态
                    │  app-N  (只读副本)   │
                    └────────┬─────────────┘
                             │ JDBC / PgVector
                    ┌────────▼─────────────┐
                    │  PG 主库 (可写)       │
                    │    │  streaming repl │
                    │    ▼                 │
                    │  PG 备库 (只读)       │  ← 故障切换/只读流量
                    └──────────────────────┘
      可观测(单点/集中): Prometheus ──► Grafana   |   Zipkin
```

主要组件：
- **应用无状态，可水平扩展**：会话(SessionEntity)与知识库/工作流均持久化于 PG，不依赖本地内存扩展性强的状态（`LlmCallTrace` 为单请求内对象，每次请求自建即弃，不跨实例）。
- **数据库**：PG 主从（streaming replication）或 Patroni 高可用。
- **负载均衡**：Nginx / 云 LB，仅 7 层转发，负责 WebSocket/SSE 长连接(需关闭 body 缓冲)。

> 注意：V3.0 尚未启用 Redis（F-40.10 缓存属批次 B）。在多实例下，进程内限流计数、熔断快照、内存缓存均为**实例本地**，如需集群级精确统计须引入集中式组件（Redis）或聚合抓取。

## 3. 多实例部署注意点（清单）

| 关注点 | 说明 | 落地 |
|---|---|---|
| JWT 密钥 | 所有实例必须使用**相同** `JWT_SECRET`，否则跨实例 token 校验互不认 | env 统一注入 |
| 限流 | [RateLimitWebFilter](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/config/RateLimitWebFilter.java) 为**进程内**计数，多实例会放大总限额 N 倍 | 需要精确限额时改集中式计数（Redis） |
| 熔断/指标 | `dcdr_llm_*`、熔断快照为实例本地；内置面板看的是当前实例 | 集群维度需 Prometheus 多 target 抓取聚合 |
| 连接池 | 每实例 Hikari `maximum-pool-size` 需与 PG `max_connections` 分配：`total = N × pool-size` 预留余量 | 见 [application-pg.yml](file:///d:/Projects/java-agent/src/main/resources/application-pg.yml) |
| 日志/traceId | 各实例日志需统一写入集中收集（如 Loki/日志服务），以 `traceId` 跨实例串联 | Zipkin 已支持 W3C 传播 |
| 定时/后台任务 | 若部署多实例，定时任务需避免重复执行（分布式锁或仅单实例启用调度） | 后续评估 |

## 4. PostgreSQL 主从（streaming replication 快速指南）

前置：已在主库执行 `docs/sql/v2.0_schema.sql`（含 pgvector 扩展）。

**主库 `postgresql.conf`**
```ini
wal_level = replica
max_wal_senders = 5
max_replication_slots = 5
wal_keep_size = 256         # 或启用连续归档
```

**主库创建复制账号**
```sql
CREATE ROLE repl LOGIN REPLICATION PASSWORD 'repl_secret';
-- pg_hba.conf: host replication repl <备库IP>/32 scram-sha-256
```

**备库初始化（streaming 复制）**
```bash
pg_basebackup -h 主库 -U repl -D /var/lib/pgsql/data -R -X stream -P
systemctl start postgresql   # 备库进入恢复模式, 持续跟随主库
# 验证
psql -c "SELECT * FROM pg_stat_replication;"
```

**故障切换**：主库故障时把某备库提升为主：
```bash
pg_ctl promote -D /var/lib/pgsql/data     # 或以 PITR/Patroni 自动提升
```

> 更高可用（自动选主、VIP、健康检查）建议使用 **Patroni + etcd/Consul**，这里不展开；生产从 streaming 复制起步即可。

## 5. PgVector 主从注意事项

- 向量表 `document_chunks.embedding VECTOR(1536)` 与普通表一并复制，主从数据一致，**备库可承担只读检索**。
- RAG 写入（上传文档→切块→向量插入）走**主库**；若把检索流量切到备库，需注意 **复制延迟** 造成刚上传的 chunk 在备库不可见的窗口。
- `pgvector` 索引（HNSW/IVFFlat）随复制保留，无需在备库重建。

## 6. Zipkin 单点与集中化

- Zipkin 本身无状态（数据在存储层），可独立部署到生产环境（`docker run -p 9411:9411 openzipkin/zipkin` 或 Kubernetes Deployment）。
- 上报开关与地址由环境变量控制（见 application.yml `management.zipkin.tracing.*`，用 `ZIPKIN_EXPORT_ENABLED` / `ZIPKIN_ENDPOINT` 注入）。
- 多实例的 span 按 `traceId` 自动聚合到同一链路，业务 span（`llm.call` 等）亦属于同 trace。
