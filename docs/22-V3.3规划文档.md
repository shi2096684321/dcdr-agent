## 1. 版本概述

### 1.1 V3.3 定位

V3.3 不新增平台级基础设施，只做"最后一公里"：把能力从界面里放出来，落到用户真实的工作环境里。

| 方向 | 内容 | 依据 |
|------|------|------|
| 本机能力 | 工作区：用户授权一个目录，模型在其中读写删，改动可撤回 | 用户核心诉求是"改我的仓库"，上传副本再拷回去无法接受（详见 `docs/21`） |
| 主动通知 | 定时任务执行结果推送到企业微信 / 钉钉 | 定时任务此前只有"下次打开页面才看得到"的结果，等于没有反馈闭环 |

### 1.2 与 V3.2 的关系

- V3.2 全部能力保持兼容，本版仅增量扩展（新包、新配置项、新表字段，默认关闭）
- 仍是**本机优先**形态：工作区功能在 `local-mode=false` 时整体不注册

## 2. 现状与差距分析

| 能力 | V3.2 现状 | V3.3 目标 | 差距 |
|------|-----------|-----------|------|
| 文件操作 | 只能通过上传/下载附件间接处理 | 直接在授权目录内读、写、删，带 diff 与撤回 | 缺工作区抽象、路径校验、快照回收区 |
| 定时任务反馈 | 执行完只回写 `last_status`，用户要主动打开页面才看得到结果 | 结果主动推送到 IM，失败必达 | 缺出站通知能力（现有 `webhook_endpoints` 是**入站触发**，方向相反） |

> **一个容易误判的点**：项目里已有 `WebhookEndpointEntity` / `WebhookController`，
> 但那是「外部系统 POST 进来触发工作流」，是**入站**。推送是**出站**，两者不能复用同一套模型。

## 4. F-49 工作区与本地文件操作

完整设计（范围界定、为什么不用沙箱、路径校验、三级撤回、内容寻址快照）见
[`docs/21-工作区与本地文件操作设计.md`](21-工作区与本地文件操作设计.md)，此处只记录结论：

- 三档访问级别 `READ ⊂ WRITE ⊂ FULL`，删权限必须显式升级，模型无权影响档位
- 删除一律进回收区（内容寻址 blob），永不直接 `Files.delete`
- 撤回分三级：单操作撤销（L1）/ 按轮次撤回（L2）/ 整会话回滚（L3）
- 默认关闭：`agent.workspace.enabled=false`

## 5. F-50 定时任务执行结果推送

### 5.1 问题

定时任务（F-26）执行完成后只把 `last_status` / `last_output` 写回数据库。用户必须主动打开
「定时任务」页才能知道「今天的晨报跑出来没有」「昨晚的数据同步是不是失败了」。

结果是两类事故：

1. **失败无声**：任务连挂三天，第四天打开页面才发现；
2. **成功也无感**：定时生成的内容没人看，等于白花模型费用。

要的是：**任务跑完，结果主动找到人。**

### 5.2 渠道选型（本功能最关键的一个决策）

个人微信（微信 App 本体）**没有任何官方推送 API** —— 腾讯从未开放过。市面上"推送到个人微信"的方案只有三条路：

| 方案 | 消息落点 | 是否官方接口 | 数据经过谁 | 主要限制 | 结论 |
|------|----------|--------------|-----------|----------|------|
| **企业微信群机器人** | 企微群；配合「微信插件」可同步到个人微信 | ✅ `qyapi.weixin.qq.com` | 仅腾讯 | 20 条/分钟；markdown 4096 **字节** | **采用** |
| **钉钉群机器人** | 钉钉群 | ✅ `oapi.dingtalk.com` | 仅阿里 | 20 条/分钟，超限**封 10 分钟** | **采用** |
| 公众号模板消息 | 个人微信 | ✅ | 腾讯 | 需认证服务号（企业主体）+ openid + 模板审核 | 前置成本过高，未做 |
| Server酱 / PushPlus 等 | 个人微信 | ❌ 第三方中转 | **对方服务器完整留存正文** | 免费额度极低（Server酱 5 条/天）；服务无契约保障 | **不采用** |
| 个人微信协议库 | 个人微信 | ❌ 违反平台协议 | 第三方 | 封号 | **禁止** |

**为什么拒绝第三方中转**：本项目的定时任务推的是 `ChatResponse.getContent()`，即 Agent 生成的正文。
Agent 能读工作区文件、能执行代码，输出里完全可能带业务字段、代码片段甚至凭据。
走中转等于把这些内容原样发到别人的磁盘上。而企业微信这条路配合官方「微信插件」
（管理员在 `我的企业 → 微信插件` 取二维码，成员用个人微信扫码关注）**同样能让消息进个人微信**，
且全程只经过腾讯。

> 官方帮助中心原文：「关注插件后可以在微信中使用第三方和自建应用、**接收应用的推送**。」
> —— 即"推到个人微信"这个需求本身是官方支持的，只是入口在企业微信而不是微信。

### 5.3 架构

```
cron 到点 → ScheduledTaskService.runJob
          → runOnce() 拿到 content + status
          → notifyAsync()  ← boundedElastic，不占调度线程
          → NotifierRegistry.dispatch()  ← 渠道选择 + 节流
          → Notifier 实现（WecomBotNotifier / DingtalkBotNotifier）
```

分层职责：

| 组件 | 职责 | 关键约束 |
|------|------|----------|
| `Notifier` | 单个渠道的发送实现 | **不得向外抛异常**，一切问题转成 `NotifyResult` |
| `NotifierRegistry` | 渠道路由 + 节流 + 三态结果 | 永不抛异常；跳过与失败必须区分 |
| `NotifyRender` | 两渠道共用的消息渲染与截断 | 字节版与字符版分开，不允许混用 |
| `ScheduledTaskService` | 异步编排、状态回写 | 推送失败**不得**修改任务的 `last_status` |

扩展方式：新增渠道 = 实现 `Notifier` + `@Component`，Registry 启动时自动收集，调度层零改动
（与 `Tool` + `ToolRegistry` 的扩展方式一致）。

### 5.4 数据模型

`scheduled_tasks` 新增 5 列（DDL 见 `docs/sql/v3.3_schema.sql` F-50 段落）：

| 列 | 类型 | 含义 |
|----|------|------|
| `notify_enabled` | BOOLEAN NOT NULL DEFAULT FALSE | 本任务是否推送（叠加在全局开关之上） |
| `notify_channel` | VARCHAR(32) | 渠道 code（`wecom_bot` / `dingtalk_bot`）；NULL = 跟随全局默认 |
| `notify_last_status` | VARCHAR(16) | `success` / `failed` / `skipped` |
| `notify_last_error` | TEXT | 失败或跳过的原因 |
| `notify_last_at` | TIMESTAMP | 最近一次推送时间 |

**为什么单独存 `notify_last_*` 而不复用 `last_status`**：两者语义不同。
任务成功但推送失败（比如 webhook 被删了），任务结果依然有效；
若合并成一个字段，用户会看到"失败"而误以为 Agent 执行挂了，于是重跑一次，白花一次模型费用。

**执行记录表 `scheduled_task_runs`**：`scheduled_tasks` 只留 last_status / last_error，
完整输出执行完就丢了 —— 于是"查看详情"的链接无处可指。该表存
`output(TEXT) / error / duration_ms / started_at / finished_at / share_token / share_expires_at`。

- 每次执行都落一条（手动触发也落，便于回看；只是不推送）
- 单任务保留最近 50 条：output 是 TEXT，抓取类任务一次上万字，分钟级任务不清理会持续膨胀
- 清理放在保存之后同步做，失败只记日志 —— 维护性动作不该影响任务成败

### 5.5 接口

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/scheduled-tasks/{id}/notify-test` | 立即推送一条测试消息，验证 Webhook 是否打通。不触发 Agent 执行，不写 `notify_last_*`，不占用节流窗口 |
| GET | `/api/scheduled-tasks/{id}/runs` | 执行历史列表（倒序，只含正文前 120 字摘要），默认 20 条、上限 100 |
| GET | `/api/scheduled-tasks/{id}/runs/{runId}` | 执行历史详情（含完整正文）；记录必须属于该任务才可读 |

> 列表刻意只返回摘要：一次输出可能上万字，全量塞进列表会让接口慢且没意义，点开某条再取详情。

**为什么必须有这个接口**：手动触发（`/trigger`）刻意不推送（结果就在页面上，再推一条只会让调试变刷屏）。
若没有测试入口，用户配好 Webhook 后只能干等下一次 cron 到点才知道通不通，排查成本极高。

### 5.6 配置项

| 配置 | 环境变量 | 默认 | 说明 |
|------|----------|------|------|
| `agent.notify.enabled` | `AGENT_NOTIFY_ENABLED` | `false` | 总开关，关闭时不产生任何外部请求 |
| `agent.notify.channel` | — | `WECOM_BOT` | 默认渠道 |
| `agent.notify.throttle-window-ms` | — | `600000` | 成功消息节流窗口；0 = 不节流 |
| `agent.notify.timeout-ms` | — | `5000` | 请求超时 |
| `agent.notify.wecom.webhook-url` | `AGENT_NOTIFY_WECOM_WEBHOOK` | 空 | 企微群机器人地址（含 key，属凭据） |
| `agent.notify.wecom.max-bytes` | — | `4096` | markdown 字节上限（只能调小） |
| `agent.notify.dingtalk.webhook-url` | `AGENT_NOTIFY_DINGTALK_WEBHOOK` | 空 | 钉钉群机器人地址 |
| `agent.notify.dingtalk.secret` | `AGENT_NOTIFY_DINGTALK_SECRET` | 空 | 加签密钥（`SEC` 开头）；留空表示不用加签 |
| `agent.notify.dingtalk.max-chars` | — | `18000` | markdown 字符上限（只能调小） |

> `max-bytes` 放在 `wecom` 下而不是顶层：两个渠道的计长单位不同（企微按字节、钉钉按字符），
> 共用一个字段迟早出错。

### 5.7 关键设计决策

**① 截断按渠道各自的计长单位，且不能切断多字节字符**

企业微信 markdown 是 **4096 字节**上限，一个汉字 3 字节、一个 emoji 4 字节 —— 4096 字节实际只能放
约 1300 个汉字。按字符截断必然超限；直接 `substring` 会把汉字/emoji 切成两半，渠道侧显示成乱码方块
**而且不报错**。

实现：切到目标位置后，若该字节是 UTF-8 续字节（高两位 `10`），向前回退到字符首字节。
钉钉按字符计长，走字符版截断，并处理代理对（末尾若是高位代理则回退一位）。
截断提示语本身也要占预算，否则"加了已截断提示"反而导致超限。

**② 推送必须异步**

调度线程池 `poolSize=4`，而推送是阻塞 HTTP 调用。一个渠道卡 5 秒，就会挤占其它定时任务的执行窗口。
推送统一丢到 `Schedulers.boundedElastic()` —— 既不占调度线程，也不占 `reactor-http-nio`。

**③ 失败消息不受节流，成功消息必须节流**

企业微信/钉钉都是 20 条/分钟硬限，钉钉超限后**封 10 分钟**。
定时任务可以配成每分钟跑一次，不节流就是自毁。但失败告警不能节流 ——
漏掉一次失败通知的代价远大于多收几条重复消息。

**④ 跳过 ≠ 失败**

`skipped`（总开关关闭 / 触发节流）是预期行为，`failed` 才是异常。
二者混为一谈会让前端持续显示"推送失败"，用户只能把整个功能关掉。

**⑤ HTTP 200 不等于发送成功**

两家都是通过 body 里的 `errcode` 表达业务错误（企微 `45009`、钉钉 `130101` / `310000`），
只看状态码会把"频率超限""签名错误"全记成成功。钉钉的错误码另外做了中文翻译，
原始 `errmsg` 是英文短句，直接展示用户看不出该改哪一项配置。

**⑥ 企业微信 webhook 地址里的 key、钉钉的 secret 是凭据**

只允许通过环境变量注入，不写进仓库的配置文件。

### 5.8 两个渠道的差异

| 维度 | 企业微信 | 钉钉 |
|------|----------|------|
| 计长单位 | **字节**（4096） | **字符**（约 20000） |
| 加签 | 不需要（key 在 URL 里） | 可选：`urlEncode(base64(hmacSha256(secret, timestamp + "\n" + secret)))`，拼在 URL query 上 |
| 着色 | 支持 `<font color="warning">` | **不支持**，传进去原样显示 |
| 超限后果 | 本次请求失败（`45009`） | **限流 10 分钟**（`130101`） |
| 安全模式 | key 即凭据 | 加签 / 自定义关键词 / IP 白名单 三选一 |

> 关键词模式注意：消息正文必须包含设定词，否则返回 `310000`。
> 本实现的标题固定为「定时任务执行完成 / 失败」，因此关键词填「定时任务」即可覆盖所有消息。

### 5.9 明确不做

| 不做 | 原因 |
|------|------|
| 富文本卡片（actionCard / template_card） | 内容以 Agent 正文为主，卡片模板反而限制表达；markdown 已够用 |
| @ 指定人 | 单人场景无意义；多人告警需要先有值班表，属于下一版 |
| 一个任务广播到多个渠道 | 目前无真实需求，会让"节流"和"重试"语义复杂化 |
| 推送失败的自动重试队列 | 同步重试会叠加频控风险；持久化重试队列的成本与收益不匹配。失败即记录，用户看界面/日志自行处理 |
| 推送内容裁剪（只推摘要） | 摘要本身需要模型二次调用，成本高于收益。改为按长度截断，保留头尾 |

### 5.10 验收标准

- [x] 任务执行成功后，消息出现在配置的群内，含任务名、时间、耗时、正文
- [x] 任务执行失败后，消息必达且不被节流
- [x] 超长正文按渠道上限截断，不出现乱码、不超限
- [x] 推送失败不影响任务的 `last_status`，且在界面「推送异常」单独展示
- [x] 总开关关闭时，不产生任何外部请求
- [x] 手动触发不推送；「测试推送」可立即验证连通性
- [x] 单测覆盖：字节/字符截断、节流、跳过与失败的区分、渠道路由、钉钉加签公式

## 7. 技术风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| Webhook 地址泄露 | 任何人可向群内灌消息 | 凭据走环境变量；群机器人 key 可在群内随时重置 |
| 出口网络不通（公司内网封锁 `qyapi` / `oapi`） | 推送持续失败 | 「测试推送」即时反馈；错误信息区分"未配置 / 请求异常 / errcode" |
| 集群多实例重复推送 | 同一任务推多条 | 定时任务本就有 `ClusterLock` 保证同一时刻只有一个实例执行，推送只从执行方发出；节流状态为进程内，符合该前提 |
| 频率超限 | 钉钉封 10 分钟，期间所有推送失败 | 成功消息 10 分钟节流；失败消息虽不节流，但失败本身通常不会高频 |
