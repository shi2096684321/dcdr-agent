## 1. 为什么要把 F-46 拆开做

F-46 原计划列了 5 项，看起来是"一套主从 + 一个 LB"。但把本地环境的**硬约束**摆出来后，优先级会翻转：

- 本机 Docker Desktop 是 **Hyper-V 后端、VM 固定 4096MB**（`memoryMiB=4096`，Hyper-V 不支持动态内存），而物理机 16GB 只剩约 1.8GB 可用 → **不可能给 VM 扩容**。
- 于是"跑两套 PG"在本机几乎必然挤爆内存。

但真正的结论是：**主从恰恰是 F-46 里最不需要本地验证的一项**（PostgreSQL 流复制本身很成熟），
而 `docs/13` 自己列出的三条"上多实例必须解决的前置债"才是本项目特有的风险，且**只需要一个 PG 就能验**：

```50:54:docs/13-部署与高可用.md
| 限流 | RateLimitWebFilter 为**进程内**计数，多实例会放大总限额 N 倍 | 需要精确限额时改集中式计数（Redis） |
| 熔断/指标 | `dcdr_llm_*`、熔断快照为实例本地；内置面板看的是当前实例 | 集群维度需 Prometheus 多 target 抓取聚合 |
| 定时/后台任务 | 若部署多实例，定时任务需避免重复执行（分布式锁或仅单实例启用调度） | 后续评估 |
```

**所以顺序是：先清偿前置债（本文件 §3），再演练多实例（§4），最后才是主从（§6）。**

## 2. 内存预算（演练前必读）

VM 里现有 6 个服务，**只有 postgres 设了上限**（`deploy.resources.limits.memory: 1g`），其余全靠抢：

| 组件 | 估算占用 | 演练时是否必需 |
|---|---|---|
| postgres（主库） | 限 1g，实际 200~400MB | ✅ |
| agent / agent-2（JVM） | 各 400~700MB | ✅ |
| redis | 10~20MB | ✅（集中式协调依赖它） |
| nginx | ~20MB | ✅（仅演练 A） |
| pg-standby | 限 256m | 仅演练 C |
| **zipkin（JVM）** | 200~300MB | ❌ 可停（`ZIPKIN_EXPORT_ENABLED=false` 时 traceId 仍进日志 MDC） |
| **searxng** | 60~120MB | ❌ 可停 |
| **opensandbox-server** | 100~200MB（+ 沙箱容器更多） | ❌ 可停（沙箱默认关闭） |

**演练前先腾内存** —— 方式是**只启动需要的服务**，而不是"先 up 再 stop"：

```powershell
docker compose -f docker-compose.yml -f docker-compose.app.yml -f docker-compose.ha.yml --profile ha up -d --build postgres redis agent agent-2 nginx
```

> ⚠️ 为什么不用 `docker compose stop zipkin searxng opensandbox-server` 这类写法：
> `stop` 之后一旦再执行 `docker compose up -d`，**被停掉的服务会被重新启动**，内存又回到原点。
> 命令行**显式列出服务名**时，compose 只会创建这些服务及其依赖；
> `zipkin` / `searxng` / `opensandbox-server` 不是任何服务的依赖（主文件里明确"沙箱起不来也不影响应用"），
> 因此不会被拉起。

HA 覆盖文件已给两个应用实例限住堆（`-Xmx384m` + `memory: 768m`）——
**必须显式设 `-Xmx`**：容器不设内存上限时 `-XX:MaxRAMPercentage=75.0`（Dockerfile 里的默认值）
会按 **VM 总内存 4GB** 计算，两个实例各自要 3GB 堆，必然撑爆。

## 3. 已落地：集群协调（多实例的前置债）

### 3.1 问题

`RateLimitWebFilter` 的计数与 `@Scheduled` 任务都是**进程内**状态，单实例正确、多实例错：

| 能力 | 单实例 | 多实例（未改造时） |
|---|---|---|
| API 限流 | 60 req/min | **60 × N**（各实例各算） |
| 工作流兜底扫描 | 每 5 分钟一次 | **N 次**（互相重复扫同一批数据） |
| 用户自定义 cron 定时任务 | 到点执行一次 | **N 次** → 重复触发 Agent（重复会话 + **重复模型费用**） |
| 预置模板初始化 | 首次插入 | 两个实例同时判空 → 同时插入相同主键 → **约束冲突导致启动失败** |

### 3.2 配置

```yaml
agent:
  v3:
    cluster:
      # memory(默认, 单实例, 行为与 V3.0 完全一致) | redis(多实例必需)
      backend: memory
      # 实例标识(租约持有者); 留空自动生成"主机名-随机后缀"
      instance-id: ""

spring:
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
      timeout: 2s
```

- `backend=memory` 时 Lettuce 连接工厂**惰性**，不会建立任何连接 —— 所以单实例部署引了这个依赖也没有副作用，**默认行为与 V3.0 逐字一致**。
- 切 `redis` 只改配置，**代码不动**（这是把两种实现都做成 Bean 而不是"单实例一套逻辑"的原因）。

启动日志会明确给出最终生效状态（不用猜）：

```
V3.1 F-46 集群协调最终状态: instance=app-1, 期望backend=redis, 实际=redis |
  限流=集中式计数 | 定时任务互斥=开启(租约锁)
```

### 3.3 两处实现

| 能力 | 接口 | redis 实现要点 |
|---|---|---|
| 限流计数 | `RateLimitStore` | 固定窗口 + **窗口分桶**：`INCR dcdr:ratelimit:{key}:{窗口序号}`，桶首次写入补 `EXPIRE`。分桶把窗口边界编码进 key，多实例并发下无需竞争"谁来重置 TTL"；单次 INCR 判定，不做二次读回 |
| 定时任务互斥 | `ClusterLock` | 加锁 `SET key <instanceId> NX PX <ttl>`；解锁用 **Lua 比对持有者再删**——直接 `DEL` 会误删"已被他人接管的租约"，导致同一时刻两个实例都在执行 |

接入点：

- `ScheduledTaskService.runJob` —— 用户 cron 任务，锁名 `scheduled:task:{taskId}`。
  **手动触发（`trigger`）刻意不加锁**：那是用户主动动作，重复执行语义是"用户点了两次"，不该被集群锁静默吞掉。
- `WorkflowExecutionSweeper` —— 锁名 `scheduled:workflow-sweeper`（原实现只靠"幂等"容忍重复，但重复扫描仍会白跑全表查询并互相打架）。
- `AgentTemplateInitializer` / `WorkflowTemplateInitializer` —— **不用锁，改用唯一约束容错**：
  逐条 `saveAndFlush` + 捕获 `DataIntegrityViolationException`。理由：锁只解决"同时"，而持锁实例崩溃会让另一个实例跳过初始化导致模板缺失；对唯一约束容错是与时序无关的确定性方案。
  （用 `saveAndFlush` 而非 `save` 是关键：`save` 的 INSERT 可能在方法返回后才 flush，那时异常已脱离 try 块。）

### 3.4 降级语义：为什么是 fail-open

| 场景 | 行为 |
|---|---|
| `backend=redis` 但依赖缺失 | 降级 memory + WARN（不让"配置漏引依赖"变成启动失败） |
| Redis 运行期不可用（**限流**） | 回退进程内计数 + WARN（限频输出） |
| Redis 运行期不可用（**租约锁**） | **fail-open（返回 true）** + WARN |

租约锁选择 fail-open 的理由：它保护的是"定时任务别重复执行"，属优化而非正确性红线。
fail-closed 的后果是 **Redis 一挂、所有定时任务彻底停摆**，比"偶尔重复执行一次"严重得多。
若将来出现"重复执行不可接受"的任务，**应在任务自身做幂等**，而不是把锁改成 fail-closed。

### 3.5 没覆盖的那笔债（重要）

三条前置债里，本文件只清偿了两条。**"熔断/指标实例本地"仍未解决**：

- `LlmMetrics`（`dcdr_llm_*`）与熔断快照都是**实例内存**，内置监控面板看的是"当前实例"。
- 要集群维度视图，需要 **Prometheus 多 target 抓取 + 聚合** —— `Micrometer` 埋点已具备（`/actuator/prometheus`），但**部署侧没有 Prometheus/Grafana**（`docker-compose.yml` 只有 zipkin）。
- 结论：**这一条不解决，多实例下的监控数据就是 1/N 的碎片**。它不阻塞演练，但阻塞"用监控判断集群健康"。

### 4.2 验收点

1. **两实例都起来了且都在集群模式**
   ```powershell
   docker logs dcdr-agent-app   | Select-String "集群协调最终状态"
   docker logs dcdr-agent-app-2 | Select-String "集群协调最终状态"
   ```
   两行都应显示 `实际=redis | 定时任务互斥=开启(租约锁)`，且 `instance` 分别是 `app-1` / `app-2`。

2. **限流是集中式的（这是本演练的核心验收）**
   在 `application.yml` 临时把 `agent.v3.rate-limit.enabled` 改 `true`（或启动参数覆盖），然后并发打统一入口：
   ```powershell
   1..200 | ForEach-Object -Parallel { Invoke-WebRequest -Uri 'http://localhost:8090/api/sessions' -SkipHttpErrorCheck -MaximumRetryCount 0 } -ThrottleLimit 20 |
     Group-Object StatusCode | Select-Object Name, Count
   ```
   **判定标准**：总放行数应接近配置的 `ip-requests-per-minute`（默认 120），而**不是 120 × 2**。
   改造前会看到接近 240（两实例各放行 120）。
   另可直接看 Redis 里的桶：
   ```powershell
   docker exec dcdr-agent-redis redis-cli --scan --pattern "dcdr:ratelimit:*"
   ```

3. **定时任务只执行一次**：建一个每分钟触发的定时任务，观察两个实例日志 ——
   `定时任务触发: xxx` 应**只出现在其中一个实例**；另一个实例只有 DEBUG 级的"已由其他实例执行, 本次跳过"。

4. **SSE 流式经 nginx 不被缓冲**：走 `http://localhost:8090` 发起流式对话，
   前端应**逐步**出现文字，而不是"转圈很久后一次性全部出现"。
   （若不逐步出现 → `docker/nginx/nginx.conf` 的 `proxy_buffering off` 没生效。）

5. **无粘滞会话也能正常工作**：JWT 是无状态的、会话数据在 PG，刷新页面/多标签页应正常
   （nginx upstream 是轮询，请求会落到不同实例）。

## 5. 演练 B：备份恢复（本地可做，零额外内存）

这项**单实例就能做**，且产出的正是"RTO/RPO 达标"的验收数字 —— 性价比最高。

### 5.1 步骤

```powershell
# 1. 备份（脚本已存在：scripts/backup-db.ps1，落点是宿主机 <项目>/data/backup）
powershell -ExecutionPolicy Bypass -File scripts\backup-db.ps1

# 2. 记录"最后一个业务数据"的时间戳（用于算 RPO），例如：
docker exec dcdr-agent-pg psql -U dcdr_agent -d dcdr_agent -c "SELECT now(), count(*) FROM sessions"

# 3. 恢复演练（恢复脚本：scripts/restore-db.sh，在容器内执行）
docker cp data\backup\<备份文件> dcdr-agent-pg:/backup/restore-test.dump
docker exec dcdr-agent-pg sh /scripts/restore-db.sh /backup/restore-test.dump   # 具体参数见脚本用法
```

### 5.2 需要记录的数字（F-46 验收依据）

| 指标 | 含义 | 本次实测 |
|---|---|---|
| RTO | 从"开始恢复"到"应用可正常读写"的耗时 | 待填 |
| RPO | 备份时刻 → 故障时刻之间丢失的数据量（= 备份周期） | 待填（当前为**每日 02:00 全量**） |
| 数据完整性 | 恢复后关键表行数与原库一致 | 待填 |

> **当前 RPO 的现实**：只有每日全量 `pg_dump`（Windows 计划任务 `dcdr-agent-db-backup`，02:00），
> **没有 WAL 归档** → 最坏情况丢一天数据。要收敛 RPO 必须上 WAL 连续归档（PITR），
> 这一步本文件未做，见 §8。

## 6. 演练 C：主从复制与手动切换（本地可做，需 256MB）

### 6.1 主库侧准备（一次性，幂等）

```powershell
powershell -ExecutionPolicy Bypass -File scripts\ha-standby-init.ps1
```

脚本做三件事：创建复制角色 `repl`（`LOGIN REPLICATION`）、在 `pg_hba.conf` 放行
`host replication all all scram-sha-256` 并 reload、核对 `wal_level`。
（PG16 的 `wal_level` 默认就是 `replica`，故**主库无需改配置、无需重启**。）

### 6.2 启动备库

```powershell
docker compose -f docker-compose.yml -f docker-compose.app.yml -f docker-compose.ha.yml --profile ha up -d pg-standby
docker logs -f dcdr-agent-pg-standby     # 首次启动会自动 pg_basebackup，约 10~60 秒
```

备库内存压到 256m 的依据：备库只做"收 WAL + replay"，**不承担业务查询**，
故 `shared_buffers=32MB / work_mem=2MB / max_connections=20 / autovacuum=off` 足够（主库是 1g）。

### 6.3 验收要点

```powershell
# 1) 主库看得到备库在流复制（application_name = standby-1）
docker exec dcdr-agent-pg psql -U dcdr_agent -d dcdr_agent -c "SELECT application_name, state, sync_state, replay_lag FROM pg_stat_replication"

# 2) 写一条数据到主库，确认能复制到备库（只读）
docker exec dcdr-agent-pg psql -U dcdr_agent -d dcdr_agent -c "CREATE TABLE IF NOT EXISTS ha_probe(ts timestamptz default now())"
docker exec dcdr-agent-pg psql -U dcdr_agent -d dcdr_agent -c "INSERT INTO ha_probe DEFAULT VALUES"
docker exec dcdr-agent-pg-standby psql -U dcdr_agent -d dcdr_agent -c "SELECT count(*) FROM ha_probe"

# 3) 备库确认是"只读 + 在恢复中"
docker exec dcdr-agent-pg-standby psql -U dcdr_agent -d dcdr_agent -c "SELECT pg_is_in_recovery()"   # 期望 t
```

**pgvector 随库复制**：`document_chunks.embedding VECTOR(1536)` 与 ivfflat/trgm 索引一并复制到备库，
无需在备库重建（见 `docs/13` §5）。

### 6.4 手动切换演练（模拟主库故障）

```powershell
# 1. 停主库，模拟故障
docker stop dcdr-agent-pg

# 2. 提升备库为主
docker exec dcdr-agent-pg-standby pg_ctl promote -D /var/lib/postgresql/data
docker exec dcdr-agent-pg-standby psql -U dcdr_agent -d dcdr_agent -c "SELECT pg_is_in_recovery()"  # 期望 f

# 3. 让应用改连新主：备库未映射宿主端口，故临时加一个端口或改 compose 后重启应用
#    （真实环境这里应是 VIP / Patroni 自动完成，本机演练用手工改连接串即可）

# 4. 记录 RTO：从"停主库"到"应用恢复可写"的耗时
```

### 6.5 清理重来

```powershell
docker compose -f docker-compose.yml -f docker-compose.app.yml -f docker-compose.ha.yml --profile ha down
docker volume rm java-agent_pgstandbydata     # 备库数据卷；重建代价 = 一次 pg_basebackup
```

⚠️ **不要在演练中 `rm` 主库卷 `pgdata`**：那会重演 2026-09-28 的数据全丢事故（见 `TODO.md`）。

## 8. 实测验证结果（2026-10-13）

本节记录**真实执行**的结果，而非设计意图。环境：本机 Redis 7 + PostgreSQL 16（均在 compose 内），
应用在**宿主**以 `-Xmx256m` 启动两个实例（8080 = app-1 / 8081 = app-2）。

### 8.1 自动化测试

| 层 | 测试类 | 用例 | 结果 |
|---|---|---|---|
| 单元 | `InMemoryRateLimitStoreTest` | 5 | ✅ |
| 单元 | `ClusterAutoConfigurationTest` | 6 | ✅ |
| 集成（真实 Redis） | `RedisClusterCoordinationIT` | 7 | ✅ |
| 回归 | `mvn test` 全量 | **243 / 0 失败**（改造前 232） | ✅ |

集成测试覆盖的行为：两节点共享计数、计数桶带 TTL、租约互斥、**越权释放无效**、
**租约过期自动接管**、Redis 不可用时锁 fail-open、限流降级为进程内计数（既不阻塞也不全放行）。
后两条在运行时真实触发了告警日志（`Unable to connect to Redis`，指向一个不存在的端口）。

### 8.2 限流跨实例共享（端到端）

两实例均 `backend=redis`、限额 `5 req/min`，**交替**打两个实例共 10 次请求：

| 请求 | 目标实例 | 结果 |
|---|---|---|
| 1 | app-1 | 200 |
| 2 | app-2 | 200 |
| 3 | app-1 | 200 |
| 4 | app-2 | 200 |
| 5 | app-1 | 200 |
| **6** | **app-2** | **429 ← 关键** |
| 7 ~ 10 | 交替 | 429 |

Redis 里只有一个共享桶：

```
dcdr:ratelimit:ip:0:0:0:0:0:0:0:1:29864660   value=10   ttl=57
```

**第 6 次请求落在 app-2 上却被拒绝** —— 因为配额已被 app-1 消耗完，计数确实跨实例共享。
若各实例各算，第 6~10 次里属于 app-2 的仍会放行，总数会变成 10。

### 8.3 定时任务互斥（A/B 对照）

同一个定时任务（`cron = 0 * * * * *`，每分钟触发），两个实例都在启动时加载它，然后只改后端对比：

| 后端 | 16:22:00 | 16:23:00 | 16:24:00 | 16:25:00 |
|---|---|---|---|---|
| `redis`（租约锁） | 仅 app-2，**1 次** | 仅 app-1，**1 次** | — | — |
| `memory`（未启用） | — | — | app-1 + app-2，**2 次** | app-1 + app-2，**2 次** |

两个结论：

1. `redis` 下每个触发时刻**只有一行日志**，且相邻两次由**不同实例**接手 ——
   说明两个实例都注册了该任务、都在竞争租约，而不是"有一边根本没调度"（排除了假阳性）。
2. `memory` 下每个触发时刻**两行日志** —— 这正是未改造时的真实行为：
   重复触发 Agent、重复创建会话、重复产生模型费用。

### 8.4 顺带修掉的一个既有缺陷

`InMemoryRateLimitStore` 的前身（V3.0 内联在 `RateLimitWebFilter` 里的 `Window`）
用 `volatile int count` + `++`，而**自增不是原子操作** —— 并发下会丢增量，
于是"实际放行数 > 配置限额"。这是写并发用例时暴露出来的，不是靠读代码看出来的。

已改为 `AtomicInteger`，并由 `InMemoryRateLimitStoreTest#concurrentAcquireIsExact`
（16 线程 × 50 次、limit=50，断言放行数**恰好** 50）长期锁住。

## 9. 已知边界与未做清单

**本次已做**

- 集中式限流计数（`RateLimitStore`：memory / redis）
- 定时任务跨实例互斥（`ClusterLock`：local / redis；覆盖用户 cron 任务 + 工作流兜底扫描）
- 预置模板初始化的并发安全（唯一约束容错，替代"启动即冲突失败"）
- `RateLimitWebFilter` 顺带修掉两个既有缺陷：计数**自增非原子**（并发下多放行）与**条目永不移除**（内存泄漏面）
- 新增测试：`InMemoryRateLimitStoreTest`(5) + `ClusterAutoConfigurationTest`(6) + `RedisClusterCoordinationIT`(7)
- HA 演练编排（nginx + agent-2 + pg-standby，profile 隔离）
- 备库自动化（容器首次启动即 `pg_basebackup`）+ 主库侧准备脚本（幂等）

**本次未做（按优先级）**

1. **指标/熔断的多实例聚合**（§3.5）：需部署 Prometheus + Grafana + 多 target 抓取。这是三条前置债里唯一没清的一条。
2. **WAL 连续归档 + PITR**：不解决则 RPO = 一天（§5.2）。
3. **登录失败锁定的多实例语义**：`AuthService.failureMap` 是**进程内** Map →
   多实例下"5 次失败锁定"会被放大成 `5 × N` 次。它不影响安全（不会放宽），但会让锁定行为不一致。
   与限流同源，可复用 `RateLimitStore` 的思路。
4. **定时任务的分布式精确调度**：当前是"每实例都注册 + 租约互斥"，属**抢到就执行**；
   严格语义应改为"DB 里 `next_run_at` + 条件 UPDATE 抢占"（避免多实例重复计算触发时间）。
   实测还暴露了现状的另一半：**`create` / `update` 只把任务注册到"处理该请求的实例"上**
   （`scheduleInternal` 是进程内动作），其他实例要等重启才会加载它。
   于是"刚建的任务"在多实例下只有 1/N 概率被某个实例执行 —— 靠租约锁只能防重复，防不了这个。
   这条与上面的"抢占式调度"是同一个改动，应一起做。
5. **优雅停机与 in-flight 任务**：`server.shutdown: graceful` 已配，
   但多实例下"实例被摘除时正在跑的 Agent 任务"仍会中断，需与 LB 的 `fail_timeout` 配合调优。
6. **多实例 + `ToolResultSpillStore`**：落盘目录是本地 `./data/tool-results/{sessionId}`，
   跨实例读取会失败（模型调用 `tool_result_read` 时若被路由到另一实例就取不到文件）。
   **这是多实例下一个真实的破坏性缺陷**，需要把落盘换成共享存储或对象存储。
7. **`routing_logs` / `audit_logs` 过期归档任务**（F-46 原计划第 4 项）未做。
