# Java AI Agent 框架对照版学习计划

| 项目名称 | Java AI Agent - 框架对照学习分支 |
|---------|----------------------------------|
| 文档版本 | V1.1 |
| 创建日期 | 2026-08-14 |
| 状态 | 进行中（Step 1 已完成） |
| 前置条件 | V3.0-alpha 完成（F-30 智能路由 + F-33 执行容错） |

> **定位**：这不是生产版本，是一次"对照学习"练习。目标是吃透 AI 工程的设计抽象，
> 不是产出可上线代码。两套代码不会同时维护，框架版完成后归档。

---

## 1. 为什么做

主线（手写版）解决"怎么实现"——理解 RAG、Tool Calling、Agent 编排的底层机制。
对照版解决"怎么抽象"——看业界（LangChain4j）如何把同样的问题抽象成可复用组件。

只有手写版，容易停留在"能跑但设计粗糙"；只有框架版，会用但不理解底层。
两者结合才完整。

---

## 2. 启动时机

**V3.0-alpha 完成后启动**，原因：
- 刚手写完 F-30 智能路由（LLM 做系统决策）和 F-33 执行容错（状态机 + 断点续跑）
- 此时对 Agent 编排、状态管理记忆最新，对照感受最强
- 不要等 V3.0 全做完——周期太长，对照学习的热度会衰减

## 3. 分支策略

```
main (手写版, 生产主线)
  │
  └─ feature/langchain4j-refactor  (对照版, 不合并)
       │
       └─ 完成后: tag 归档, 保留分支不删除
```

- 从 main 切出，独立演进
- **不合并回主线**，避免污染手写版的硬约束设计
- 对照版可以大胆打破现有约束（embedding 维度、chunk 策略等），用框架默认行为跑通即可
- 完成后打 tag `langchain4j-refactor-v1`，分支保留作为学习记录

## 4. 框架选择

**LangChain4j**（不选 Spring AI）

| 维度 | LangChain4j | Spring AI |
|------|------------|-----------|
| Agent 抽象 | `AiServices` + 接口代理，纯粹 | Advisor 链，偏 Spring 生态 |
| RAG 抽象 | `RetrievalAugmentor` 独立可组合 | 偏向 Advisor 集成 |
| 学习价值 | 高（设计模式清晰） | 中（很多是 Spring 自动配置） |
| 与 WebFlux | 阻塞 API，需包裹 | 部分支持响应式 |

对照版目标是学抽象，不是学 Spring 集成，所以选 LangChain4j。
WebFlux 阻塞问题在对照版里可以暂时容忍（或直接换 MVC 跑通）。

---

## 5. 对照范围

只重写 AI 核心模块，平台工程模块不重写（重写学不到新东西）。

| 模块 | 是否重写 | 学习重点 |
|------|---------|---------|
| RAG 检索管线 | 是 | `EmbeddingStore` + `RetrievalAugmentor` 的组合设计 |
| Tool / Function Calling | 是 | `@Tool` 注解 + 自动 JSON Schema 生成 |
| Agent 编排（路由 + DAG） | 是 | `AiServices` 如何把 LLM + Tools + Memory 组合成 Agent |
| Memory | 选做 | `ChatMemory` 接口对比手写的 [InMemoryChatMemory](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/agent/memory/InMemoryChatMemory.java) |
| 模型 Provider 层 | 否 | 纯 HTTP 封装，重写无收益 |
| 多租户 / 监控 / 配额 | 否 | 与 AI 无关，平台工程 |
| 认证 / RBAC | 否 | V2.2 已完成，无关 AI |

## 6. 对照学习清单

### 6.1 RAG 检索管线

**手写版基线**：
- [EmbeddingProvider](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/rag/embedding/EmbeddingProvider.java) 抽象 + 各厂商实现
- [RetrievalService](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/rag/service/RetrievalService.java) Top-K + min-score 过滤
- [RecursiveSplitter](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/rag/splitter/RecursiveSplitter.java) 分块 + metadata 前缀注入
- [VectorType](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/entity/VectorType.java) 自实现 pgvector UserType

**对照 LangChain4j**：
- `EmbeddingStore<TextSegment>` 接口 vs 手写的 Repository + VectorType
- `DocumentSplitter` vs 手写的 RecursiveSplitter（看它如何处理 metadata）
- `RetrievalAugmentor` vs 手写的 Agentic RAG（LLM 决定是否检索）
- **反思点**：手写的 metadata 前缀策略、ThreadLocal 上下文时序，框架如何处理？框架不支持时是设计缺陷还是刻意为之？

### 6.2 Tool / Function Calling

**手写版基线**：
- [Tool](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/tool/Tool.java) 接口 + [ToolRegistry](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/tool/ToolRegistry.java) 手动注册
- [AbstractTool](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/tool/AbstractTool.java) 手写参数解析
- 手写 Function Calling JSON 往返

**对照 LangChain4j**：
- `@Tool` + `@P` 注解自动生成 JSON Schema
- `ToolSpecification` vs 手写的 ToolInfo
- 框架如何处理工具调用的错误、重试、超时
- **反思点**：手写参数解析的痛点，框架用注解 + 反射解决了；但手写版对参数校验的控制力更强

### 6.3 Agent 编排

**手写版基线**：
- [AgentOrchestrator](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/AgentOrchestrator.java) 工具调用循环
- [WorkflowEngine](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/agent/workflow/WorkflowEngine.java) 线性 steps 执行 + V3.0 的 DAG 扩展
- F-30 IntentRouter（LLM 做路由决策）

**对照 LangChain4j**：
- `AiServices.builder(Interface.class)` 把 LLM + Tools + Memory 组合成声明式 Agent
- 对比手写的"工具调用循环"——框架如何抽象 ReAct 循环
- 框架有没有 DAG 编排能力？（LangChain4j 偏单 Agent，多步编排较弱，这本身是个学习点）
- **反思点**：手写的 WorkflowEngine 是命令式编排，框架的 AiServices 是声明式组合，各有什么优劣？

### 6.4 Memory（选做）

**手写版基线**：[InMemoryChatMemory](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/agent/memory/InMemoryChatMemory.java) + [TokenEstimator](file:///d:/Projects/java-agent/src/main/java/com/dcdr/agent/agent/memory/TokenEstimator.java)

**对照 LangChain4j**：
- `ChatMemory` 接口 + `MessageWindowChatMemory`（按消息数裁剪）vs 手写的 token 估算裁剪
- 持久化实现（`ChatMemoryStore`）对比手写的 JPA 持久化
- **反思点**：按消息数 vs 按 token 裁剪，哪个更合理？框架为什么默认用消息数？

## 8. 收手标准

满足以下任一条件即停止：
1. 完成 Step 1-4（核心三个模块对照）
2. 连续两次感觉"在重复造轮子，学不到新东西"
3. 发现框架对某个模块的抽象明显不如手写版（说明手写设计已到位，对照无收益）

**不必追求功能对齐**——框架版不需要实现 V3.0 全部功能，跑通核心流程、写完对照笔记即可。
