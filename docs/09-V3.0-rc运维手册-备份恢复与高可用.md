# V3.0-rc 运维手册：备份恢复 · 分布式追踪 · 灾备高可用

> 适用范围：F-40.11（备份恢复）、F-40.12（分布式追踪）、F-40.13（灾备与高可用）。
> 本文面向运维/部署人员，配套脚本位于 `scripts/`。

---

## 1. F-40.11 备份恢复

### 1.1 备份策略

| 对象 | 方式 | 频率 | 保留 | 脚本 |
|------|------|------|------|------|
| PostgreSQL（会话/知识库/工作流/审计等全部业务表） | `pg_dump -Fc` 全量 | 每日 02:00 | 14 天 | `scripts/backup-db.sh` |
| 知识库原始文件（`./data/kb`、`./data/uploads`） | tar.gz 归档（生产建议 rsync 至对象存储） | 每日 | 30 天 | `scripts/backup-db.sh` |
| 配置（application-pg.yml + 环境变量清单） | Git 版本控制（不含密钥） | 每次发布 | 永久 | — |

### 1.2 定时任务配置

```bash
# crontab -e（应用服务器上）
0 2 * * * /opt/dcdr-agent/scripts/backup-db.sh >> /var/log/dcdr-backup.log 2>&1
```

环境变量可在脚本头部或 crontab 中覆盖：`DB_HOST / DB_PORT / DB_NAME / DB_USER / BACKUP_DIR / DATA_DIR`。

### 1.3 恢复流程

```bash
# 恢复到测试库（默认目标库名 agent，可指定新库名）
./restore-db.sh /var/backups/dcdr-agent/db/agent_20260827_020000.dump agent_restore_test
```

脚本内置保护：目标库已存在时中止（防误覆盖生产库）；恢复使用 `--single-transaction` 保证一致性；恢复后自动抽查核心表行数。

### 1.4 恢复演练（每季度一次）

1. 取最近一份 `.dump`，在测试环境执行 `restore-db.sh`；
2. 应用指向恢复库启动（`SPRING_PROFILES_ACTIVE=pg`，数据源指向新库名）；
3. 抽查清单：登录 → 会话列表与历史 → 知识库上传/检索 → 工作流执行 → 审计日志；
4. 记录实测 RTO，与目标值（≤ 30 分钟）对比；偏差大时优化备份/恢复链路；
5. 演练记录归档（日期、备份文件、RTO、问题）。

## 2. F-40.12 分布式追踪

### 2.1 依赖与配置

已引入 `micrometer-tracing-bridge-brave`（traceId 自动注入日志 MDC）与 `zipkin-reporter-brave`（导出）。

`application.yml`：

```yaml
management:
  tracing:
    sampling:
      probability: 0.1          # 采样率，排障时可临时调 1.0
    export:
      zipkin:
        enabled: true           # 默认 false；开启后上报 Zipkin
        endpoint: ${ZIPKIN_ENDPOINT:http://localhost:9411/api/v2/spans}
  propagation:
    type: w3c                    # traceparent 头跨服务传播

logging:
  pattern:
    console: "... [${traceId:-},${spanId:-}] ..."   # 日志带 traceId
```

### 2.2 启动 Zipkin

```bash
docker run -d --name zipkin -p 9411:9411 openzipkin/zipkin
# 浏览器打开 http://localhost:9411 查询链路
```

### 2.3 验证

1. `management.tracing.export.zipkin.enabled=true` 后发起一次对话；
2. 应用日志中出现非空 traceId：`... [64f5bcb3b9b1c484, 9e2c1f2b6a1c1d2e] ...`；
3. Zipkin UI 按 traceId 检索，可见 `对话 → 路由 → LLM 调用` 的 span 链路；
4. 不开启导出时（默认），traceId 仍写入日志，可按日志文件 grep 串联全链路。

### 2.4 与指标的关系

追踪与 Prometheus 指标（`/actuator/prometheus`）共用 Micrometer 体系；Grafana 看板可通过 Exemplars 关联指标点与 trace。采样率只影响导出，不影响日志 traceId 注入（100% 注入）。

## 3. F-40.13 灾备与高可用

### 3.1 目标

| 指标 | 目标 | 手段 |
|------|------|------|
| RPO | ≤ 5 分钟 | PostgreSQL WAL 归档（`archive_timeout=300s`） |
| RTO | ≤ 30 分钟 | Patroni 自动故障切换 + 应用多实例预热 |
| 应用可用性 | 单实例宕机无感 | 多实例 + Nginx 负载均衡 + 健康检查摘除 |
| 演练 | 每半年一次 | 模拟主库宕机，验证切换 |

### 3.2 应用多实例 + Nginx

```nginx
upstream dcdr_agent {
    least_conn;
    server 10.0.0.11:8080 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:8080 max_fails=3 fail_timeout=10s;
    # 健康检查摘除: 探活 /actuator/health (已在 auth permit-paths 白名单)
}

server {
    listen 443 ssl;
    location / {
        proxy_pass http://dcdr_agent;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_read_timeout 300s;      # SSE 流式对话长连接
        proxy_buffering off;          # SSE 必须关闭缓冲, 否则流式输出被攒包
    }
}
```

多实例部署注意：

1. **会话亲和性（sticky session）**：SSE 中断/继续依赖本实例的 `SessionManager` 内存态，Nginx 需按会话 Cookie 亲和（`ip_hash` 或 `hash $cookie_JSESSIONID`）；会话状态下沉 Redis 为后续演进项。
2. **本地文件**：`./data/kb` 等目录需挂共享存储（NFS/对象存储），否则各实例知识库不一致。
3. **插件目录**：F-37 插件 JAR 需同步到所有实例的 `./plugins`。
4. 实例无状态化程度：JWT 无状态鉴权天然支持多实例；限流/熔断为进程内统计，各实例独立计数（严格全局配额需下沉 Redis，规划允许）。

### 3.3 PostgreSQL 高可用

- 流复制 + Patroni + etcd 自动故障切换（标准方案）；
- 关键参数：`archive_mode=on`、`archive_timeout=300s`（RPO≤5min）、`synchronous_commit=remote_apply`（可选，牺牲吞吐换 RPO≈0）；
- 从库可兼任只读副本，分担知识库检索等读负载。

### 3.4 故障切换演练（每半年一次）

1. 主库执行 `pg_ctl stop -m fast` 模拟宕机；
2. 观察 Patroni 在 etcd 仲裁后自动提升从库（预期 < 1 分钟）；
3. 应用连接串使用 Patroni VIP/代理（pgbouncer + patroni rest api 或 HAProxy tcp 模式）自动重连；
4. 验证业务恢复（对话/上传/工作流），记录实际 RTO；
5. 拉起旧主库作为新从库，确认复制恢复。

### 3.5 备份与灾备的关系

- 备份（F-40.11）是最后防线：误删/逻辑损坏/勒索场景靠备份恢复，RPO=备份间隔；
- 复制 + 自动切换（本节）应对实例/主机级故障，RPO≈WAL 间隔；
- 两者同时保留，互不替代。
