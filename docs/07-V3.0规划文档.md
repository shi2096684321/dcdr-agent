## 1. 版本概述

### 1.1 V3.0 定位

V3.0 是 V2.x 系列的**生产化升级版本**。V2.3 已经具备了自定义 Agent、工作流编排、定时任务、流式图片生成的"骨架"能力，但存在五个关键缺口：

| 缺口 | 现状 | 生产级要求 |
|------|------|-----------|
| 用户需手动选择工作流 | 切页面、点按钮 | 对话即触发，用户无感 |
| 工作流模板需自己创建 | 空白页面从零搭 | 预置模板 + 模板市场 |
| 编排方式是表单填空 | 写 `contains(text,"YES")` 表达式 | 拖拽式可视化 DAG |
| 执行失败即中断 | 无重试、无续跑 | 失败重试 + 断点续跑 + 人工审批 |
| 无治理能力 | 无监控、无版本、无成本追踪 | 全链路可观测 |

V3.0 的目标就是补齐这五个缺口，让平台达到生产可用水平。

### 1.2 版本目标

```
V2.3 (已实现)                    V3.0 (本文档)
──────────────────               ──────────────────────
用户手动选工作流        →        对话即触发(智能路由)
表单式编排              →        可视化 DAG 拖拽
执行失败即中断          →        失败重试 + 断点续跑 + 人工审批
无治理                  →        监控 + 版本 + 成本 + 审计
无模板市场              →        Agent/工作流模板市场
单租户                  →        多租户 SaaS
```

### 1.3 与 V2.x 的兼容性

| 兼容项 | 说明 |
|--------|------|
| API 兼容 | V2.x 所有 API 保持兼容，V3.0 新增 API |
| 数据兼容 | V2.x 数据库结构保留，V3.0 通过 ALTER TABLE 增量扩展 |
| 配置兼容 | V2.x 配置项保留，V3.0 新增配置项（默认关闭，按需开启） |
| 功能开关 | 每个新能力可通过 `agent.v3.*` 配置开关独立启用 |

## 2. 现状与差距分析

### 2.1 五层架构差距

```
┌─────────────────────────────────────────────────────────┐
│  层级       │  V2.3 现状              │  V3.0 目标       │
├─────────────────────────────────────────────────────────┤
│  触发层     │  手动 + cron 定时       │  +对话/API/事件  │
│  路由层     │  无 (用户手动选)        │  LLM 意图识别    │
│  编排层     │  表单式, 需自己创建     │  可视化 DAG+模板 │
│  执行层     │  Agent 执行(已可用)     │  +重试+续跑+审批 │
│  治理层     │  基本无                 │  监控+版本+成本  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 用户体验差距

| 场景 | V2.3 体验 | V3.0 目标体验 |
|------|----------|--------------|
| 写技术博客 | 跳到工作流页 → 选模板 → 输入 → 执行 | 对话说"帮我写博客" → 系统自动命中工作流 → 返回结果 |
| 工作流失败 | 看到"失败"二字, 从头重跑 | 看到失败步骤 → 点"重试" → 从断点续跑 |
| 配置工作流 | 填表单、写条件表达式 | 拖拽节点连线, 条件用自然语言描述 |
| 了解执行情况 | 无 | 仪表盘看耗时、token、成功率 |
| 想用新场景 | 自己从零搭 | 模板市场搜一个改改就用 |

## 4. F-30 智能路由层

### 4.1 目标

用户在对话中正常说话，系统自动判断该走普通对话、单 Agent 还是工作流，全程无感。

### 4.2 设计

```
用户消息
    ↓
┌─────────────────────────┐
│  IntentRouter (LLM)     │  ← 一次轻量 LLM 调用 (低成本模型)
│  输入: 用户消息 +       │
│        可用 Agent/      │
│        工作流列表       │
│  输出: {                │
│    "type": "workflow",  │
│    "target": "wf_xxx",  │
│    "reason": "..."      │
│  }                      │
└─────────────────────────┘
    ↓                       ↓                      ↓
走工作流                走单 Agent              普通对话
(静默执行,               (注入 Agent             (默认行为)
 结果作为回复)            配置覆盖)
```

### 4.3 路由策略

IntentRouter 用一次 LLM 调用判断意图，输入是：
- 用户消息
- 当前用户可用的 Agent 列表（名称 + 描述）
- 当前用户可用的工作流列表（名称 + 描述 + enabled）

输出 JSON：
```json
{
  "type": "workflow | agent | chat",
  "target": "wf_xxx | agent_xxx | null",
  "reason": "判断理由"
}
```

### 4.4 实现要点

- 路由结果缓存：相同前缀的对话只路由一次
- 置信度阈值：LLM 不确定时回退到普通对话
- 可关闭：`agent.v3.smart-routing.enabled=false` 时退化为 V2.3 行为
- 路由过程对用户可见（可选）：返回"已自动选择 XX 工作流"提示

### 4.5 数据模型

```sql
-- 路由记录表 (用于分析路由准确率)
CREATE TABLE IF NOT EXISTS routing_logs (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    session_id       VARCHAR(64),
    user_message     TEXT         NOT NULL,
    route_type       VARCHAR(16)  NOT NULL,    -- workflow / agent / chat
    target_id        VARCHAR(64),
    confidence       DECIMAL(3,2),
    reason           TEXT,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

## 5. F-31 触发层扩展

### 5.1 目标

支持除手动和 cron 外的多种触发方式。

### 5.2 触发方式

| 触发方式 | 场景 | 实现 |
|---------|------|------|
| 对话触发 | 用户在对话中触发工作流 (F-30) | IntentRouter 自动路由 |
| API 触发 | 外部系统调用 API 触发 | `POST /api/workflows/{id}/trigger` |
| Webhook | GitHub push、用户注册等事件 | `POST /api/webhooks/{token}` → 触发绑定的工作流 |
| 事件驱动 | 内部事件总线 | ApplicationEvent → 工作流订阅 |
| 定时触发 | cron 表达式 (V2.3 已有) | ScheduledTaskService |

### 5.3 Webhook 设计

```sql
CREATE TABLE IF NOT EXISTS webhook_endpoints (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    token            VARCHAR(128) NOT NULL UNIQUE,    -- 随机 token, 用于 URL
    secret           VARCHAR(128),                    -- 可选, 用于签名验证
    enabled          BOOLEAN      NOT NULL DEFAULT true,
    last_triggered   TIMESTAMP,
    trigger_count    INT          NOT NULL DEFAULT 0,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

URL 格式：`POST /api/webhooks/{token}`，请求体作为工作流输入。

## 6. F-32 可视化 DAG 编排

### 6.1 目标

用拖拽画布替代表单填空，让非技术用户也能搭工作流。

### 6.2 前端技术选型

- **Vue Flow**（基于 d3）：Vue 3 原生，轻量，支持自定义节点
- 备选：LogicFlow、AntV X6

### 6.3 节点类型

| 节点类型 | 图标 | 作用 |
|---------|------|------|
| Agent 节点 | 🤖 | 调用一个 Agent 处理输入 |
| 条件节点 | 🔀 | 根据条件分支（LLM 判断或表达式） |
| 并行节点 | ⫸⫷ | 并行执行多个分支 |
| 合并节点 | ⊕ | 合并多个分支输出 |
| 人工审批 | 👤 | 暂停等待人工确认 |
| 代码节点 | &lt;/&gt; | 执行简单脚本（沙箱） |
| HTTP 节点 | 🌐 | 调用外部 API |

### 6.4 条件判断升级

V2.3 的 `contains(text,"YES")` 死规则升级为两种模式：

- **自然语言模式**（默认）：`"上一步输出是否表示审校通过"` → LLM 判断
- **表达式模式**（高级）：支持 `${step.output} contains "xxx"` 等表达式

### 6.5 DAG 存储格式

```json
{
  "nodes": [
    {
      "id": "n1",
      "type": "agent",
      "position": {"x": 100, "y": 100},
      "data": {
        "agentId": "tpl_coder",
        "input": "针对 ${user_message} 列出技术要点"
      }
    },
    {
      "id": "n2",
      "type": "condition",
      "position": {"x": 300, "y": 100},
      "data": {
        "condition": "${n1.output} 是否包含代码示例",
        "mode": "llm"
      }
    }
  ],
  "edges": [
    {"source": "n1", "target": "n2"},
    {"source": "n2", "target": "n3", "label": "是"},
    {"source": "n2", "target": "n4", "label": "否"}
  ]
}
```

向后兼容 V2.3 的 `steps_json` 格式（自动转换）。

## 7. F-33 执行容错与人工介入

### 7.1 目标

工作流执行失败时不中断、可重试、可续跑、可人工介入。

### 7.2 失败重试

每个步骤可配置重试策略：

```json
{
  "retry": {
    "maxAttempts": 3,
    "backoff": "exponential",    // fixed / linear / exponential
    "initialDelayMs": 1000,
    "multiplier": 2
  }
}
```

### 7.3 断点续跑

执行记录持久化到 `workflow_executions` 表，记录每步状态：

```sql
CREATE TABLE IF NOT EXISTS workflow_executions (
    id               VARCHAR(64)  PRIMARY KEY,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    trigger_type     VARCHAR(16)  NOT NULL,        -- manual / api / webhook / event / schedule
    input            TEXT,
    status           VARCHAR(16)  NOT NULL,        -- running / paused / success / failed / cancelled
    current_step     VARCHAR(64),
    steps_state_json TEXT,                          -- 每步状态 + 输出
    started_at       TIMESTAMP    NOT NULL DEFAULT now(),
    completed_at     TIMESTAMP,
    error            TEXT,
    cost_tokens      INT,
    cost_amount      DECIMAL(10,4)
);
```

失败后调 `POST /api/workflows/executions/{id}/resume` 从断点续跑。

### 7.4 人工审批节点

工作流执行到审批节点时暂停，状态置为 `paused`，通知用户：
- 站内通知
- 可选：邮件/飞书 webhook

用户审批后调 `POST /api/workflows/executions/{id}/approve` 继续。

## 8. F-34 治理与可观测性

### 8.1 执行监控仪表盘

前端新增"监控"页面，展示：
- 工作流执行历史列表（含状态、耗时、token 消耗）
- 每步耗时 breakdown
- 成功率统计（按工作流、按时间）
- 失败原因分析

### 8.2 版本管理

工作流定义每次修改生成新版本：

```sql
CREATE TABLE IF NOT EXISTS workflow_versions (
    id               VARCHAR(64)  PRIMARY KEY,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    version          INT          NOT NULL,
    steps_json       TEXT         NOT NULL,
    change_note      VARCHAR(255),
    created_by       VARCHAR(64),
    created_at       TIMESTAMP    NOT NULL DEFAULT now(),
    UNIQUE(workflow_id, version)
);
```

可回滚到任意历史版本。

### 8.3 成本追踪

每次 Agent 调用和 LLM 调用记录 token 消耗：

```sql
CREATE TABLE IF NOT EXISTS llm_usage_logs (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    session_id       VARCHAR(64),
    workflow_execution_id VARCHAR(64),
    model            VARCHAR(128),
    input_tokens     INT,
    output_tokens    INT,
    cost_amount      DECIMAL(10,6),
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

### 8.4 审计日志扩展

V2.2 的 `audit_logs` 表扩展工作流相关操作类型：
- `workflow.create` / `workflow.update` / `workflow.delete`
- `workflow.execute` / `workflow.approve`
- `agent.create` / `agent.update` / `agent.delete`

## 9. F-35 Agent 与工作流模板市场

### 9.1 目标

用户不用从零创建，可以从模板市场挑选现成的 Agent 或工作流。

### 9.2 模板来源

| 来源 | 说明 |
|------|------|
| 系统预置 | 平台自带（V2.3 已有 Agent 模板，V3.0 扩展工作流模板） |
| 管理员发布 | 管理员创建并标记为模板，对所有用户可见 |
| 用户分享 | 用户将自己的 Agent/工作流分享到市场 |
| 官方市场 | 远程模板仓库（可选，V3.1+） |

### 9.3 模板市场前端

- 模板分类（翻译、写作、编程、分析、客服等）
- 搜索 + 排序（按使用次数、评分）
- 一键克隆到自己的工作区
- 评分和评论（V3.1+）

### 9.4 数据模型

```sql
-- 模板分享记录
CREATE TABLE IF NOT EXISTS template_shares (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    type             VARCHAR(16)  NOT NULL,        -- agent / workflow
    target_id        VARCHAR(64)  NOT NULL,
    title            VARCHAR(255),
    description      TEXT,
    category         VARCHAR(64),                  -- 分类
    tags             TEXT,                          -- 逗号分隔标签
    clone_count      INT          NOT NULL DEFAULT 0,
    rating_avg       DECIMAL(3,2) DEFAULT 0,
    rating_count     INT          DEFAULT 0,
    enabled          BOOLEAN      NOT NULL DEFAULT true,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

## 10. F-36 多租户 SaaS 化

### 10.1 目标

支持企业租户隔离，每个租户有自己的用户、Agent、工作流、知识库。

### 10.2 租户模型

```sql
CREATE TABLE IF NOT EXISTS tenants (
    id               VARCHAR(64)  PRIMARY KEY,
    name             VARCHAR(255) NOT NULL,
    plan             VARCHAR(32)  NOT NULL DEFAULT 'free',    -- free / pro / enterprise
    max_users        INT          NOT NULL DEFAULT 5,
    max_agents       INT          NOT NULL DEFAULT 10,
    max_workflows    INT          NOT NULL DEFAULT 20,
    max_kb_docs      INT          NOT NULL DEFAULT 100,
    max_tokens_month BIGINT       NOT NULL DEFAULT 1000000,
    status           VARCHAR(16)  NOT NULL DEFAULT 'active',
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);

-- users 表加 tenant_id
ALTER TABLE users ADD COLUMN tenant_id VARCHAR(64) REFERENCES tenants(id);
```

### 10.3 隔离策略

所有业务表（`agent_definitions`、`workflow_definitions`、`knowledge_bases`、`sessions` 等）通过 `user_id → tenant_id` 间接隔离。查询时 JOIN users 表过滤 tenant_id。

### 10.4 资源配额

每个租户有资源上限（用户数、Agent 数、工作流数、文档数、月 token 数），超额时拒绝创建。

### 11.1 目标

```java
public interface ToolPlugin {
    String getName();
    String getVersion();
    List<ToolDefinition> getTools();
    void initialize(PluginContext context);
}
```

### 11.3 插件市场

V3.1+ 提供插件市场，可在线安装/卸载插件。

## 12. F-38 本地模型支持

### 12.1 目标

集成 Ollama，支持私有化部署，降低 API 成本。

### 12.2 设计

- 新增 `OllamaChatModel` 实现，通过 Ollama HTTP API 调用本地模型
- 模型配置支持指定 provider：`dashscope` / `ollama`
- 前端模型选择器展示可用本地模型

### 12.3 配置

```yaml
agent:
  models:
    providers:
      ollama:
        base-url: http://localhost:11434
        models:
          - llama3:8b
          - qwen2:7b
```

## 13. F-39 成本与配额管理

### 13.1 目标

控制 LLM 调用成本，防止滥用。

### 13.2 配额维度

| 维度 | 限制项 |
|------|--------|
| 用户级 | 日 token 上限、月 token 上限 |
| 租户级 | 月 token 上限、并发工作流数 |
| 工作流级 | 单次执行 token 上限 |

### 13.3 配置

```yaml
agent:
  v3:
    quota:
      enabled: true
      user:
        daily-tokens: 100000
        monthly-tokens: 2000000
      workflow:
        max-tokens-per-execution: 50000
```

### 13.4 超额处理

- 接近上限时预警（80%、90%）
- 超额时拒绝调用，返回 `429 Too Many Requests`

## 附录: 技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 智能路由准确率 | 路由错误影响体验 | 置信度阈值 + 用户反馈修正 + 路由日志分析 |
| DAG 引擎复杂度 | 开发周期长 | 先支持核心节点类型, 逐步扩展 |
| 断点续跑一致性 | 状态不一致 | 执行状态原子写入, 幂等设计 |
| 多租户隔离泄漏 | 数据安全 | 所有查询强制带 tenant_id, 代码审查 + 自动化测试 |
| 本地模型性能 | 响应慢 | 异步执行 + 流式输出 |
| 插件安全 | 恶意插件 | 沙箱隔离 + 签名验证 + 权限控制 |
