## 1. 版本概述

### 1.1 V3.0 定位

V3.0 是 V2.x 系列的**生产化升级版本**。V2.3 已经具备了自定义 Agent、工作流编排、定时任务、流式图片生成的"骨架"能力，但存在五个关键缺口：

| 缺口 | 现状 | 生产级要求 |
|------|------|-----------|
| 用户需手动选择工作流 | 切页面、点按钮 | 对话即触发，用户无感 |
| 工作流模板需自己创建 | 空白页面从零搭 | 预置模板 + 模板市场 |
| 编排方式是表单填空 | 写 `contains(text,"YES")` 表达式 | 拖拽式可视化 DAG |
| 执行失败即中断 | 无重试、无续跑 | 失败重试 + 断点续跑 + 人工审批 |
| 无治理能力 | 无监控、无版本、无成本追踪 | 全链路可观测 |

V3.0 的目标就是补齐这五个缺口，让平台达到生产可用水平。

### 1.2 版本目标

```
V2.3 (已实现)                    V3.0 (本文档)
──────────────────               ──────────────────────
用户手动选工作流        →        对话即触发(智能路由)
表单式编排              →        可视化 DAG 拖拽
执行失败即中断          →        失败重试 + 断点续跑 + 人工审批
无治理                  →        监控 + 版本 + 成本 + 审计
无模板市场              →        Agent/工作流模板市场
单租户                  →        多租户 SaaS
```

### 1.3 与 V2.x 的兼容性

| 兼容项 | 说明 |
|--------|------|
| API 兼容 | V2.x 所有 API 保持兼容，V3.0 新增 API |
| 数据兼容 | V2.x 数据库结构保留，V3.0 通过 ALTER TABLE 增量扩展 |
| 配置兼容 | V2.x 配置项保留，V3.0 新增配置项（默认关闭，按需开启） |
| 功能开关 | 每个新能力可通过 `agent.v3.*` 配置开关独立启用 |

## 2. 现状与差距分析

### 2.1 五层架构差距

```
┌─────────────────────────────────────────────────────────┐
│  层级       │  V2.3 现状              │  V3.0 目标       │
├─────────────────────────────────────────────────────────┤
│  触发层     │  手动 + cron 定时       │  +对话/API/事件  │
│  路由层     │  无 (用户手动选)        │  LLM 意图识别    │
│  编排层     │  表单式, 需自己创建     │  可视化 DAG+模板 │
│  执行层     │  Agent 执行(已可用)     │  +重试+续跑+审批 │
│  治理层     │  基本无                 │  监控+版本+成本  │
└─────────────────────────────────────────────────────────┘
```

### 2.2 用户体验差距

| 场景 | V2.3 体验 | V3.0 目标体验 |
|------|----------|--------------|
| 写技术博客 | 跳到工作流页 → 选模板 → 输入 → 执行 | 对话说"帮我写博客" → 系统自动命中工作流 → 返回结果 |
| 工作流失败 | 看到"失败"二字, 从头重跑 | 看到失败步骤 → 点"重试" → 从断点续跑 |
| 配置工作流 | 填表单、写条件表达式 | 拖拽节点连线, 条件用自然语言描述 |
| 了解执行情况 | 无 | 仪表盘看耗时、token、成功率 |
| 想用新场景 | 自己从零搭 | 模板市场搜一个改改就用 |

## 4. F-30 智能路由层

### 4.1 目标

用户在对话中正常说话，系统自动判断该走普通对话、单 Agent 还是工作流，全程无感。

### 4.2 设计

```
用户消息
    ↓
┌─────────────────────────┐
│  IntentRouter (LLM)     │  ← 一次轻量 LLM 调用 (低成本模型)
│  输入: 用户消息 +       │
│        可用 Agent/      │
│        工作流列表       │
│  输出: {                │
│    "type": "workflow",  │
│    "target": "wf_xxx",  │
│    "reason": "..."      │
│  }                      │
└─────────────────────────┘
    ↓                       ↓                      ↓
走工作流                走单 Agent              普通对话
(静默执行,               (注入 Agent             (默认行为)
 结果作为回复)            配置覆盖)
```

### 4.3 路由策略

IntentRouter 用一次 LLM 调用判断意图，输入是：
- 用户消息
- 当前用户可用的 Agent 列表（名称 + 描述）
- 当前用户可用的工作流列表（名称 + 描述 + enabled）

输出 JSON：
```json
{
  "type": "workflow | agent | chat",
  "target": "wf_xxx | agent_xxx | null",
  "reason": "判断理由"
}
```

### 4.4 实现要点

- 路由结果缓存：相同前缀的对话只路由一次
- 置信度阈值：LLM 不确定时回退到普通对话
- 可关闭：`agent.v3.smart-routing.enabled=false` 时退化为 V2.3 行为
- 路由过程对用户可见（可选）：返回"已自动选择 XX 工作流"提示

### 4.5 数据模型

```sql
-- 路由记录表 (用于分析路由准确率)
CREATE TABLE IF NOT EXISTS routing_logs (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    session_id       VARCHAR(64),
    user_message     TEXT         NOT NULL,
    route_type       VARCHAR(16)  NOT NULL,    -- workflow / agent / chat
    target_id        VARCHAR(64),
    confidence       DECIMAL(3,2),
    reason           TEXT,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

## 5. F-31 触发层扩展

### 5.1 目标

支持除手动和 cron 外的多种触发方式。

### 5.2 触发方式

| 触发方式 | 场景 | 实现 |
|---------|------|------|
| 对话触发 | 用户在对话中触发工作流 (F-30) | IntentRouter 自动路由 |
| API 触发 | 外部系统调用 API 触发 | `POST /api/workflows/{id}/trigger` |
| Webhook | GitHub push、用户注册等事件 | `POST /api/webhooks/{token}` → 触发绑定的工作流 |
| 事件驱动 | 内部事件总线 | ApplicationEvent → 工作流订阅 |
| 定时触发 | cron 表达式 (V2.3 已有) | ScheduledTaskService |

### 5.3 Webhook 设计

```sql
CREATE TABLE IF NOT EXISTS webhook_endpoints (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    token            VARCHAR(128) NOT NULL UNIQUE,    -- 随机 token, 用于 URL
    secret           VARCHAR(128),                    -- 可选, 用于签名验证
    enabled          BOOLEAN      NOT NULL DEFAULT true,
    last_triggered   TIMESTAMP,
    trigger_count    INT          NOT NULL DEFAULT 0,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

URL 格式：`POST /api/webhooks/{token}`，请求体作为工作流输入。

## 6. F-32 可视化 DAG 编排

### 6.1 目标

用拖拽画布替代表单填空，让非技术用户也能搭工作流。

### 6.2 前端技术选型

- **Vue Flow**（基于 d3）：Vue 3 原生，轻量，支持自定义节点
- 备选：LogicFlow、AntV X6

### 6.3 节点类型

| 节点类型 | 图标 | 作用 |
|---------|------|------|
| Agent 节点 | 🤖 | 调用一个 Agent 处理输入 |
| 条件节点 | 🔀 | 根据条件分支（LLM 判断或表达式） |
| 并行节点 | ⫸⫷ | 并行执行多个分支 |
| 合并节点 | ⊕ | 合并多个分支输出 |
| 人工审批 | 👤 | 暂停等待人工确认 |
| 代码节点 | &lt;/&gt; | 执行简单脚本（沙箱） |
| HTTP 节点 | 🌐 | 调用外部 API |

### 6.4 条件判断升级

V2.3 的 `contains(text,"YES")` 死规则升级为两种模式：

- **自然语言模式**（默认）：`"上一步输出是否表示审校通过"` → LLM 判断
- **表达式模式**（高级）：支持 `${step.output} contains "xxx"` 等表达式

### 6.5 DAG 存储格式

```json
{
  "nodes": [
    {
      "id": "n1",
      "type": "agent",
      "position": {"x": 100, "y": 100},
      "data": {
        "agentId": "tpl_coder",
        "input": "针对 ${user_message} 列出技术要点"
      }
    },
    {
      "id": "n2",
      "type": "condition",
      "position": {"x": 300, "y": 100},
      "data": {
        "condition": "${n1.output} 是否包含代码示例",
        "mode": "llm"
      }
    }
  ],
  "edges": [
    {"source": "n1", "target": "n2"},
    {"source": "n2", "target": "n3", "label": "是"},
    {"source": "n2", "target": "n4", "label": "否"}
  ]
}
```

向后兼容 V2.3 的 `steps_json` 格式（自动转换）。

## 7. F-33 执行容错与人工介入

### 7.1 目标

工作流执行失败时不中断、可重试、可续跑、可人工介入。

### 7.2 失败重试

每个步骤可配置重试策略：

```json
{
  "retry": {
    "maxAttempts": 3,
    "backoff": "exponential",    // fixed / linear / exponential
    "initialDelayMs": 1000,
    "multiplier": 2
  }
}
```

### 7.3 断点续跑

执行记录持久化到 `workflow_executions` 表，记录每步状态：

```sql
CREATE TABLE IF NOT EXISTS workflow_executions (
    id               VARCHAR(64)  PRIMARY KEY,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    trigger_type     VARCHAR(16)  NOT NULL,        -- manual / api / webhook / event / schedule
    input            TEXT,
    status           VARCHAR(16)  NOT NULL,        -- running / paused / success / failed / cancelled
    current_step     VARCHAR(64),
    steps_state_json TEXT,                          -- 每步状态 + 输出
    started_at       TIMESTAMP    NOT NULL DEFAULT now(),
    completed_at     TIMESTAMP,
    error            TEXT,
    cost_tokens      INT,
    cost_amount      DECIMAL(10,4)
);
```

失败后调 `POST /api/workflows/executions/{id}/resume` 从断点续跑。

### 7.4 人工审批节点

工作流执行到审批节点时暂停，状态置为 `paused`，通知用户：
- 站内通知
- 可选：邮件/飞书 webhook

用户审批后调 `POST /api/workflows/executions/{id}/approve` 继续。

## 8. F-34 治理与可观测性

### 8.1 执行监控仪表盘

前端新增"监控"页面，展示：
- 工作流执行历史列表（含状态、耗时、token 消耗）
- 每步耗时 breakdown
- 成功率统计（按工作流、按时间）
- 失败原因分析

### 8.2 版本管理

工作流定义每次修改生成新版本：

```sql
CREATE TABLE IF NOT EXISTS workflow_versions (
    id               VARCHAR(64)  PRIMARY KEY,
    workflow_id      VARCHAR(64)  REFERENCES workflow_definitions(id) ON DELETE CASCADE,
    version          INT          NOT NULL,
    steps_json       TEXT         NOT NULL,
    change_note      VARCHAR(255),
    created_by       VARCHAR(64),
    created_at       TIMESTAMP    NOT NULL DEFAULT now(),
    UNIQUE(workflow_id, version)
);
```

可回滚到任意历史版本。

### 8.3 成本追踪

每次 Agent 调用和 LLM 调用记录 token 消耗：

```sql
CREATE TABLE IF NOT EXISTS llm_usage_logs (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    session_id       VARCHAR(64),
    workflow_execution_id VARCHAR(64),
    model            VARCHAR(128),
    input_tokens     INT,
    output_tokens    INT,
    cost_amount      DECIMAL(10,6),
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

### 8.4 审计日志扩展

V2.2 的 `audit_logs` 表扩展工作流相关操作类型：
- `workflow.create` / `workflow.update` / `workflow.delete`
- `workflow.execute` / `workflow.approve`
- `agent.create` / `agent.update` / `agent.delete`

## 9. F-35 Agent 与工作流模板市场

### 9.1 目标

用户不用从零创建，可以从模板市场挑选现成的 Agent 或工作流。

### 9.2 模板来源

| 来源 | 说明 |
|------|------|
| 系统预置 | 平台自带（V2.3 已有 Agent 模板，V3.0 扩展工作流模板） |
| 管理员发布 | 管理员创建并标记为模板，对所有用户可见 |
| 用户分享 | 用户将自己的 Agent/工作流分享到市场 |
| 官方市场 | 远程模板仓库（可选，V3.1+） |

### 9.3 模板市场前端

- 模板分类（翻译、写作、编程、分析、客服等）
- 搜索 + 排序（按使用次数、评分）
- 一键克隆到自己的工作区
- 评分和评论（V3.1+）

### 9.4 数据模型

```sql
-- 模板分享记录
CREATE TABLE IF NOT EXISTS template_shares (
    id               VARCHAR(64)  PRIMARY KEY,
    user_id          VARCHAR(64)  REFERENCES users(id) ON DELETE CASCADE,
    type             VARCHAR(16)  NOT NULL,        -- agent / workflow
    target_id        VARCHAR(64)  NOT NULL,
    title            VARCHAR(255),
    description      TEXT,
    category         VARCHAR(64),                  -- 分类
    tags             TEXT,                          -- 逗号分隔标签
    clone_count      INT          NOT NULL DEFAULT 0,
    rating_avg       DECIMAL(3,2) DEFAULT 0,
    rating_count     INT          DEFAULT 0,
    enabled          BOOLEAN      NOT NULL DEFAULT true,
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);
```

## 10. F-36 多租户 SaaS 化

### 10.1 目标

支持企业租户隔离，每个租户有自己的用户、Agent、工作流、知识库。

### 10.2 租户模型

```sql
CREATE TABLE IF NOT EXISTS tenants (
    id               VARCHAR(64)  PRIMARY KEY,
    name             VARCHAR(255) NOT NULL,
    plan             VARCHAR(32)  NOT NULL DEFAULT 'free',    -- free / pro / enterprise
    max_users        INT          NOT NULL DEFAULT 5,
    max_agents       INT          NOT NULL DEFAULT 10,
    max_workflows    INT          NOT NULL DEFAULT 20,
    max_kb_docs      INT          NOT NULL DEFAULT 100,
    max_tokens_month BIGINT       NOT NULL DEFAULT 1000000,
    status           VARCHAR(16)  NOT NULL DEFAULT 'active',
    created_at       TIMESTAMP    NOT NULL DEFAULT now()
);

-- users 表加 tenant_id
ALTER TABLE users ADD COLUMN tenant_id VARCHAR(64) REFERENCES tenants(id);
```

### 10.3 隔离策略

所有业务表（`agent_definitions`、`workflow_definitions`、`knowledge_bases`、`sessions` 等）通过 `user_id → tenant_id` 间接隔离。查询时 JOIN users 表过滤 tenant_id。

### 10.4 资源配额

每个租户有资源上限（用户数、Agent 数、工作流数、文档数、月 token 数），超额时拒绝创建。

## 11. F-37 插件系统

### 11.1 目标

允许第三方开发插件扩展工具能力，不用改主代码。

### 11.2 插件机制

- 插件以 JAR 形式放入 `plugins/` 目录
- 实现 `ToolPlugin` 接口，注册自定义工具

### 14.2 系统级可观测性 (P0)

F-34 的"治理与可观测性"是**业务层**（执行监控/版本/成本/审计），本节是**系统层**——JVM、HTTP、连接池、下游依赖的健康与性能。

**依赖与暴露端点**：

```xml
<!-- pom.xml 新增 -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
# application.yml 新增
management:
  endpoints:
    web:
      exposure:
        include: health,info,metrics,prometheus,env,loggers
  endpoint:
    health:
      show-details: when-authorized   # 生产环境不暴露细节给匿名
  metrics:
    tags:
      application: ${spring.application.name}
    distribution:
      percentiles-histogram:
        http.server.requests: true
  health:
    db:
      enabled: true
    # 自定义: LLM provider / Redis / Ollama 主动探测
```

**关键指标**：

| 类别 | 指标 | 用途 |
|------|------|------|
| JVM | jvm.memory.used/committed, jvm.threads.live | 内存/线程趋势，定位 OOM |
| HTTP | http_server_requests_seconds (QPS/RT/P99) | 接口性能与错误率 |
| DB | hikaricp.connections.active/idle/pending | 连接池饱和度 |
| LLM | 自定义 dcdr.llm.calls{provider,model} / dcdr.llm.latency / dcdr.llm.errors | 下游模型调用耗时与失败率 |
| 工作流 | dcdr.workflow.executions{status,workflow_id} / dcdr.workflow.step.duration | 执行成功率/慢步骤 |
| RAG | dcdr.rag.retrieval.duration / dcdr.rag.retrieval.score | 检索性能与质量 |

**健康检查**：扩展 `HealthIndicator` 实现 `LlmProviderHealthIndicator`（主动 ping 各 provider 的 `/models` 端点）、`RedisHealthIndicator`、`OllamaHealthIndicator`。`/actuator/health` 返回聚合状态，配合 K8s liveness/readiness 探针。

**Grafana 看板**：预置 4 个 Dashboard——JVM 概览、HTTP 接口、LLM 调用、工作流执行。

### 14.3 API 限流 (P0)

F-39 只限 LLM token 配额，**不限请求频率**。缺少限流会导致：恶意刷接口、LLM 上游限流传导、单用户拖垮实例。

**方案**：Bucket4j（基于令牌桶，支持 WebFlux 响应式）。

```xml
<dependency>
    <groupId>com.bucket4j</groupId>
    <artifactId>bucket4j-core</artifactId>
    <version>8.10.1</version>
</dependency>
```

**限流维度**：

| 维度 | 限流键 | 默认阈值 | 说明 |
|------|--------|---------|------|
| 用户级 | userId | 60 req/min | 防单用户刷量 |
| IP 级 | clientIp | 120 req/min | 未登录接口 + 防爬 |
| 接口级 | 路由+方法 | 分级 | 对话 30/min、生图 10/min、工作流触发 20/min、查询 120/min |
| LLM 并发 | provider+model | 信号量 | 避免触发 DashScope/OpenAI 上游 429 |

超限返回 `429 Too Many Requests` + `Retry-After` 头。实现为 WebFilter（非 @Component，避免双重注册），从 Reactor Context 取 userId，从 exchange 取 IP。

### 14.4 熔断与降级 (P0)

当前 `WebClientFactory` 已做连接池回收（maxIdleTime=20s/maxLifeTime=60s），但**无熔断**：上游 LLM 持续 5xx 时仍逐个请求超时，拖垮工作线程。

**方案**：Resilience4j（Spring Boot 3 原生集成，支持响应式）。

```xml
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-spring-boot3</artifactId>
    <version>2.2.0</version>
</dependency>
<dependency>
    <groupId>io.github.resilience4j</groupId>
    <artifactId>resilience4j-reactor</artifactId>
    <version>2.2.0</version>
</dependency>
```

**包裹范围**：

| 调用点 | 熔断配置 | 降级策略 |
|--------|---------|---------|
| LLM 对话 (`ChatModelProvider`) | 失败率>50% 开启, 等待 30s 半开 | 返回"模型繁忙，请稍后" |
| LLM 路由 (`IntentRouter`) | 同上 | 降级为普通对话 (type=chat) |
| 工具调用 (ToolRegistry) | 失败率>60% | 返回工具不可用，LLM 自行降级 |
| Webhook 触发 (F-31) | 失败率>40% | 拒绝触发并记录日志 |
| RAG embedding | 失败率>50% | 跳过检索，退化为无 RAG 对话 |

**与重试整合**：F-33 的步骤重试 + Resilience4j 的 CircuitBreaker 组合使用——CircuitBreaker 优先拦截（避免无意义重试），Retry 在半开/关闭态生效。

### 14.5 配置管理 (P0)

**问题**：当前 DDL 靠手工执行 `docs/sql/*.sql`（V3.0 schema 需手动跑），`ddl-auto=validate` 不会自动建表；`JWT_SECRET` 默认值硬编码在 yml 中（仅靠 `${JWT_SECRET:default}` 兜底，开发期易泄露到生产）。

**Flyway 迁移**：

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

```
src/main/resources/db/migration/
├── V2.0__base_schema.sql          # 从现有 v2.0_schema.sql 迁入
├── V2.1__rag_schema.sql
├── V2.2__auth_schema.sql
├── V2.3__agent_workflow_schema.sql
└── V3.0__routing_webhook_execution.sql
```

```yaml
spring:
  flyway:
    enabled: true
    locations: classpath:db/migration
    baseline-on-migrate: true       # 已有数据的库首次接入
    baseline-version: 2.3           # 现有库基线版本
    validate-on-migrate: true
```

切换后 `ddl-auto=none`（由 Flyway 全权管理 DDL），彻底避免 schema 漂移。

**敏感配置外置**：

| 配置项 | 现状 | 生产要求 |
|--------|------|---------|
| `JWT_SECRET` | yml 默认值兜底 | 环境变量强制注入，启动时校验 `>=32 字节`，缺失则启动失败 |
| `*.api-key` (DashScope/OpenAI 等) | yml 默认 `demo-key` | 环境变量或 Vault；启动时检测 `demo-key` 占位符并 WARN |
| `spring.datasource.password` | 空 | 环境变量 |
| `agent.v3.webhook.secret` | 无 | 生成时强随机 |

新增 `ProdConfigValidator` 在 `ApplicationRunner` 中校验生产环境关键配置缺失项，缺失即 fail-fast。

**Profile 分离**：明确 `application-dev.yml`（H2/调试日志）/ `application-pg.yml`（PostgreSQL）/ `application-prod.yml`（生产：Flyway + Actuator 收敛 + INFO 日志 + 优雅停机）。`application-prod.yml` 默认 `agent.auth.enabled=true`，禁止关闭。

### 14.6 优雅停机与日志轮转 (P0)

**优雅停机**：当前无配置，`SIGTERM` 立即断开 SSE 连接和进行中的工作流步骤。

```yaml
server:
  shutdown: graceful                # 等待进行中请求完成
spring:
  lifecycle:
    timeout-per-shutdown-phase: 30s # 最多等 30s
```

配合 `WorkflowEngine` 在停机时把 `running` 状态的执行标记为 `interrupted`，重启后可 `resume` 续跑（复用 F-33 断点续跑能力）。

**日志轮转**：当前仅 console 输出，生产环境日志无法持久化和审计。

```yaml
logging:
  level:
    com.dcdr.agent: info
  pattern:
    file: "%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n"
  file:
    name: ./logs/application.log
  logback:
    rollingpolicy:
      max-file-size: 100MB
      max-history: 30
      total-size-cap: 5GB
```

可选：接入 Loki/ELK 集中日志（V3.0-rc）。

### 14.8 数据一致性与可靠性 (P1)

| 问题 | 方案 |
|------|------|
| 工作流执行无超时，卡审批/死循环会永久占用线程 | 单步超时 `step.timeout-seconds`（默认 300s）+ 整体执行超时 `execution.max-duration`（默认 1h），超时标记 `timeout` 并可 resume |
| Webhook 重复触发导致工作流重复执行 | Webhook 请求带 `X-Webhook-Id` 头，落库唯一约束，重复直接返回上次结果（幂等） |
| 审批操作重复提交 | `approve` 接口幂等：已审批的 executionId 再次 approve 返回当前状态而非重复推进 |
| 重试耗尽后执行"消失" | 多次重试失败的 execution 进入 `dead_letter`（新增 `workflow_executions.status='dead_letter'`），管理后台人工介入 |
| 长事务锁表 | `WorkflowEngine` 持久化状态改为短事务（读-改-写分离），避免整个步骤执行期间持有事务 |
| 数据库连接泄漏 | 已有 `WebClientFactory` 连接池；JPA 侧 `open-in-view: false`（已配置），监控 HikariCP pending |

### 14.9 安全加固 (P1)

在 V2.2 认证/RBAC 基础上补充：

| 项 | 方案 |
|----|------|
| HTTPS 强制 | 反向代理层（Nginx/ALB）终止 TLS，或 `server.ssl` 配置；HSTS 头 |
| 安全响应头 | 新增 `SecurityHeadersWebFilter`：`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`CSP: default-src 'self'`、`Referrer-Policy: strict-origin` |
| 接口防刷 | 在 14.3 限流基础上，同一 userId/IP 在 1s 内 >50 次请求触发临时拉黑 5min，记录审计日志 |
| 审计日志保留 | `audit_logs` 表定时任务清理，保留 `>=180 天`；路由日志 `routing_logs` 默认保留 90 天后归档 |
| JWT 安全 | Refresh Token 旋转（每次刷新发新 refresh，旧失效）；access token 黑名单（登出/改密时） |
| 文件上传安全 | 校验 magic number 而非仅扩展名；限制单文件大小（已配 20MB）；存储路径不可执行 |
| 插件/模板代码审计 | F-37 插件加载前扫描危险 API（Runtime.exec/反射/文件写），人工审批白名单 |

### 14.10 性能与扩展性 (P1)

**Redis 缓存**（当前无缓存层，所有 Agent 配置/路由结果都查库）：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
```

| 缓存对象 | TTL | 失效策略 |
|---------|-----|---------|
| Agent 配置 (AgentDefinitionEntity) | 10min | 更新时主动 evict |
| 工作流定义 (WorkflowDefinitionEntity) | 10min | 同上 |

**水平扩展**：当前 SSE 会话状态在内存（`SessionManager`），多实例部署需会话亲和性（sticky session）或将会话状态下沉 Redis（V3.0-rc）。文件存储从本地磁盘迁对象存储（OSS/S3）以支持多实例共享（V3.0-rc）。

## 附录: 技术风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| 智能路由准确率 | 路由错误影响体验 | 置信度阈值 + 用户反馈修正 + 路由日志分析 |
| DAG 引擎复杂度 | 开发周期长 | 先支持核心节点类型, 逐步扩展 |
| 断点续跑一致性 | 状态不一致 | 执行状态原子写入, 幂等设计 |
| 多租户隔离泄漏 | 数据安全 | 所有查询强制带 tenant_id, 代码审查 + 自动化测试 |
| 本地模型性能 | 响应慢 | 异步执行 + 流式输出 |
| 插件安全 | 恶意插件 | 沙箱隔离 + 签名验证 + 权限控制 |
| LLM 上游持续故障 | 雪崩拖垮实例 | F-40.4 Resilience4j 熔断 + 降级为友好提示 |
| 流量突增打满实例 | 服务不可用 | F-40.3 Bucket4j 限流 + 429 限速保护 + 自动扩容 |
| 数据库 schema 漂移 | 上线后 DDL 不一致事故 | F-40.5 Flyway 版本化迁移 + CI 校验 |
| 配置密钥泄露 | 安全事故 | 环境变量/Vault 注入 + 启动校验占位符 + 代码审查禁硬编码 |
| 日志无限增长 | 磁盘打满 | F-40.6 日志轮转 + routing_logs/audit_logs 定时清理归档 |
| 单点故障 | 服务中断 | F-40.13 多实例 + DB 主从 + 定期灾备演练 |
