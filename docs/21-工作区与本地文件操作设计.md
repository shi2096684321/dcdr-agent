# 工作区与本地文件读写删设计（V3.3 F-49）

> 状态：设计稿 v3（未实现）
> 范围：**读 / 写 / 删** + 用户自选工作区 + **按轮次撤回**。不含 Computer Use / 屏幕识别 / 图像理解 / 命令执行。
> 目标形态：用户选定一个目录（工作区），模型在该目录内读写删；每一轮对话的改动都能整体撤回，对齐 WorkBuddy 的「撤回」体验。
> v1 → v2：范围从"只读"扩到"读+写+删"。
> v2 → v3：撤回从"单次操作"升级为「**单轮 / 整会话**」两级，新增变更日志与内容寻址快照（§6.4）。
> 部署前提：**本机运行**（`local-mode=true`），已确认。

---

## 1. 问题与目标

现状：模型能联网搜索、能查知识库、能执行沙箱代码，但**看不见用户电脑上的真实文件**。用户想把一个代码仓库丢给模型改，只能靠上传副本再手工拷回去。

要解决的是：**让模型在主目录上直接读写，范围由用户显式授予，每一次破坏性操作都可撤销。**

### 明确不做

| 不做 | 原因 |
|---|---|
| 屏幕截图 / 图像识别 / Computer Use | 成本高、可靠性差，文件操作不需要 |
| 执行命令（shell / 脚本） | 攻击面比写文件大一个量级，单独评估，不混在这个功能里 |
| 全量文件索引 | 索引大仓库是知识库的活，不是工作区的活（见 §9） |
| 直接真删 | 删除一律进回收区，永不 `Files.delete` 正本（见 §6.3） |

### 一条贯穿全文的原则

> **写入和删除必须是"可撤销的、可见的、可审计的"，三者缺一不可。**
> 可撤销靠回收区兜底；可见靠 diff 回显；可审计靠 `AuditService`。缺任何一条，这个功能都不该上线。

## 2. 前提：文件在哪台机器上

Spring Boot 进程只能看见**它自己所在的操作系统**的文件。这是地基，必须先定。

| 形态 | 用户选目录的含义 | 可行性 | 建议 |
|---|---|---|---|
| **A. 本机运行**（`java -jar` 跑在自己电脑） | 真实的本地路径 | 完全可行 | **推荐，一期只做这个** |
| **B. 容器运行**（docker compose） | 容器内路径 + 挂载卷 | 可行，需改 compose 加 `volumes` | 支持，配置标 `local-mode` |
| **C. 服务器 + 多用户浏览器访问** | **服务器**的盘，不是用户的 | 语义错位 | **禁用**。让人以为在改自己电脑，后果是**删错服务器的文件** |

> 判定：`agent.workspace.local-mode`（默认 `true`）。为 `false` 时功能整体不注册、API 返回 503。`cluster.enabled=true` 且 `local-mode=true` 时启动告警——`rootPath` 在另一台机器上不存在。

**C 形态不是"体验差"，是危险**：只读模式下最多是读错文件；加了写删之后，用户一句"把这个目录清一下"，删的是服务器。

### 2.1 为什么不用沙箱（常见质疑）

先看主流产品怎么做的，分界线不在"是否先进"，而在**进程以谁的身份运行**：

| 形态 | 代表 | 文件操作跑在哪 | 隔离手段 |
|---|---|---|---|
| **本机 agent** | Claude Code、CodeBuddy、Cursor、Cline | 用户自己的进程身份，直接操作真实文件系统 | 权限确认 + 工作区根目录限制 + 路径校验。**默认没有 OS 沙箱** |
| **云端 agent** | Devin、Codex Cloud、Copilot coding agent | 远端容器 / 临时 VM | 一任务一 VM，跑完即毁 |
| **企业托管** | Copilot Studio 等 | 托管运行时 | 低代码权限模型 + 站点/资源白名单 |

本机形态的头部产品默认都不套 OS 沙箱，原因很简单：**进程身份就是用户本人**。用户在终端里能 `rm` 的东西，agent 换个壳也能，沙箱不创造新的安全边界，只创造新的复杂度。

更关键的是，沙箱在本场景有三个**反作用**：

1. **看不见真实文件**：沙箱要么看不到宿主目录（这功能等于没有），要么把目录挂进去（等于放弃隔离）。挂载是有意义的，但那是"减少可见范围"，不是"隔离"。
2. **撤回机制直接失效**：blob 的 `move`/`rename` 必须在真实卷上做。在沙箱里改的是副本，用户 IDE 里看到的还是旧文件——撤回撤回了个副本。
3. **工具链割裂**：用户要 IDE 实时看到改动、要 `git status`、要构建。沙箱内改完还得同步出去，同步逻辑本身就是新的 bug 面。

**正确的问法不是"要不要沙箱"，而是"控制手段要和风险类型匹配"：**

| 风险类型 | 特征 | 该用的控制 |
|---|---|---|
| 执行模型写的任意代码（`code_interpreter`） | 不可枚举、可能反弹 shell、可能读任意文件 | **OS 级隔离**：禁网、无数据挂载、非 root、资源配额。所以本项目走 OpenSandbox，是对的 |
| 语义化的文件读写删（本设计） | 动作可枚举、可逐次审计、可逐次撤销 | **逻辑边界**：三档授权 + 路径六道校验 + blob 快照 + 三级撤回 + 审计 |

拿沙箱去管文件读写，属于用大炮打蚊子；拿路径校验去管代码执行，那是真会出事。两者的控制点不能互换。

**但也要承认：纵深防御上这里确实少了一层。** 补强成本低的三个点，实施时一并做掉：

1. **不以管理员身份运行**：启动时检测到 Windows 管理员 / `root` 直接 WARN。管理员身份跑的 agent 能改系统目录，此时应用层校验是唯一防线。
2. **路径解析必须单点**：所有文件访问只允许经过 `WorkspacePathResolver`，任何工具不得直接调 `Files.*`。这条靠 code review + 一条 ArchUnit 规则卡住——**它是本设计的"逻辑沙箱"**，破了这条，前面所有校验都白写。
3. **不想开放写权限的目录，就建 READ 档工作区**，而不是指望沙箱兜底。

> Java 17 起 `SecurityManager` 已被移除，JVM 层沙箱这条路走不通。真要 OS 隔离，那是部署层决策（专用账户 / 容器 / 独立 VM），不属于应用代码能解决的问题。
> 反过来，**如果哪天要做云端多租户**，这套设计必须整体重做——不是加个沙箱就够，撤回机制在副本上本来就没有意义。

### 2.2 参考实现对照（WorkBuddy Desktop / CodeBuddy CLI）

翻了一遍本机安装的 `app.asar.unpacked/cli/dist/codebuddy-lite-wb.mjs`，把它真实的做法记下来，作为本设计的对照系：

| 能力 | 参考实现的做法 | 本设计 |
|---|---|---|
| **工作区** | `permissions.additionalDirectories` + 当前 work dir；有 `listWorkspaceDirs` / `addWorkspaceDir` 接口供 UI 加目录，**幂等** | 三档 `access_level` + 会话绑定。比它多一个"读/写/删分级"，它只有"放行/不放行" |
| **路径边界** | `isContainedPath` = 相等 或 `isPathInside`；配合 `realPathOrUndefined` 解析真实路径 | 同思路（§6.1 第 3 步） |
| **软链接** | `assertSymlinkChainContained`：**逐跳 `lstat`/`readlink`，上限 32 跳，已访问集合防环**，任一跳逃出根即拒绝 | 采纳。我原来只做一次 `toRealPath`，链式链接（A→B→C 逃出）可能漏 |
| **沙箱** | 存在，但主要包 **子进程命令**：`wrapCommand` + `network/filesystem{denyRead, allowWrite, denyWrite}`；桌面端强制 `allowUnsandboxedCommands=false` | 不做（§2.1）。但沙箱配置里的 `denyRead/allowWrite/denyWrite` 三件套正好可以借来当**配置项结构** |
| **权限模式** | `default / acceptEdits / plan / bypassPermissions / dontAsk / auto / ignore` | 简化为三档工作区授权。模式与授权是两个维度，本项目先不引入模式 |
| **提权防护** | 扫描输入文本里是否出现 `bypassPermissions` / `--dangerously-skip-permissions` / `permissions.allow` 等字样——**有人会直接在 prompt 里试图让 agent 自我提权** | 采纳（见 §11 风险表），一期做关键字扫描 + 审计 |
| **写入前新鲜度** | `readFileStateService` + `isFileFresh(path)`：读时登记，写前校验文件是否被外部改过 | 同思路（§6.2 ②），只是换成 `(lastModified, size)` 比对 |
| **编码 / 换行** | `readFileWithEncodingDetection` + `restoreLineEndings` + `writeFileContent(path, content, lineEnding, encodingInfo)`，区分 `LF/CRLF/MIXED`、看 `encodingInfo` 决定能否 patch | 完全一致，连"检测后按原样写回"这一步都一样 |
| **原子写** | `atomicWriteHostFile`：同目录 `.tmp`（`flag:"wx"`）→ `rename`；Windows 上 `EEXIST/EPERM` 退化为 `rm` + `rename`，`finally` 清理 tmp | 一致，采纳这个 Windows 退化分支 |
| **撤回存储** | `<home>/file-history/<sessionId>/<pathHash>~<version>`；`file-history-snapshot` 作为**会话历史的一种 item**，内含 `fileSnapshots{path → {backupFileName, version, backupTime, existedAtTrack}}` | 我用 `<app-data>/workspace-trash` + JSONL journal。**两者对 `existed` 语义完全一致** |
| **撤回点** | 从消息列表推导（`getRewindableCheckpoints`，只认真实用户消息），配合 `revertToCheckpoint` + lane pointer 回退 + 消息 tombstone **原子提交** | 同思路（§6.4.2），turnId 即用户消息 id |
| **防伪造** | 恢复前用 `formatBackupName(pathHash, version)` 重算校验备份名，并强制 `isSinglePathSegment` | 我用内容寻址 sha，**恢复时重算 sha 与文件名比对**即可，天然防伪造 |

结论：本设计的方向和参考实现是一致的，主要差异在**存储位置**（它放 home，我原来放工作区内）和**授权粒度**（它二值放行，我分三档）。前者我要改——放工作区内会污染用户仓库，`git status` 里多出一坨东西，IDE 也会去索引它。后者是有意的增强。

## 3. 核心概念

**工作区（Workspace）** = 一个被用户显式授权给模型的目录 + 一组访问策略。

四条不变量：

1. **工作区是归属对象**，属于某个 `userId`，走现有 `OwnershipRegistry` 框架。
2. **工作区不是沙箱**，是"用户主动开的门"。安全边界在路径解析层实施，不依赖文件系统权限（为什么不套 OS 沙箱见 §2.1）。
3. **会话绑定工作区**，不是全局绑定。两个会话可以分别绑定不同目录。
4. **读、写、删是三档独立授权**。给了读不等于给了删——这是本次设计最重要的一条权限约束。

---

## 4. 授权模型

工作区带一个三档 `access_level`，直接映射到工具可见性：

| 档位 | 允许 | 工具可见 | 前端展示 |
|---|---|---|---|
| `READ` | 列目录、读文件、搜索 | `workspace_list` `workspace_read` `workspace_search` | 灰色「只读」徽标 |
| `WRITE` | 上述 + 新建/修改 | 加 `workspace_write` `workspace_edit` | 蓝色「可写」徽标 |
| `FULL` | 上述 + 删除 | 加 `workspace_delete` | 橙色「可写可删」徽标 + 确认提示 |

工具层做硬门禁：不在档位内的工具**不注册进本会话的工具列表**（不是执行时再拒，那样模型会反复尝试、浪费轮次）。同时执行时再校验一次，防 ContextHolder 被污染。

`FULL` 的前端徽标要显眼且不可忽略——用户随时能看出"这个会话的模型有删文件的权力"。

## 5. 领域模型

### 5.1 表结构

```sql
CREATE TABLE workspaces (
    id              VARCHAR(64)   PRIMARY KEY,
    user_id         VARCHAR(64)   NOT NULL,
    name            VARCHAR(128)  NOT NULL,
    root_path       VARCHAR(1024) NOT NULL,   -- 归一化后的真实绝对路径
    access_level    VARCHAR(16)   NOT NULL DEFAULT 'READ',  -- READ / WRITE / FULL
    include_globs   TEXT,                     -- 逗号分隔，空=全部
    exclude_globs   TEXT,
    max_depth       INT           NOT NULL DEFAULT 6,
    created_at      TIMESTAMP     NOT NULL,
    updated_at      TIMESTAMP     NOT NULL
);
CREATE INDEX idx_workspace_user ON workspaces(user_id);

ALTER TABLE sessions ADD COLUMN workspace_id VARCHAR(64);
```

`root_path` 存 `toRealPath()` 解析后的值，创建时算一次，后续只做比对。

**不建索引表、不建版本表**。撤回需要的两样东西都放在磁盘上（§6.4）：内容寻址的 blob 快照 + append-only 的 JSONL 变更日志。不依赖数据库——数据库挂了用户仍能手工把文件捞回来，这个冗余是故意的。

### 5.2 类结构

```
com.dcdr.agent.workspace
├── WorkspaceEntity / WorkspaceRepository
├── WorkspaceService            # CRUD + 归属校验 + 档位校验
├── WorkspacePathResolver       # 安全核心：相对路径 → 绝对路径，六道校验
├── WorkspaceContextHolder      # ThreadLocal，当前请求绑定的 workspace
├── WorkspaceTrashService       # 回收区：内容寻址 blob 的存取、恢复、清理
├── WorkspaceJournal            # 变更日志（append-only JSONL），按 turnId 归组
├── SessionRewindService        # 撤回：L1 单操作 / L2 单轮 / L3 整会话
└── WorkspaceController         # /api/workspaces/**

com.dcdr.agent.tool.workspace
├── WorkspaceListTool           # workspace_list
├── WorkspaceReadTool           # workspace_read
├── WorkspaceSearchTool         # workspace_search
├── WorkspaceWriteTool          # workspace_write
├── WorkspaceEditTool           # workspace_edit
└── WorkspaceDeleteTool         # workspace_delete
```

`WorkspaceContextHolder` 照抄 `SandboxContextHolder` 的形态，由编排层在进入工具循环前 `set`，`finally` 里 `clear`。

## 6. 功能设计

### 6.0 六个工具一览

| 工具 | 能力 | 最低档位 | 参数 |
|---|---|---|---|
| `workspace_list` | 列目录 | READ | `path` `depth` `limit` |
| `workspace_read` | 按行读文本 | READ | `path` `offset` `limit` |
| `workspace_search` | 按内容/文件名搜 | READ | `pattern` `path` `glob` `max_results` |
| `workspace_write` | 新建或整体覆盖 | WRITE | `path` `content` `overwrite` |
| `workspace_edit` | 精确替换片段 | WRITE | `path` `old_string` `new_string` `replace_all` |
| `workspace_delete` | 移入回收区 | FULL | `path` `recursive` |

**为什么 write 和 edit 分开**：让模型整文件覆盖，是丢代码的主要来源——它记不住 800 行文件的全貌，重写时静默丢掉中间几段。`edit` 用唯一字符串定位替换，改动范围可验证。`write` 只用于新建文件和明确要整体重写的场景，且 `overwrite=true` 必须显式声明。

六个工具全部 `supportsStreaming()=true`，全部**不进** `PLATFORM_TOOLS`（业务能力，必须能被 Agent 白名单控制），统一 `workspace_` 前缀——名字本身就是边界声明。

### 6.1 公共安全层：六道校验

`WorkspacePathResolver.resolve(workspace, relativePath, intent)`，`intent ∈ {READ, WRITE, DELETE}` 决定用哪套 deny 规则：

```
1. 入参清洗
   - 空 → 读操作允许（=根目录），写删一律拒绝
   - 含 "\0" → 拒绝
   - 绝对路径 / 盘符 (C:\) / UNC (\\server) → 拒绝，只接受相对路径
   - NUL / CON / PRN / AUX / COM1-9 / LPT1-9 → 拒绝

2. 拼接归一化
   target = root.resolve(rel).normalize()
   !target.startsWith(root) → 拒绝（拦 ../ 穿越）

3. 真实路径 + 符号链接链校验（关键）
   real = target 存在 ? target.toRealPath() : 父目录.toRealPath().resolve(文件名)
   !real.startsWith(rootReal) → 拒绝（拦 mklink /J、软链接逃逸）
   逐跳遍历：lstat → readlink → resolve，上限 32 跳 + 已访问集合防环
   任一跳的目标逃出 root → 立即拒绝

4. 敏感路径 deny（大小写不敏感）
   READ  拒绝：.ssh  .aws  .gnupg  .env  id_rsa*  *.pem  *.p12  *.p8
                *.keystore  .npmrc  .pypirc  *.kdbx  credentials*
   WRITE 追加拒绝：.git/objects  .git/refs  .git/HEAD  .git/config
                   回收区目录/**（trash-location=workspace 时才用得上）
   DELETE 追加拒绝：.git/**  回收区目录/**

5. 文件校验（按 intent）
   READ  : size > max-file-size(2MB) → 拒绝；前 8KB 含 \0 → 二进制，拒绝
   WRITE : content 长度 > max-write-bytes(1MB) → 拒绝
   DELETE: 目录必须 recursive=true；文件数 > max-delete-files(100) → 拒绝

6. 策略校验
   - include_globs 非空时必须命中
   - exclude_globs 命中即拒绝
   - access_level 是否覆盖 intent
```

**第 3 步不能省**：`normalize()` 只处理字符串，不解析链接。Windows 上 `mklink /J` 指向 `C:\Users` 的目录联接，第 2 步完全通过，只有真实路径能拦下。

**为什么要逐跳而不是只 `toRealPath` 一次**：`toRealPath` 解的是最终落点，链式链接（A→B→C，中间跳出去再跳回来）在只有一次解析时容易漏判。参考实现用的是逐跳遍历 + 32 跳上限 + 环检测，本项目照抄——这类代码写一次就够，没必要自己发明。

**WRITE 对 `.git/` 的额外保护**：改 `.git/objects` 或 `refs` 会直接把仓库搞坏，且 `git` 自己不会提示。`.gitignore` / `.gitattributes` 这类工作区文件不拦。

### 6.2 写入设计（这是最容易做错的一段）

一次 `workspace_write` / `workspace_edit` 的完整流程，顺序不可换：

```
① 路径解析（intent=WRITE）
② 存在性检查 + 并发校验         ← 最关键的一步，见下
③ 编码与换行检测（决定写入字节）
④ 新内容写到同目录 .tmp
⑤ 原文件 move 进 blob → tmp ATOMIC_MOVE 到目标位置   ← 全程不复制大文件
⑥ 审计：before/after 的 sha256、字节数、diff 统计
⑦ 返回 diff 摘要（前 20 行变更 + 统计），不回灌全文
```

**② 并发校验解决一个真实事故**

场景：用户在 IDE 里改了 `UserService.java`，模型的上下文里还是旧版本，一句"帮我加个日志"就整文件覆盖——用户刚写的代码没了，而且没有任何提示。

做法：读文件时记录 `(lastModifiedTime, size)`，写入前重新 stat 比对，不一致就拒绝：

```
文件在读取后被外部修改过（可能你在编辑器里改了它）。
请重新读取 src/.../UserService.java 再修改。
```

`workspace_edit` 天然免疫这个问题——`old_string` 匹配不上就失败，不会误覆盖。这是 edit 优于 write 的第二个理由。

**④ 编码与换行必须保持原样**

| 场景 | 错误做法 | 后果 |
|---|---|---|
| GBK 文件按 UTF-8 写回 | `Files.writeString(p, s, UTF_8)` | 整个文件中文变乱码 |
| CRLF 文件按 LF 写回 | 统一写 `\n` | git 显示全文件 1000 行变更，review 没法看 |

规则：
- 编码：读时用 UTF-8 严格解码，失败降级 GBK，再失败 GB18030；**写回用检测到的同一编码**；新文件默认 UTF-8；原文件有 BOM 则保留 BOM
- 换行：`workspace_edit` 必须沿用原文件换行符（检测首个 `\r\n`）；`workspace_write` 新文件默认 `\n`，覆盖时沿用原文件

**⑤ 原子写与快照顺序**

绝不能 `Files.write(path, bytes)` 直接覆盖——写到一半进程挂了，文件就是半截，且原内容已丢。

顺序也不能反：**先把原文件 move 进 blob，再把 tmp move 到目标位置**。如果先覆盖再备份，中间那一刻原内容已经没了。

Windows 上 `ATOMIC_MOVE` 会遇到 `EEXIST` / `EPERM`（目标被 IDE、杀软、OneDrive 占着）。参考实现的处理是：退化为 `rm` + `rename`，`finally` 里清理 tmp。这个分支必须写，否则 Windows 用户会间歇性写失败。

```java
Path tmp = path.resolveSibling(path.getFileName() + ".tmp");
Files.write(tmp, bytes);
Files.move(tmp, path, StandardCopyOption.ATOMIC_MOVE, StandardCopyOption.REPLACE_EXISTING);
```

同卷 `ATOMIC_MOVE` 在 Windows 上可用（NTFS）。跨卷会抛 `AtomicMoveNotSupportedException`，此时退化为「原文件已在回收区有快照 → copy + delete」，因为快照保证了可恢复。

**⑦ 返回格式**——写操作的结果要让模型和用户都能一眼确认改了什么：

```
[workspace_edit] src/main/java/.../UserService.java  已修改
  -  private void validate(User u) {
  +  private void validate(User u) {
  +      log.debug("validate user {}", u.getId());
  共 1 处替换，+1 / -0 行

提示：修改前的内容已快照，可在界面点「撤销」回滚。
```

### 6.3 删除设计

**唯一规则：永不真删。**

`workspace_delete` 的实现分三步：**先算 sha → 把文件 move 进 blob → 记日志**：

```
① 读文件算 sha256（只需一遍读）
② 若 blobs/<sha> 不存在 → Files.move(path, blobs/<sha>)（同卷 rename，O(1)）
   若已存在（内容重复）→ 直接删原文件
③ journal 追加 {"type":"DELETE","path":"...","beforeSha":"9f2c...","existed":true}
```

对用户而言文件"消失"了，但内容在 blob 里躺着，任何一级撤回都能拿回来。

**为什么不用"移动整个目录到删前快照目录"**：一轮里可能删 50 个文件、又改了 20 个，按操作建目录会让回收区变成一堆碎目录，撤回单轮时要跨几十个目录拼状态。内容寻址只有一份内容、一条日志，撤回就是"照着日志把 blob 贴回去"。

**顺带解决大文件成本**：`Files.move` 是同卷 rename，不搬数据。所以哪怕删一个 10G 的文件，也只是读一遍算哈希 + 一次 rename。

**五条硬限制**

| 限制 | 值 | 理由 |
|---|---|---|
| 删工作区根 | 禁止 | 一句"清理一下"就没了 |
| 删目录必须 `recursive=true` | 强制 | 防模型顺手删掉非空目录 |
| 单次文件数上限 | 100 | 超出说明意图不明确，应让用户手动处理 |
| `deny` 路径不可删 | 见 §6.1 | `.git/` 删了仓库就废了 |
| 回收区不可删/不可写 | 强制 | 否则撤销能力本身会被抹掉 |

回收区放哪，是个真实取舍：

| 位置 | 优点 | 缺点 |
|---|---|---|
| **应用数据目录**（`<app-data>/workspace-trash/<wsId>/`）**← 默认** | 不污染用户仓库，`git status` 干净，IDE 不索引 | 跨卷时 `move` 退化为复制，大文件有成本 |
| 工作区内（`<root>/.workspace-trash/`） | 同卷 `move` 是 O(1)，用户肉眼可见、能手工恢复 | 仓库里多一坨东西，要改 `.gitignore`，容易误提交 |

默认选应用数据目录：**污染用户的仓库是更贵的代价**。同卷时 `Files.move` 仍然走 rename，只有跨卷才退化成复制，而这个场景一次操作最多 1MB（`max-write-bytes`），代价可接受。配置项 `trash-location: app-data | workspace` 留给想自己掌控的用户。

无论放哪，目录扫描都永远排除回收区，不让模型看见自己的垃圾桶。

保留期 `trash-retention-days`（默认 30 天），由现有 `ScheduledTaskService` 挂一个每日清理任务。清理时**真删**，并在审计里记录——这是唯一真正不可逆的动作，需要留痕。

### 6.4 三级撤回

单次操作的撤销（从 trash 里捞回一个文件）不够用——用户真正想要的是「**这一轮对话白做了，全部退回去**」。所以要三级：

| 级别 | 入口 | 范围 |
|---|---|---|
| **L1 单操作** | 工具结果旁的「撤销」 | 一次 write / edit / delete |
| **L2 单轮** | 用户消息 hover 的「撤回此轮」 | 该轮所有文件改动 + 该轮之后的消息 + 该轮产物 |
| **L3 整会话** | 会话菜单「清空本会话改动」 | 会话内所有轮的改动，保留会话本身 |

三级共用同一套底座：**变更日志 + 内容寻址快照**。

#### 6.4.1 底座：blob + journal

```
<app-data>/workspace-trash/<workspaceId>/
├── blobs/
│   └── 3f/9a/3f9a1c...e7          # sha256 分片存放，同名即同内容，天然去重
└── journal/
    └── sess_8f2a.jsonl            # 追加写，一行一条
```

**为什么是内容寻址，而不是"每次操作一个目录"**：一轮里同一个文件被改 5 次，只需要保留它最初始的那份内容。存 5 份目录副本会让回收区膨胀 5 倍，撤回时还得逆序回放才能凑出正确结果。

journal 记录（先写 `begin`，再动文件）：

```json
{"v":1,"op":"op_7f3","turnId":"msg_128","seq":12,"ts":"2026-10-26T17:49:12+08:00",
 "type":"MODIFY","path":"src/A.java","existed":true,
 "beforeSha":"3f9a...","afterSha":"8c2b...","bytes":4821,"status":"begin"}
```

`turnId` = 触发这一轮的用户消息 id。编排层在进入工具循环前放进 `WorkspaceContextHolder`，工具落日志时直接取——**模型既不需要、也无法指定它**，这是撤回范围不可被模型操纵的前提。

**为什么先写 begin 再动文件**：如果先改文件、后落日志，进程在两者之间崩溃，这个文件就永远回不去了。先落 begin，最坏情况是日志里存在 begin 而没有 end，重启后按 blob 回滚即可。

#### 6.4.2 L2 单轮撤回（本次核心）

`POST /api/sessions/{id}/rewind`，body `{messageId, scope}`，`scope ∈ {FILES, MESSAGES, ALL}`。

执行顺序（不可换）：

```
1. 校验 messageId 属于该会话
2. 读 journal，筛出该 turnId 及其之后的所有轮次
3. 每个 path 只取**最早**的 before 状态（一轮里改 5 次 → 回滚到最初始那份）
4. 冲突检测（见 6.4.3），冲突项跳过
5. 逆序恢复：MODIFY/CREATE 把 blob 贴回原路径；DELETE 从 blob 取回
6. 该轮新建的文件 → 移入 `<app-data>/workspace-trash/<wsId>/undo-<ts>/`，**不是真删**
7. scope 含 MESSAGES：删除该 messageId 及其之后的所有消息
8. 清理该轮自动抽取的长期记忆（按 origin 关联；用户手写的记忆不动）
9. journal 里这些轮次标记 `reverted`，重复调用直接返回「已撤回」
10. 审计 + 返回报告
```

返回报告必须具体，不能只说成功：

```json
{
  "reverted": ["src/A.java", "src/B.java"],
  "skipped": [{ "path": "src/C.java", "reason": "文件在撤回前被外部修改过" }],
  "messagesDeleted": 6,
  "artifactsMoved": 2
}
```

#### 6.4.3 冲突检测（必须有）

用户可能在一轮对话之后、点撤回之前，自己在 IDE 里改了文件。无脑回滚 = 覆盖他的手改，比不撤回更糟。

规则：回滚前比对当前文件 sha 与 journal 里的 `afterSha`。

| 情况 | 处理 |
|---|---|
| 一致 | 正常回滚 |
| 不一致 | **跳过该文件**并报告原因；不覆盖、不静默 |
| 文件已不存在（用户自己删的） | 正常回滚（恢复成撤回前状态） |
| 路径被新文件占用 | 跳过并报告 |

不提供"强制覆盖"选项——那等于把最危险的动作变成一次点击。

#### 6.4.4 L1 / L3

- **L1**：只回滚一条 journal 记录，前端挂在每条工具结果右侧
- **L3**：等价于对最早一轮执行 L2，`scope=ALL`。清空改动但不删会话

#### 6.4.5 blob 的生命周期

- 保留 `trash-retention-days`（默认 30 天）
- 清理任务扫 journal 收集仍被引用的 sha，其余删除（简易引用计数）；**被后续轮次引用的 blob 不能删**，否则 L2 撤回会拿到残缺快照
- **不做任何 git 操作**。工作区可能是 git 仓库，但撤回绝不执行 `git checkout` / `reset`——那是用户的仓库，不是我们的

### 6.5 是否需要人工二次确认

| 动作 | v1 方案 | 理由 |
|---|---|---|
| `write` / `edit` | 直接执行 | 有快照 + 有 diff 回显 + 可一键撤销，边际风险低 |
| `delete` | 直接执行（进回收区） | 本质是"移动"，不是销毁；撤销成本低于确认成本 |
| 清理回收区（真删） | 系统定时任务 | 不经模型，不需要确认 |

**不做两阶段审批**（工具阻塞等用户点同意）。理由：两阶段会让工具循环卡住，超时/断连的边界情况一大堆，实现成本高；而在"永不真删"的前提下，它防的风险已经被快照和撤销覆盖了大半。

如果后续要上，接口位留在这里：`WorkspaceProperties.approvalMode = AUTO | CONFIRM_WRITE | CONFIRM_DELETE`，实现时在工具执行前查一次 `WorkspaceApprovalService`。**但 v1 不要做**，先看真实使用中 model 到底会不会乱删。

### 6.6 上下文与 token 治理

| 位置 | 策略 |
|---|---|
| system prompt | 只注入工作区摘要：名称 + 相对结构（深度 1，最多 30 行）+ 档位。**绝不注入全量文件树** |
| 单次读取 | 默认 200 行，单次回灌上限 `max-read-chars`（8000） |
| 超长结果 | 走现有 `ToolResultCompressor` → `ToolResultSpillStore` 落盘 → `tool_result_read` 分页。**不自己截断** |
| 写操作回显 | 只回 diff 摘要（前 20 行），不回全文；全文在磁盘上，模型需要可用 `workspace_read` 再读 |
| 搜索 | `max_results` 默认 30，超出提示"命中 M 处，请缩小范围" |
| 目录遍历 | `max-entries` 5000 早停；默认忽略 `node_modules .git target dist build .idea __pycache__ .venv`，以及回收区目录（若配置在工作区内） |

摘要注入示例：

```
当前工作区: java-agent  (/Users/me/work/java-agent, 可写可删, 共 1284 个文件)
顶层结构:
  docs/  src/  frontend/  pom.xml  README.md  docker-compose.yml
```

## 7. API 设计

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/workspaces` | `workspace:read` | 列表（自己 / admin 全部） |
| POST | `/api/workspaces` | `workspace:write` | 创建 `{name, rootPath, accessLevel}` |
| PATCH | `/api/workspaces/{id}` | `workspace:write` | 改名 / **升降档位** |
| DELETE | `/api/workspaces/{id}` | `workspace:write` | 只删记录，**不动磁盘** |
| GET | `/api/workspaces/{id}/tree` | `workspace:read` | 前端树形浏览 |
| POST | `/api/workspaces/{id}/journal/{op}/undo` | `workspace:write` | L1 单操作撤销 |
| GET | `/api/sessions/{id}/checkpoints` | `session:read` | 可撤回点列表（每轮改动统计 + 是否可撤回） |
| POST | `/api/sessions/{id}/rewind` | `session:write` | L2/L3 撤回，`{messageId, scope}` |
| GET | `/api/workspaces/browse` | `workspace:browse` | 目录选择器，默认关闭 |
| PUT | `/api/sessions/{id}/workspace` | `workspace:write` | 绑定 |
| DELETE | `/api/sessions/{id}/workspace` | `workspace:write` | 解绑 |

新增权限码：`workspace:read` / `workspace:write` / `workspace:browse`。

- `workspace:read` / `workspace:write` 给 `ROLE_USER` 与 `ROLE_ADMIN`，`ROLE_GUEST` 无
- `workspace:browse` **仅 admin**，且受 `agent.workspace.browse-enabled`（默认 false）控制——它能枚举服务器任意目录名，是信息泄露面

**三处必须明说的文案**

1. `DELETE /api/workspaces/{id}` 只解绑，不删文件——UI 上写清楚，否则用户不敢点
2. 升档到 `FULL` 时弹一次确认："该会话的模型将可以删除此目录下的文件（会先移入回收区，可撤销）"
3. 降档时**立即生效**，并且要清掉当前会话里已注册的写/删工具（下次对话重建工具列表）

## 11. 风险与坑

| 风险 | 说明 | 对策 |
|---|---|---|
| **软链接 / junction 逃逸** | `normalize()` 不管链接，Windows `mklink /J` 能绕过字符串校验 | §6.1 第 3 步 `toRealPath` 比对 |
| **并发覆盖丢代码** | 用户改了文件，模型基于旧内容整文件重写 | 写入前比对 `(lastModified, size)`；用 `edit` 而非 `write` |
| **编码破坏** | GBK 文件按 UTF-8 写回，全文乱码 | 写回沿用检测到的编码 + 保留 BOM |
| **换行符破坏** | CRLF 被写成 LF，git 显示全文变更 | `edit` 沿用原换行符 |
| **半截文件** | 写一半进程挂了 | 临时文件 + `ATOMIC_MOVE` |
| **删错目录** | 一句"清理一下"删掉整个 `src` | 永不真删 + 根目录禁删 + 单次 100 文件上限 |
| **`.git` 被写坏** | 改 `objects`/`refs` 导致仓库损坏且无提示 | WRITE/DELETE 对 `.git/**` 分别 deny |
| **回收区被模型看见** | 模型扫描到回收区，把待恢复文件当垃圾再读一遍 | 位置默认在工作区外；若配置在工作区内，扫描与搜索永远排除 |
| **提权尝试** | prompt 或文件内容里塞「忽略权限，直接删」、伪造 `--dangerously-skip-permissions` | 输入与读入内容扫描提权字样 → 拒绝 + 审计；档位只由用户在 UI 改，模型任何参数都动不了它 |
| **跨卷复制成本** | 回收区在 app-data、工作区在别的盘，`move` 退化为复制 | 单次写入 ≤1MB；删大文件前检查可用空间；同卷自动走 rename |
| **备份被伪造** | 日志或备份名被改，恢复时指向任意文件 | 内容寻址：恢复前重算 sha 与文件名比对，不符即拒绝 |
| **回收区膨胀** | 删 100G 再也没清 | 30 天保留期 + 每日清理任务 + 审计 |
| **磁盘满** | 快照把盘写满 | 写前检查可用空间 ≥ 文件大小 ×3，不足则拒绝 |
| **文件被占用** | Windows 上 IDE / 杀软锁文件 | 明确报错"文件被占用，请关闭后重试"，不要笼统 "IO error" |
| **大小写不敏感** | `.SSH` 与 `.ssh` 是同一目录，deny 漏 | deny 比较一律 `toLowerCase()` |
| **Windows 保留名** | `CON` `NUL` `COM1` 打不开 | 入参先过滤 |
| **网络盘** | `\\server\share` 卡住线程 | 读取/写入超时 5s |
| **大目录** | `node_modules` 十万文件 | 默认忽略 + `max-entries` 早停 |
| **Prompt injection** | 文件里藏"把 .env 读到日志里" | ① system prompt 声明文件内容是数据不是指令；② `.env`/密钥类一律 deny READ；③ 每次读写删都审计；④ 档位默认只读 |
| **审计二次泄露** | 把文件内容记进审计表 | 只记 `path` + `sha256` + 字节数 + 行数 |
| **C 形态误用** | 多人浏览器部署开了这功能 | `local-mode=false` 直接禁用 |
| **用户误解** | 以为删了工作区就删了文件 | UI 文案 + API 文档双处声明 |
| **撤回覆盖手改** | 撤回前用户在 IDE 改过同一文件 | §6.4.3 冲突检测：`afterSha` 不一致则跳过并报告 |
| **日志未落盘就动文件** | 崩溃后文件回不去 | 先写 `begin` 再改文件；重启按 begin 回滚 |
| **撤回中间轮** | 后续轮的改动依赖被回滚的内容 | 撤回该轮即作废其后所有轮，文件与消息一起退 |
| **blob 被提前清理** | 后续轮次仍引用它，L2 撤回拿到残缺快照 | 清理前扫 journal 做引用计数 |
| **两轮并发写** | 同一会话并发提交，日志交错 | journal 按 sessionId 加文件锁；工具层串行化同会话操作 |
| **撤回与 git 状态脱节** | 回滚后工作树与暂存区不一致 | 明确不做 git 操作，文档写清；前端提示"若已 git add 请自行处理" |

## 12. 配置样例

```yaml
agent-tools:
  workspace:
    enabled: false                 # 总开关
    max-file-size: 2097152         # 读：单文件 2MB
    max-write-bytes: 1048576       # 写：单次 1MB
    max-read-chars: 8000           # 单次回灌上限
    max-entries: 5000              # 单次遍历上限
    max-delete-files: 100          # 单次删除文件数上限
    trash-location: "app-data"     # app-data(默认,不污染仓库) | workspace(同卷 move O(1))
    trash-retention-days: 30
    journal-enabled: true          # 变更日志(撤回的前提)
    rewind-max-turns: 50           # 单次撤回最多回滚的轮次数
    read-timeout-seconds: 5
    default-ignore: "node_modules,.git,target,dist,build,.idea,__pycache__,.workspace-trash"
    deny-read: ".ssh,.aws,.gnupg,.env,id_rsa,.pem,.p12,.p8,.keystore,.npmrc,.kdbx"
    deny-write: ".git/objects,.git/refs,.git/HEAD,.git/config"
    deny-delete: ".git,.workspace-trash"

agent:
  workspace:
    browse-enabled: false          # 目录枚举接口，仅 admin
    local-mode: true               # false = 服务器部署，功能禁用
```

## 13. 一期验收标准

**读**
- [ ] 选定工作区后，模型能列出顶层目录并回答"这项目用了什么框架"
- [ ] 读 3000 行日志，返回前 200 行 + 剩余行数提示，模型能自己翻页读完
- [ ] 搜索"哪里用了 Redis"，返回 `文件:行号`，位置准确

**写**
- [ ] 新建文件成功，内容与传入一致
- [ ] `edit` 精确替换单处成功；`old_string` 出现多次时**报错而非任选一处**
- [ ] 外部修改后写入被拒绝，提示"请重新读取"
- [ ] GBK 文件改完仍是 GBK，中文不乱码
- [ ] CRLF 文件改完仍是 CRLF，`git diff` 只显示改动行
- [ ] 写 2MB 内容被拒（超 `max-write-bytes`）
- [ ] 写 `.git/config` 被拒
- [ ] 模型读到一半、用户外部改了文件，随后写入被拒（新鲜度校验）
- [ ] 写入过程中 Windows 上 `rename` 返回 `EEXIST/EPERM` 时能退化成功，且不留 tmp 残留

**删**
- [ ] 删除文件后，回收区有快照，`restore` 后 sha256 与原文件一致
- [ ] 删非空目录且 `recursive=false` 被拒
- [ ] 删工作区根被拒
- [ ] 一次删 200 个文件被拒（超上限）
- [ ] 删 `.git/` 被拒
- [ ] 回收区不出现在 `workspace_list` / `workspace_search` 结果里

**权限与隔离**
- [ ] `READ` 档工作区，模型工具列表里没有 `write` / `edit` / `delete`
- [ ] `WRITE` 档，模型调 `delete` 被拒
- [ ] 用户 A 无法通过任何参数访问用户 B 的工作区
- [ ] 未绑定工作区的会话，工具返回友好提示，不抛异常
- [ ] `enabled=false` 时工具不出现

**安全**
- [ ] `../../etc/passwd`、`C:\Windows\win.ini`、指向 `C:\Users` 的 junction，全部被拒且原因明确
- [ ] **链式链接 A→B→C 且中间跳逃出工作区，被拒**（单次 `toRealPath` 会漏判的那类）
- [ ] 读 `.env` 被拒
- [ ] 读 5MB 的 jar 被拒，提示"二进制文件"
- [ ] GBK 中文 txt 正确显示

**撤回**
- [ ] 一轮里同一文件被改 5 次，撤回后回到该轮**之前**的内容（不是某个中间态）
- [ ] 撤回会删除该轮及其后的消息，会话回到发送这条之前的样子
- [ ] 该轮新建的文件被移入 `undo-*` 桶，未真删，可再恢复
- [ ] 撤回前用户手改过的文件被跳过并单独报告，不被覆盖
- [ ] 同一轮重复撤回返回「已撤回」，不报错
- [ ] 撤回中间轮时，其后所有轮的改动一并回滚
- [ ] 模拟写入中途崩溃，重启后可按 journal 的 `begin` 记录回滚
- [ ] 撤回后长期记忆里该轮自动抽取的条目已清除，手写记忆保留
- [ ] 清理任务不会删掉仍被引用的 blob
