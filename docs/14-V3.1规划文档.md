## 1. 版本概述

### 1.1 V3.1 定位

V3.0 发布后，平台已具备生产级编排能力。V3.1 不追求大而全的新能力堆叠，而是**三收一扩**：

| 方向 | 内容 | 依据 |
|------|------|------|
| 安全收口 | 会话接口越权修复、对话检索归属校验 | V3.0 开放知识库给普通用户后，安全边界需完整闭合（技术债） |
| 体验增强 | 语音输入/输出（STT/TTS） | `docs/12` 存档项②，设计已齐备（F-12/F-13），对话承载链路早已交付，恢复时机成熟 |
| 生态扩展 | 代码执行沙箱、Agent/工作流版本管理、成本分析报表、远程模板市场 | `07-V3.0规划文档.md` §20 远景展望（V3.1 项）+ F-34 收尾 |
| 运维落地 | 多实例 + PostgreSQL 主从 + 灾备演练 | `docs/13-部署与高可用.md` 已有完整方案（F-40.13），本版实施 |

### 1.2 与 V3.0 的关系

- V3.0 全部能力保持兼容，V3.1 仅增量扩展（新 API / 新配置项，默认关闭）
- V3.0 明确"不实施"的事项继续冻结：完整 SaaS 多租户（`docs/12` ①）、本地模型扩大投入（`docs/12` ③）
- 浏览器 Agent / 多模态 Agent 扩展 / Agent 自主学习 维持 V3.2+ 远景，不纳入本版

## 4. F-41 安全加固收口

> 背景知识库开放给普通用户（user 角色拥有 kb:read/kb:write）后，部分访问路径的归属校验存在缺口。本项为**安全硬伤修复**，最先交付。

### 4.1 已识别的越权面

| 位置 | 问题 | 修复方式 |
|------|------|---------|
| `SessionController` 修改类接口 | `PATCH /{id}/system-prompt`、`PUT /{id}/title`、`DELETE /{id}` 仅校验存在性（`getSession(id)` 无 userId），任何登录用户可篡改/删除他人会话 | 改用 `sessionManager.getSession(id, userId)` 归属校验，越权统一返回 404 |
| `GET /{id}/messages` 等读取接口 | 部分读取路径未校验归属，存在消息记录越权读取风险 | 同上，统一按 userId 过滤 |
| 对话内 RAG 检索 | `ChatRequest.knowledgeBaseIds` 由前端传入，后端未校验 kbId 归属——用户可传他人 USER 级 kbId 触发检索其私有文档 | 在编排层（`prepareForChat`/检索工具入口）按 `getAccessible` 同口径校验每个 kbId（自己的 USER 级或 PLATFORM 级才放行） |
| 越权回归测试 | 缺少自动化越权用例，修复后易回退 | `docs/10-完整测试用例文档.md` 增加安全用例章节（横向越权矩阵），纳入 CI |

### 4.2 实施要点

1. 归属校验统一收敛到各 Manager/Service 层（与 `KnowledgeBaseService.getAccessible` 同模式），Controller 只做参数传递，避免散点判断
2. 修复遵循"越权即不存在"原则（返回 404 而非 403，避免资源枚举探测）
3. 审计日志记录越权尝试（`audit/` 模块，`record("access_denied", ...)`），为风控提供数据
4. 验收标准：横向越权矩阵用例全绿（用户 A 对用户 B 的会话/知识库/文档做读写删均被拒绝）

### 4.3 实施状态（2026-09-14 已落地）

> 落地时对方案做了**两次升级**：
> ① 原文设想是"逐层沿用 `KnowledgeBaseService.getAccessible` 模式"，实际抽出为一套可复用的
> **统一归属框架**（`com.dcdr.agent.auth.ownership`）—— 新增受保护资源只需「加一个枚举 + 一个 Provider」，
> 无需再写任何判断分支；
> ② 声明式接入最终采用 **Spring Security 官方响应式方法级安全**（`@EnableReactiveMethodSecurity` +
> `@PreAuthorize`），而非自研 AOP 切面 —— 上下文由框架从 Reactor Context 提供，
> Controller 方法**零额外参数**。

| 交付物 | 位置 | 说明 |
|--------|------|------|
| 归属框架骨架 | `auth/ownership/` | `OwnedEntity` / `ResourceType` / `AuthContext` / `Ownership` / `ResourceOwnershipProvider` / `OwnershipRegistry` / `OwnershipGuard` |
| 声明式接入 | `SecurityConfig`（`@EnableReactiveMethodSecurity`）+ `OwnershipGuard.requireRead/requireWrite` | Controller 方法标注 `@PreAuthorize("@ownershipGuard.requireRead(#id, 'SESSION', principal)")` 即完成校验；当前用户由 SpEL 变量 `principal` 注入，**方法无需 `ServerWebExchange` 等任何上下文参数**。要求被保护方法返回 `Mono`（接入端点统一 `Mono<Result<T>>`，对外 JSON 契约不变）；返回 `Flux` 的流式端点用 `currentContext()` 手工包一层 |
| 响应式取值 | `OwnershipGuard.currentContext()` | 供需要 userId（按用户隔离 / 写入归属）的接口使用，同样无需声明参数 |
| 资源 Provider | `auth/ownership/provider/`（11 个） | SESSION / KNOWLEDGE_BASE / DOCUMENT / AGENT / WORKFLOW / WORKFLOW_EXECUTION / SCHEDULED_TASK / WEBHOOK / USER_MODEL / PROJECT / GENERATION |
| 会话越权修复 | `SessionController` | delete / title / persona / messages / deleteMessages / export 六个端点接入（4.1 表首行缺口关闭） |
| RAG kbId 归属校验 | `ChatController.sanitizeKnowledgeBaseIds` | 4.1 表第三行缺口关闭：请求携带的越权 kbId **静默剔除**，不报错（避免探测） |
| 统一越权语义 | `OwnershipGuard` | 越权与不存在一律 **404**；admin 放行；匿名仅 `auth.enabled=false` 时兼容；越权写 `access_denied` 审计 |
| 创作项目补归属 | `ProjectEntity.userId` + `docs/sql/v3.1_schema.sql`（归属段落） | `ProjectEntity` 原先无归属字段，PG 下需执行 DDL（当时 `ddl-auto=validate` 不会自动加列；后已调整为 `update`，现由 JPA 启动时自动补齐） |

**口径变更提示（需回归关注）**：迁移前各模块越权返回码为 403/404 混用、admin 放行范围不一致、
匿名（`userId == null`）多数无条件放行。迁移后统一为：越权 404、admin 放行、匿名按 `auth.enabled` 决定。
原先返回 403 的 Agent / 工作流 / 定时任务 / Webhook 已改为 404；`ScheduledTaskService` 原先不支持 admin 放行，现已对齐。

**已验证范围**：H2 启动装配 11 类 Provider 成功；**会话域 9 项 + 创作项目域 8 项**横向越权矩阵
（`docs/10-完整测试用例文档.md` §2.1）实测通过 —— 用户 A 访问/删除自己的资源返回 200，
用户 B 跨用户读取/改名/改人设/读消息/删消息/导出/删除一律返回 404。其余域用例（TC-OWN-09~27）待回归。

**迁移状态（全部完成）**：12 类受保护资源的 HTTP 入口已全部切换到
`@PreAuthorize` + `OwnershipGuard.currentContext()`，Controller 方法**不再声明 `ServerWebExchange` 参数**。
覆盖 Controller：`SessionController` / `ProjectController` / `GenerationController` / `VideoController` /
`ImageController` / `AgentController` / `WorkflowController` / `ScheduledTaskController` /
`WebhookController`（管理端点）/ `UserModelController` / `FeedbackController` /
`KnowledgeBaseController` / `TemplateMarketController`。
Service 层（`KnowledgeBaseService.getAccessible` / `AgentDefinitionService` / `WorkflowEngine` /
`ScheduledTaskService` / `UserModelService` / `FeedbackService` 等）保留原有校验作为**纵深防御**，
与 `OwnershipGuard` 口径一致。

**写入侧自动化（V3.1 增强）**：新增 `CurrentUserHolder`（线程局部当前用户）、
`OwnershipFillListener`（JPA `@PrePersist` 回调）与 `OwnedEntity` 契约，11 个归属实体通过
`@EntityListeners` 注册。insert 前若实体 `userId` 为空则自动填充，用于兜住「新增写入点时漏设归属」
造成无主数据的风险（**显式设置过的一律不覆盖**）。
- 上下文贯通：`SecurityContextWebFilter` 采用「每个请求先清空 → 认证后写入 → 链尾再清空」三段式防残留；
  实测确认 `reactor-http-nio-*` 线程上 JPA 回调可读到当前用户，且**换用户/换线程不串号**。
- 失效边界：跨异步边界（`boundedElastic` / 定时任务 / 工作流内部）读不到上下文，此时**不填充**（fail-closed），
  必须显式传 userId —— 现有 Service 方法签名均保留 userId 参数正是为此。

**设计取舍记录（勿重复踩坑）**：曾先尝试「同步 AOP 切面 + 自备 `ThreadLocalAccessor` +
`Hooks.enableAutomaticContextPropagation()`」从 `SecurityContextHolder` 取用户，
实测在同步返回 `Result<T>` 的 Controller 下始终取不到（表现为用户访问自己的资源也 404），
已放弃并删除相关代码。根因：WebFlux 下 SecurityContext 只存在于 Reactor Context，
同步方法调用不在算子回调语义内，自动上下文传播覆盖不到。结论已写入 `OwnershipGuard` 类注释。

**框架级 fail-fast**：任一 `ResourceType` 缺少 Provider 时应用启动失败，
避免后续新增受保护资源时漏接归属校验被静默放过。

## 6. F-43 代码执行沙箱

> 来源 `07-V3.0规划文档.md` §20 远景展望（代码执行沙箱，V3.1 项）。

### 6.1 范围

- 新增内置工具 `code_interpreter`：模型可生成并执行 Python/JS 代码段，返回 stdout/结果，用于数据计算、格式转换、图表数据生成等任务
- 与现有工具框架一致（`Tool` + `ToolRegistry` 注册期 Schema 转换）

### 6.2 安全设计（本项核心难点）

1. **隔离执行**：容器化沙箱（如独立 Docker 运行时 / gVisor）或进程级沙箱（seccomp + 无网络 + 只读 FS + 资源限额 CPU/内存/时长）
2. **权限控制**：默认关闭（`agent.tools.sandbox.enabled=false`）；仅 admin 可配置启用；自定义 Agent 工具白名单机制复用（`agentAllowedTools`）
3. **输入输出管控**：代码长度与执行时长上限；输出截断入库（复用 `TOOL_RESULT_MAX_LEN` 机制）
4. **审计**：每次执行记录代码摘要 + 耗时 + 退出码，审计日志留痕

### 6.3 里程碑

放 **V3.1-rc**：安全方案需评审通过后再编码，不阻塞 alpha/beta。

## 7. F-44 治理完善（版本管理 + 成本分析）

> F-34 的收尾项。V3.0 已交付监控视图 / 链路追踪 / 审计，本项补齐"版本"与"成本"两块。
>
> **实施前纠正了原文两处与代码不符之处**（否则会做出重复能力）：
> ① 原文写的 `cost_records` **并不存在** —— F-39 落地用的就是 `llm_usage_logs`，故不新建成本表；
> ② 原文写的 `workflow_definition_versions` **已存在**，V3.0 建的表叫 `workflow_versions`，
> 且 `WorkflowEngine.snapshotVersion/listVersions/rollback` 与前端版本弹窗早已交付 →
> 工作流版本**复用现有表**，本项只新建 Agent 侧同构表。

### 7.1 版本管理（F-44.1）

**范围**
- Agent / 工作流定义变更时生成**全量快照**版本
- 支持查看历史版本 diff、回滚到指定版本
- 发布到模板市场时强制携带版本号，克隆按该版本还原

**设计要点**

| 决策 | 结论 | 理由 |
|------|------|------|
| 工作流版本表 | **复用 `workflow_versions`** | V3.0 已交付且在用，不迁移、不改名 |
| Agent 版本表 | 新增 `agent_definition_versions`（`UNIQUE(agent_id, version)`） | 与工作流同构；字段与定义列一一对应（只有存全量才能 diff/回滚） |
| 是否用通用单表 | **否** | 两类快照字段差异大，单表需大 JSON 列，diff 与索引都退化 |
| 主表是否冗余 `version` 列 | **否** | 避免双写不一致；读最新版本用 `findFirstByAgentIdOrderByVersionDesc` |
| diff 实现 | **结构化 diff，不引 java-diff-utils** | 行级 diff 无法表达"哪个字段/哪个节点改了"，对 prompt 与 JSON 编排没有可读性 |
| 工作流结构 diff | 把 `dag_json` 与 `steps_json` **统一成"节点/边"**比较 | 两种编排格式一套口径：节点按 `id`/步骤名对齐，边按 `source->target(label)` |
| 归属校验 | **复用 `ResourceType.AGENT` / `WORKFLOW`**，不新增枚举 | 版本是定义的子资源，归属随父资源 |

**语义**：创建→v1；更新→`max+1`（可带 `changeNote`）；回滚→回写快照并**再生成一版**（历史不被覆盖、可继续回滚）；
快照失败仅 warn 不阻断主流程（与 `WorkflowEngine` 同策略）。
**模板市场"发布即钉版本"**：`template_shares.source_version`；分享时缺省取最新版本、显式传入则校验存在（否则 404）；
克隆按该版本快照还原；预置模板与存量分享 `source_version` 为 null 时保持 V3.0 行为（按当前定义克隆）。

### 7.2 成本分析报表（F-44.2）

**范围**：基于 `llm_usage_logs` 按 用户 / 模型 / 时间 维度聚合；监控视图新增成本页（日/周/月趋势、Top 用户、模型占比）；支持导出 CSV。

**设计要点**

| 决策 | 结论 | 理由 |
|------|------|------|
| 数据源 | `llm_usage_logs`（**不新建 cost_records**） | F-39 已落库，新建即双写/双源 |
| 金额口径 | 新增 `agent.v3.cost.pricing`（元/千 token）→ 写入时折算落 `cost_amount` | 混合模型下"成本占比 ≠ token 占比"（实测：某模型占 58.8% token 但仅 5.2% 金额） |
| 未配置定价时 | 落 **null**（不是 0），报表返回 `costDataAvailable=false`，前端金额列降级为 `—` | 否则把"没定价"误报成"零成本"；且默认 `pricing: {}` 为空 —— 单价是事实数据，预设编造值会让错误金额静默入库 |
| 周/月趋势 | **Java 侧 rollup**（数据库只查天粒度） | JPQL 无 `date_trunc`，nativeQuery 会绑死 PG 并在 H2 下报错（项目已有同类踩坑） |
| 用户维度权限 | **仅管理员 `scope=global` 下返回** | 否则即跨用户信息泄露 |
| CSV | 自写 `common/CsvWriter`，不引 Commons CSV | 需要 UTF-8 BOM（Excel 中文乱码）+ 公式注入转义（`= + - @` 前缀），轮子太小且是本项目特有需求 |

### 7.3 实施状态（2026-09-28 已落地）

## 10. F-47 工具结果体积治理

> 来源：V3.1 规划期对工具调用链路（`AgentOrchestrator`）的代码走查。现状已有"字符数硬截断"兜底，但缺少 token 级控制、摘要压缩与落盘分页机制，属工具结果超限技术债。

### 10.1 现有机制（改造前基线；实际变更见 §10.5）

| 机制 | 位置 | 说明 |
|------|------|------|
| 回灌截断 | `AgentOrchestrator`（`truncate` / `TOOL_RESULT_MAX_LEN=6000`） | 工具结果写入 `history` 前统一截断，覆盖 chat/agent 全部工具调用路径，是当前**唯一兜底** |
| 正文二次截断 | `AgentOrchestrator`（`MAX_CONTENT_LENGTH=4000`；联网精简每来源正文 1000；`EXTRACT_TOP_N=3`） | 网页正文清洗后截断，限制抓取全文的文章数 |
| 工具内部瘦身 | `McpTool`（snippet 200 / 来源上限 12）、`KnowledgeSearchTool`（snippet 300） | 工具自身做结果精简，只给模型摘要不塞全文 |
| 展示/日志截断 | `AgentOrchestrator`（调用链日志 500；`MESSAGE_SNAPSHOT_LIMIT=1000`） | **不影响模型上下文**，仅控制日志/落库体积 |

### 10.2 缺口清单

| 编号 | 缺口 | 影响 | 处置建议 |
|------|------|------|---------|
| F-47.1 | 阈值硬编码：`TOOL_RESULT_MAX_LEN=6000`、`MAX_CONTENT_LENGTH=4000` 等均为常量，`application.yml` 与 `AgentProperties` 无对应配置项 | 无法按模型上下文窗口/环境调优 | 新增 `agent.tools.result.*` 配置（max-length / max-token-budget / keep-tail），默认值与现值一致 |
| F-47.2 | 按字符不按 token：中文约 1 token/字，6000 字符 ≈ 6000 token，多工具并发时可撑爆上下文；`TokenEstimator` 仅用于"接近上限提示" | 上下文溢出/响应异常 | 复用 `TokenEstimator` 做工具结果 token 预算分配 |
| F-47.3 | head-only 截断：`truncate` 用 `substring(0, maxLen)`，只保留头部 | 尾部结论/表格末尾等关键信息丢失 | 改为头尾保留（keep-head + keep-tail）或结构化切分 |
| F-47.4 | 无摘要/压缩降级：截断即丢弃；`InMemoryChatMemory.loadWindow` 仅按**条数**裁剪（`max-messages: 6`），不看单条体积 | 超长结果信息整体丢失 | 超阈值时先 LLM 摘要再回灌，摘要失败回退硬截断 |
| F-47.5 | 无落盘 + 按需分页读取：无"超大结果写临时文件 + 模型分页/检索读取"机制 | 大文件/大查询结果无法被有效利用 | 超落盘阈值（如 32KB）写入 `data/tool-results/{sessionId}/`，回灌"路径 + 摘要 + 前 N 行"，新增分页读取工具 |
| F-47.6 | sources 落库未截断：`collectedSources` 经 `InMemoryChatMemory` 写入 `sources` 列时不做截断，`web_extract` 整页 `content` 原样入库 | DB 单行膨胀 | 落库前套用同一阈值 |
| F-47.7 | 前端展示未截断：`ChatChunk.toolResult` 下发完整 `result`，与模型侧看到的截断版本不一致 | 前端/带宽压力，且两侧不一致 | 下发前截断或附带 truncated 标记 |
| F-47.8 | 无截断统计/告警：截断后不记录原长与被截长度 | 线上排查不可见 | 记录原长/截断长并打点（日志 + 审计） |

### 10.3 实施要点

1. **配置化（低风险，先做）**：阈值收敛到 `AgentProperties`，默认值与 V3.0 现值一致（6000 / 4000），升级后行为不变，保证兼容
2. **预算化 + 降级**：以 `TokenEstimator` 估算工具结果 token；超单条阈值按"头尾保留"截断，超总量预算时对最旧/最长结果做摘要
3. **落盘（可选增强）**：超大结果落盘 + 分页读取工具，与 F-43 代码沙箱的输出管控复用同一套截断机制（见 §6.2 第 3 条）
4. **一致性**：模型上下文、落库 `sources`、前端下发三处使用同一阈值口径

### 10.4 验收标准

- 阈值可通过配置调整，且默认行为与 V3.0 一致（兼容性验证通过）
- 工具结果回灌 token 数不超过配置预算（以 `TokenEstimator` 断言）
- 超长结果不再只保留头部，尾部关键信息（结论/表格末尾）保留可验证
- 落盘模式下模型可通过工具读取被截断部分
- 截断事件可在日志/审计中查询到原长与被截长度

### 10.5 实施状态（2026-09-28 已落地）

**落地前先纠正原文三处与代码不符之处**（否则会把已有能力当成缺口来做）：

| 原文说法 | 实际 |
|---|---|
| `MESSAGE_SNAPSHOT_LIMIT=1000` 用于展示/日志截断 | **代码中无此常量**；`snapshotMessages` 显式注释"不做内容截断"，体积控制下沉到接口层 |
| "模型 / 落库 / 前端三处同一口径" | **实际只有 2 处截断**（回灌模型 + `role=tool` 消息落库）；**前端下发 `ChatChunk.result` 与 assistant 正文拼接的工具结果都未截断** —— 缺口比原文描述的更严重 |
| `TokenEstimator` 仅用于"接近上限提示" | 还用于**模型未返回 usage 时的 token 兜底估算**（`resolveUsage`）；内核已是 jtokkit `cl100k_base` BPE。可复用性优于原文假设 |

另有一处命名冲突：现有工具配置前缀是 **`agent-tools.*`**（`ToolsProperties`），与原文提议的 `agent.tools.*` 不一致。
本项按"回灌治理属<b>编排层</b>行为、不是某个工具的设置"的判断，落在 **`agent.tools.result.*`**（`AgentProperties` 下，与 `agent.memory.*` 同层）。

**核心设计：单点收口**

```
工具执行 → raw（原先无任何上限）
   ↓
ToolResultCompressor.compress(tool, raw, roundCap)          ← 唯一收口点
   ├─ ① 超 spill.threshold   → 全文落盘；回灌"路径 + 规模 + 前 N 行"，模型用 tool_result_read 分页取回
   ├─ ② 超 summary.threshold → LLM 摘要（失败/异常一律回退硬截断）
   └─ ③ 超 max-length / token 预算 → 头(70%) + 截断标记 + 尾(30%)
   ↓
三个消费点共用同一份文本：① history 的 tool 消息 ② ChatChunk.result ③ assistant 正文与落库
```

- **为什么在"产出处"收口，而不是三个消费点各截一次**：三处各截必然漂移（V3.0 的现状正是漏了两处）；
  单点收口让"口径一致"成为结构性保证 —— 将来新增第四个消费点也不会漏。
- **降级顺序刻意是"落盘 → 摘要 → 硬截断"**：落盘后回灌体积已很小，再做一次模型调用纯属浪费；
  摘要是"中间带"（未到落盘阈值但远超上下文可承受体积）的最优解，代价是一次模型调用。
- **压缩失败绝不影响主链路**：摘要异常、落盘失败一律回退到下一档。

**交付物**

| 文件 | 作用 |
|---|---|
| `tool/result/ToolResultCompressor` | 三级降级的唯一收口点（含 `Compressed` 统计记录） |
| `tool/result/ToolResultSpillStore` | 落盘 + 分页读取 + 惰性过期清理；**路径穿越与会话隔离校验** |
| `tool/result/ToolResultContextHolder` | 会话上下文 ThreadLocal（同 `KnowledgeSearchContextHolder` 模式） |
| `tool/result/ToolResultReadTool` | `tool_result_read` 工具（分页取回落盘全文，`supportsStreaming=true`） |
| `config/AgentProperties` | 新增 `agent.tools.result.{max-length, max-token-budget, keep-tail-ratio, source-content-max-length, window-token-budget, window-floor-length, summary.*, spill.*}` |
| `AgentOrchestrator` | 产出处压缩一次；删除本地 `TOOL_RESULT_MAX_LEN` / `truncate`（消除第二种口径） |
| `InMemoryChatMemory` | `sources` 落库前按 `source-content-max-length` 截断（F-47.6） |

**验收：新增 11 条单元测试 `ToolResultGovernanceTest`（实测全绿）**

| 覆盖点 | 断言要点 |
|---|---|
| 未超限不改动 | 原样返回、`changed=false` |
| 超限头尾保留 | `startsWith(头部)` 且 `endsWith(尾部哨兵)`、保留量 ≤ 上限 |
| 尾比 0 兼容 | 尾部哨兵不出现（退回 V3.0 纯头截断） |
| token 预算生效 | 5000 个中文字符在 `max-token-budget=300` 下实测估算 ≤ 300 |
| 落盘 | 落盘文件内容**逐字符等于原文**；回灌为原文零头，且含 `tool_result_read` 提示与相对路径 |
| 窗口预算 | 未触顶返回 0（不收紧）；触顶返回下限 |
| 路径穿越防护 | `../../etc/passwd`、归一化后越界、空路径**全部被拒** |
| 会话隔离 | 切换会话后读取他人落盘文件被拒 |
| 分页读取 | 返回范围头（`第 1-100 行 / 共 300 行`）与续读提示，可从 offset 续读 |
| 工具契约 | 缺 `path` 给出可读提示；合法 `path` 能取回内容；`supportsStreaming=true` |

**与原文的偏差（显式记录，均未实现）**

1. **F-47.4 的"超总量预算时对最旧/最长结果做摘要"** → 改为"窗口预算触顶后，本轮结果统一收紧到
   `window-floor-length`"。理由：对历史消息补摘要需要回溯改写已回灌内容，复杂度与失败面都大得多；
   两级降级可预测、且不产生额外模型调用。
2. **F-47.8 的"日志 + 审计"** → 只做**日志**（WARN 含原长/压缩后/token 估算）与**回灌文本内的截断标记**
   （随调用链快照归档）。**未写 audit 记录** —— 每次工具调用都写审计会把审计表变成噪声源，
   与 F-41 建立的"审计只记安全/运维事件"口径冲突。需要时可一行接上。
3. **摘要超时** → 未新增超时开关，依赖 Provider 的 HTTP 客户端超时（已有配置），失败即回退硬截断。

| 权限 | 新接口纳入 RBAC：语音 `chat:chat`、沙箱执行 `chat:chat` + Agent 白名单、版本管理 `agent:read/write`、成本报表 `user:manage`（本人数据除外） |

> **实施后修正（2026-10-15，发布收尾时与实际交付的出入）**：
> ① 增量脚本**不是**上表所说单一 `docs/sql/v3.1_schema.sql` —— 发布时按功能拆为 5 个分脚本，后于 2026-10-15 并入 `docs/sql/v3.1_schema.sql`（段落顺序即依赖顺序，见 [`docs/sql/README.md`](sql/README.md)）；
> ② `agent.audio.*` 与 `agent.market.remote-repos` 均未交付（语音为 V1.1 遗留键 `agent.models.audio`，见 `docs/12`）；
> ③ 沙箱随仓默认值为**开启**（`agent-tools.sandbox.enabled=${AGENT_TOOLS_SANDBOX_ENABLED:true}`），与"默认关闭"相反；
> ④ `agent.tools.result.*` 的 `window-token-budget`/`summary.enabled` 代码默认 0/false，随仓覆盖为 6000/true —— "与 V3.0 逐字一致"并不完全成立；
> ⑤ 发布收尾时新增两项**必填**密钥（`JWT_SECRET` / `MODEL_API_KEY_SECRET`），缺省拒绝启动，见发布说明"破坏性变更"小节。

## 13. 技术风险

| 风险 | 影响 | 缓解 |
|------|------|------|
| 沙箱逃逸 | 服务器安全 | 容器隔离 + 无网络 + 资源限额；安全评审前置；默认关闭 |
| 语音服务成本 | API 费用 | 用量入 CostTracker；配额联动；默认关闭按需开启 |
| 多实例 SSE | 长连接负载不均 | LB 粘滞会话 + 优雅停机（V3.0 已具备） |
| 远程模板安全 | 恶意模板 | 包签名校验 + 导入审查提示；仓库源仅 admin 可配 |
| 工具结果超长撑爆上下文 | 多工具并发/大结果导致上下文溢出或响应异常 | F-47 按 token 预算控制 + 摘要降级 + 可选落盘；保留现有字符截断兜底 |
