## 一、前置条件

| 组件 | 版本 | 用途 |
|------|------|------|
| JDK | 17 | 后端 |
| Maven | 3.9+ | 构建 |
| Node.js | 18+ | 前端 |
| Docker | 20.10+ | PostgreSQL / Redis / SearXNG / 沙箱（推荐；也可本机安装，见 `docs/sql/README.md` 第九节） |

**两项必填密钥**（v3.1 起启动期强制校验，缺省会**拒绝启动**）：

| 环境变量 | 用途 |
|---|---|
| `JWT_SECRET` | 登录令牌签名密钥。公开可知 = 任何人可伪造任意用户（含 admin）的 Token |
| `MODEL_API_KEY_SECRET` | 用户自定义模型 API Key 的加密主密钥。公开可知 = 拿到库即可解出用户真实 Key |

生成随机值（**两个密钥不要复用同一个值**）：

```powershell
# Windows PowerShell（每次执行得到一个不同的 64 位十六进制）
[guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
```
```bash
# Linux / macOS
openssl rand -hex 32
```

## 二、本地运行（开发模式）

### 2.1 准备 `.env`（项目根目录）

`.env` 会被**本地运行与 docker compose 同时读取**（`application.yml` 的 `spring.config.import`），
且已被 `.gitignore` 忽略 —— **绝不提交**。内容示例：

```dotenv
# 必填（启动期校验）
JWT_SECRET=<随机值>
MODEL_API_KEY_SECRET=<另一个随机值>

# 模型 API Key：配哪个取决于 application.yml 里哪个模型 enabled: true（见 2.3）
# DASHSCOPE_API_KEY=sk-xxx
# DEEPSEEK_API_KEY=sk-xxx

# 可选：代码执行沙箱的访问口令（不写则用 compose 的缺省值）
# SANDBOX_API_KEY=<随机值>
```

### 2.2 启动依赖（数据库 + Redis）

```bash
docker compose up -d postgres redis
```

- 首次启动会**自动建库**：initdb 按序执行 `v2.0 → v3.0 → v3.1` 三个脚本（含 pgvector 扩展），
  **无需手工执行任何 SQL**
- 只需要这两个服务 —— 应用 / SearXNG / 沙箱在开发模式下跑在本机或按需再起
- 无 Docker：按 [`docs/sql/README.md`](sql/README.md) 第九节本机安装 PostgreSQL 16 + pgvector + Redis，
  然后一条命令建库：`psql -U dcdr_agent -d dcdr_agent -f docs/sql/v2.0_schema.sql -f docs/sql/v3.0_schema.sql -f docs/sql/v3.1_schema.sql`

### 2.3 模型 API Key

`application.yml` 里各模型的 `api-key` 形如 `${DASHSCOPE_API_KEY:demo-key}` —— `demo-key` 只是**占位**，
让应用能启动但模型调用会失败。把你要用的模型对应的环境变量加进 `.env` 即可；
或登录后在界面右上角配置**用户自定义模型**（Key 加密存储、不回显）。

### 2.4 启动后端

```bash
mvn spring-boot:run          # 默认激活 pg profile（PostgreSQL）
```

- 后端：`http://localhost:8080`，接口文档：`http://localhost:8080/swagger-ui.html`
- 如果启动报「`agent.auth.jwt.secret ... 未配置`」，是 `.env` 没被读到或变量名拼错 ——
  报错信息里会写明缺哪个变量、怎么生成（`SecretGuard` 的提示是可操作的）

### 2.5 启动前端

```bash
cd frontend
npm install
npm run dev
```

前端 dev server 跑在 `http://localhost:5173`，`/api` 自动代理到 8080（`vite.config.js`）。

### 2.6 首次使用

- 打开前端，**注册的第一个用户自动成为 admin**（之后注册的都是普通用户）
- 左侧「记忆」页可管理长期记忆；「AI 自动记忆」开关默认跟随部署配置
  （`agent.memory.auto-extract.enabled` 随仓为 `true`，会周期性产生模型费用，不想用就在界面关掉或改配置）

### 2.7 可选能力

| 能力 | 本地怎么开 |
|---|---|
| 联网搜索 | `docker compose up -d searxng`（应用默认访问 `http://localhost:8888`），并在对话里打开「联网」 |
| 代码执行沙箱 | 起 OpenSandbox Server（compose 服务 `opensandbox-server`，默认 `localhost:18080`）；`agent-tools.sandbox.enabled` 随仓为 `true`，**对外交付建议改 `false`** |
| 本地模型（Ollama） | `application.yml` 的 `ollama-chat`，`enabled` 改 `true` 并填模型名 |

## 三、Docker 部署

### 3.1 最小部署（单机）

```bash
# 1) 准备 .env（两项必填密钥 + 要用的模型 Key）
# 2) 先起依赖，再起应用（v3.2 起两个编排分开，见下）
docker compose up -d
docker compose -f docker-compose.app.yml up -d --build
```

服务分布（拆成了两个文件）：

| 服务 | 端口 | 所在文件 | 说明 |
|---|---|---|---|
| `agent` | 8080 | `docker-compose.app.yml` | 应用本体（本地构建镜像 `dcdr-agent:local`） |
| `postgres` | 5432 | `docker-compose.yml` | PostgreSQL 16 + pgvector，**首次启动自动执行全部建库脚本** |
| `redis` | 6379 | `docker-compose.yml` | 缓存 / 多实例协调 |
| `searxng` | 8888 | `docker-compose.yml` | 自建联网搜索 |
| `opensandbox-server` | 18080 | `docker-compose.yml` | 代码执行沙箱 |
| `zipkin` | 9411 | `docker-compose.yml` | 调用链追踪 |

> **为什么拆开**：中间件生命周期远长于应用。改代码只需 `docker compose -f docker-compose.app.yml up -d --build`，
> 不再连带重建/重启 PG 与 Redis；本机调试时也只起 `docker compose up -d`，应用在 IDEA 里跑。
> 两者通过固定网络 `dcdr-net` 互通，容器内按服务名访问 `postgres:5432` 等。
> 注意顺序：`docker-compose.app.yml` 里不能写 `depends_on: postgres`（跨文件的服务不可见），
> 所以必须先起依赖再起应用。

### 3.2 验证

```bash
docker compose ps                                   # 依赖全部 healthy
docker compose -f docker-compose.app.yml ps         # 应用 running
docker compose -f docker-compose.app.yml logs -f agent   # 看到 Netty 启动完成、无 SecretGuard 报错
```

然后访问 `http://localhost:8080`（前端可 `npm run build` 后由后端静态托管，或单独部署）。

### 3.3 升级已有部署

```bash
git pull
docker compose -f docker-compose.app.yml up -d --build   # 只重建应用，依赖不动
```

- **数据库升级**：每个主版本一个脚本（`v3.0_schema.sql` / `v3.1_schema.sql`），一条命令即可
  （全部幂等，可重复执行）：

  ```bash
  psql -U dcdr_agent -d dcdr_agent -f docs/sql/v3.0_schema.sql -f docs/sql/v3.1_schema.sql
  ```

  应用侧 `ddl-auto=update` 也会自动补齐表与列 —— SQL 脚本的价值在于可控、可审查
  （`document_chunks.embedding` 的 `VECTOR` 类型与 pgvector 扩展必须由脚本创建）。
- ⚠️ **更换 `JWT_SECRET`** → 所有已签发 Token 立即失效，用户需重新登录（预期行为）
- ⚠️ **更换 `MODEL_API_KEY_SECRET`** → 已保存的用户自定义模型解不出 Key，需重新填写
  （旧密文是用旧密钥加密的；**不要**把新密钥设成任何随仓出现过的值）
- 数据备份：`scripts/backup-db.ps1`（详见 `docs/16`）—— 备份必须落宿主机

### 3.4 上生产前的加固清单

| 项 | 随仓值 | 建议 |
|---|---|---|
| `agent-tools.sandbox.enabled` | `${AGENT_TOOLS_SANDBOX_ENABLED:true}` | 对外交付改 `false`，或严格限制可用的 Agent |
| `agent.memory.auto-extract.enabled` | `true` | 周期性模型费用，按需关闭 |
| `agent.skill.hub.enabled` | `true` | 会访问外部 SkillHub，内网环境改 `false` |
| `POSTGRES_PASSWORD` / `dcdr_agent` 口令 | `dcdr_agent` | **必须**修改（compose 与 `application-pg.yml` 同步改） |
| `SANDBOX_API_KEY` / searxng `secret_key` | 占位值 | 改为随机值 |
| `platform-kb-ids` | 本部署的真实知识库 ID | 换部署需替换或清空 |

## 五、常见问题

| 现象 | 原因与处理 |
|---|---|
| 启动报「`agent.auth.jwt.secret ... 未配置`」 | `.env` 缺 `JWT_SECRET`，或本地运行没读到 `.env`（确认文件在**项目根目录**、变量名拼写正确） |
| 所有用户被登出 | 换过 `JWT_SECRET`（预期行为） |
| 用户自定义模型报「主密钥可能已变更」 | 换过 `MODEL_API_KEY_SECRET`，重新保存一次 API Key |
| 5432 端口被占用 | 改 compose 端口映射并同步数据源（见 `docs/sql/README.md` 第八节） |
| 镜像拉取慢 | 配置 registry-mirrors（见 `docs/sql/README.md` 第八节） |
| 前端 401 | 后端未启动 / `.env` 缺密钥导致后端没起来；先看 `docker compose logs agent` 或本地后端日志 |
