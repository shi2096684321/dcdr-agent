## 1. 一句话定位

> **面向个人创业者（一人公司）的 AI 助手工作台：用户像安排员工一样分配任务，平台内部用多个角色分工完成，对外只呈现一个统一入口。**

---

## 2. 定位四要素

| 要素 | 内容 | 为什么必须明确 |
|------|------|---------------|
| **谁** | 一人公司 / 自由职业者 / 独立创作者 | 不是"所有个人"。普通消费者没有需要外包的重复劳动 |
| **干什么** | **分配任务**（不是配置 Agent） | 这是与"Agent 构建平台"的分界线 |
| **怎么做到** | **内部多角色分工**（技能换装为主，多 Agent 协作为辅） | 技术纵深所在，也是与"普通聊天机器人"的分界线 |
| **对外现状** | **单一入口 + 单一身份** | C 端生死线：用户不能感知"我有 10 个 Agent" |

**判断标准**：如果一句话里出现"用户需要先选择 / 配置 / 搭建"，就是违背定位了。

---

## 3. 三个必须守住的边界（防漂移）

### 3.1 "一人公司"是用户身份，"员工"是心智模型

- **用户是老板**（一人公司），产品是"帮他干活的人"
- "员工"只用于沟通与界面隐喻，**不能让用户真的去管理员工**（那是负担）
- 目标感觉是："我有几个人在帮我"，而不是"我在管理一个 Agent 列表"

### 3.2 "工作台"是干活的地方，不是配置的地方

工作台的正确形态：

```
一个对话框（主入口） + 一排"我的员工"卡片（点卡片 = 派活）
```

❌ 错误形态（必须避免）：

```
Agent 列表页 → 点进去 → 填 prompt / 选工具 / 调 temperature
```

**C 端铁律：用户做不了"配置"，只能做"选择"。**

### 3.3 "Agent"对外永远不出现复数

- 用户看到的不是"我有 8 个 Agent"，而是"我有调研、整理资料这几个人"
- 内部派生多少执行体，用户不感知、不需要知道
- **"多 Agent"是内部实现细节，绝不能变成用户的认知负担**

## 4. 首批岗位

### 4.1 选岗位的判据（最重要）

> **选"天生需要多角色协作"的过程型任务，而不是"一次生成就完事"的生成型任务。**

原因：生成型任务（写一段文案）单次调用就能完成，**既练不到多 Agent 协作，也证明不了平台价值**。

### 4.2 首批两个岗位

| 岗位 | 典型场景 | 天然的角色分工 | 复用的现有能力 |
|------|---------|---------------|---------------|
| **调研员** | "帮我调研一下 XX 领域的竞品" | 搜索员找资料 → 筛选员判相关性 → 汇总员写报告 | 联网搜索（v1.1.0）、RAG、工具注册 |
| **资料管家** | 扔一堆文档/链接，整理成可问答的知识库 | 解析 → 分类 → 摘要 → 去重 | RAG 全套（分块 / 向量 / 检索） |

### 4.3 暂不纳入首批

| 岗位 | 原因 |
|------|------|
| 文案员 | 竞品极多（通用大模型即可完成），且生成型任务不需要架构支撑 |
| 客服/回复员 | 需接入第三方平台（微信/电商后台），技术依赖重，风险高 |
| 记账/票据 | 低频刚需，但涉及财务数据，合规与安全成本高 |

### 4.4 多模态能力的定位（**保留**，分期实现）

多模态**不纳入首批岗位**，但**明确保留为长期能力**，不因首批收敛而删除。

> **现状说明**：图像生成 / 视频生成 / 音频（TTS）/ 图片理解的**底层能力已实现**
> （见 `README.md` §二 特性总览），待补的是**在岗位体系中的整合与统一入口**，不是从零开发。

#### 4.4.1 对一人公司的价值

| 能力 | 一人公司场景 | 建议归属 |
|------|-------------|---------|
| **图片理解** | 看懂客户截图、识别票据、读懂图表 | 作为**工具**挂在客服 / 资料类角色上 |
| **图像生成** | 商品图、封面、海报、配图 | 独立岗位「设计员」，或「内容员」的子能力 |
| **视频生成** | 短视频素材、产品演示 | 独立岗位或高级功能 |
| **语音（TTS）** | 口播配音、回复朗读 | 作为**输出形式**（回复朗读），不单独成岗位 |

#### 4.4.2 两种接入形态（并存，不冲突）

1. **作为工具**：挂在需要它的角色上（如客服角色天然具备"看懂客户图片"的能力）
2. **作为独立岗位**：出图 / 出视频是高频且独立的任务，值得单独成岗（如「设计员」）

判断依据仍是 4.1 节的判据：**是不是需要多角色协作的过程型任务。**

#### 4.4.3 实现顺序建议

| 顺序 | 能力 | 理由 |
|------|------|------|
| 1 | **图片理解** | 成本最低（一次识别），能立刻增强现有岗位 |
| 2 | **图像生成** | 需求最直观，且是最自然的付费点（见第 8 节） |
| 3 | **语音 TTS** | 锦上添花，投入产出比中等 |
| 4 | **视频生成** | 单次成本最高，放最后，且必须严格配额 |

#### 4.4.4 与定位的一致性

多模态**不违反**第 3 节的边界：

- 仍走**单一入口**（用户说"帮我做张封面"，而不是切到"图像生成器"页面）
- 仍是**单一身份**（用户面对的还是同一个助手）
- **不在首批实现 ≠ 不做**，只是排期在后

## 5. 明确不做什么

| 不做 | 原因 |
|------|------|
| ❌ 企业 / 团队协作 | 那是另一个产品（需权限层级、审批流、组织架构） |
| ❌ 通用聊天助手 | 正面撞豆包 / ChatGPT / Kimi，无胜算 |
| ❌ "什么活都能干"的万能 Agent | 万能 = 没有定位 |
| ❌ 需要用户写 prompt / 选工具的能力 | C 端最忌配置 |
| ❌ 无限制开放注册 | 成本不可控（见第 8 节） |
| ❌ 首批就支持完整的自建 Agent | 安全、成本、归因风险高，且不产生首批用户 |

## 6. 术语澄清

这几个概念在本项目里有严格区分，混用会导致架构决策出错。

### 6.1 Agent vs 角色配置 vs 技能

| 概念 | 是什么 | 有无决策能力 | 本项目现状 |
|------|--------|-------------|-----------|
| **Agent** | 会自主决策、有独立上下文的执行体 | 有 | 运行时**单执行体** |
| **角色配置**（`AgentDefinition`） | prompt + 工具 + 知识库 + 温度，是一条**数据** | 无 | 已实现，多条记录 |
| **技能（Skill）** | 注入给执行体的领域知识 + 作业流程 | 无 | 等价于角色配置的加载 |

**关键结论**：
> 项目库里的多个 `AgentDefinition` 是**多个角色配置（技能包）**，不是多个 Agent。
> 运行时是**同一个执行体在换装**，不是多个 Agent 在协作。

### 6.2 配置（数据实体）vs 执行体（运行时）

| | 用户创建时会创建吗 | 说明 |
|---|---|---|
| **数据实体**（`agent_definition` 一行） | ✅ 会 | 相当于"员工档案"，长期存在 |
| **运行时执行体** | ❌ 不会 | 运行时按需组装，跑完即弃 |

运行时会话的真相：一份角色配置被**展开**成 `ChatContext` 的若干字段（`agentAllowedTools`、`agenticKbIds`、`provider`、`history`），驱动一次推理。

```
AgentDefinition  =  类 / 方法定义      // 存在数据库，不执行
ChatContext      =  一次调用的栈帧      // 临时创建，跑完销毁
```

### 6.3 什么才算"多 Agent"（判定三标准）

必须**同时**满足，缺一不算：

1. **同一时刻有多个执行体并发存在**
2. **各自拥有独立上下文**（不共享同一份 history）
3. **它们之间有信息交换**（委派 / 汇总 / 协商）

对照本项目：

| 路径 | 机制 | 是否多 Agent |
|------|------|-------------|
| 对话路径（`IntentRouter` → `AgentOrchestrator`） | 选一个角色 → 展开一次执行 | ❌ 单 Agent 换装 |
| 工作流路径（DAG 引擎） | 多节点编排 + 节点间传值（含并行节点） | ⚠️ **多 Agent 雏形**（但是确定性编排） |

**所以本项目缺的不是"更多配置"，而是"运行时动态委派"** —— 执行体自主决定派生帮手（独立 `ChatContext` + 独立 history），拿回结论后继续。

### 6.4 持久化的四层

| 层 | 存什么 | 生命周期 | 现状 |
|----|--------|---------|------|
| **定义层** | 角色配置（prompt / 工具 / 知识库） | 长期 | `agent_definition` ✅ |
| **记忆层** | 对话历史、上下文 | 会话级 | `session` / `message` ✅ |
| **执行层** | 任务定义、断点、重试 | 任务生命周期 | `scheduled_task` / `workflow_execution` ✅ |
| **瞬态层** | 单次推理上下文 | 毫秒~秒 | 内存，不持久化 ✅ |

**待补的第五层：跨会话的"角色长期记忆"**

| | 工具 | 员工 |
|---|---|---|
| 每次使用 | 全新、无状态 | **带着上次经验** |
| 表现 | 永远一样 | **越用越顺手** |

若角色每次派活都从零开始，它本质仍是工具。"员工感"来自跨会话的经验沉淀（结论 / 偏好 / 教训），这是"越用越好用"与留存的关键来源。

## 7. 架构原则

### 7.1 内置与自建：入口分离 + 路由池分层

**问题**：`IntentRouter` 按 `userId` 取候选时，用户自建的角色会与平台内置角色**在同一路由池竞争**，导致：

| 问题 | 后果 |
|------|------|
| 候选数量膨胀 | 路由准确率随数量下降 |
| 用户乱写描述 | 劣质描述抢走内置角色流量 |
| 选到效果差的自建角色 | 体验差，但归因于"平台不行" |

**解法**：两者的"选择语义"本就不同。

| | 内置角色 | 用户自建角色 |
|---|---|---|
| 用户知道要用哪个吗 | 不知道，也不关心 | 明确知道 |
| 谁做决定 | 路由（隐形） | 用户（显式唤起） |
| 是否进路由池 | **进** | **不进**（或极低优先级） |
| 交互形态 | 直接说需求 | 点卡片 / `@` 指定 |

**落地方式**：`AgentDefinition` 增加来源类型

```
type = BUILTIN      → 平台维护，进路由池，用户无感知（隐形）
type = USER_CUSTOM  → 用户克隆而来，不进路由池，仅显式唤起（可见）
```

### 7.2 用户"创建"的对象是角色配置，不是 Agent

| 用户可改（安全） | 用户不可改（危险） |
|---|---|
| 名字、头像、一句描述 | 是否进全局路由池 |
| 语气、风格 | 能调用哪些工具（仅白名单内，或不可选） |
| 关联哪些自己的知识库 | 独立上下文 / 是否派生执行体 |
| 从模板克隆后微调 | 配额、是否公开 |

**形态要求：是"填空"，不是"编程"**

| ❌ 别让用户 | ✅ 应该让用户 |
|---|---|
| 写 system prompt | 用自然语言描述"我要它干什么" |
| 挑工具 | 从内置模板克隆，工具已配好 |
| 调 temperature | 选"严谨一点 / 活泼一点" |

**唯一可行路径：克隆内置模板再改**（复用现有 `isTemplate` + 克隆能力）。

### 7.3 技能换装 vs 多 Agent 的适用边界

**优先走"技能换装"（单执行体 + 加载不同角色配置）**，它有四个压倒性优势：

1. 符合"对外单一身份"铁律：记忆连续、风格稳定
2. **成本低**（C 端生死线）：无额外路由调用与多轮开销
3. 实现成本几乎为零：现有 `AgentDefinition` 本身就是完整的技能包定义
4. 无错误级联：不存在"选错角色导致后续全错"

**仅两种情况值得升级为多 Agent**：

- **需要并行**（同时搜多个来源）
- **需要上下文隔离**（中间结果量大，会污染后续推理）

| 任务 | 该走哪条路 | 原因 |
|------|-----------|------|
| 写周报 / 回消息 / 整理资料 | 技能换装 | 串行任务，污染不严重 |
| 调研员 | **多 Agent** | 并行搜多源，原始结果用完即弃，必须隔离 |
| 资料管家（批量解析） | **多 Agent** | 解析结果量大，隔离防止上下文爆炸 |

### 7.4 拆分的判断信号

**该拆（满足任一）**：

- 一个 prompt 里出现**互斥的语气 / 人格**
- 工具数量 > 15~20 个
- 不同场景需要的知识完全不重叠
- 不同场景需要不同权限
- 有明确的阶段依赖（收集 → 分析 → 输出）
- 某类任务效果持续差，想单独调优

**不该拆（出现即停）**：

- 只是"事多"，但都是同一类活、同一套知识
- 拆开后需要频繁互传大量上下文
- 拆开后没有任何一个角色能独立完成有意义的工作（粒度太细）

> 经验：**过度拆分比不拆分更常见，也更糟。** 3 个调好的角色，远胜 8 个弱角色。

### 7.5 目标架构

```
用户
  ↓
单一入口（一个对话框，一个身份）
  ↓
技能调度层（按需加载对应角色的 prompt + 工具 + 知识）
  ↓
大部分岗位 → 单执行体换装跑完
少数岗位（调研 / 批量） → 内部升级为多 Agent 协作，对外仍是一个身份
```

**对外永远一个入口、一个身份；内部按任务需要决定"自己干还是叫帮手"。**

## 8. 成本护栏（C 端生死线）

### 8.1 根本差异：本产品有变动成本

| | 普通 SaaS | 本产品 |
|---|---|---|
| 边际成本 | 接近零 | **每次对话都烧 token** |
| 用户翻倍 | 成本几乎不变 | **成本翻倍** |

**用户越多，亏损越快。** 在 C 端，"能不能做出来"不是问题，"能不能撑住成本"才是。

### 8.2 现有能力的用途转换

同一套治理能力，在 B 端用于合规，在 C 端用于**止损**：

| 能力 | B 端用途 | C 端用途 |
|------|---------|---------|
| 配额（F-39） | 包年套餐 | **防止白嫖烧穿** |
| 限流（F-40.3） | 保护系统 | **防止恶意刷** |
| 熔断（F-40.4） | 保护上游 | **防止单点故障拖崩** |
| 成本追踪 | 财务对账 | **算清每个用户是否在亏钱** |

### 8.3 必配护栏清单

1. **按用户日限额**（次数 + token 双维度）
2. **限流**：同用户/IP 高频请求拦截
3. **模型分级**：低额度用户走便宜模型，高额度 / 付费用户走强模型
4. **缓存**：相似请求复用结果
5. **不开放注册**：邀请制，控制总量

### 8.4 多模态的成本特殊性（对应 4.4 节）

多模态是**成本最高的部分**，且无法用文本侧的策略降本：

| | 文本对话 | 图像 / 视频生成 |
|---|---|---|
| 能否缓存 | 相似请求可复用 | **不能**（每次都是真实调用） |
| 单次成本 | 低 | **远高于一次文本对话** |
| 用量计量 | token | **按张 / 按秒**，直观可计 |

**结论：多模态是最自然的付费点。**

| 理由 | 说明 |
|------|------|
| 用户感知价值高 | 一张图的价值一眼可见，比"多聊几句"更值钱 |
| 成本真实存在 | 必须收费才能持续，收费理由充分、用户能理解 |
| 用量可计量 | 按张数计价，计费透明 |

**因此建议：付费能力优先放在多模态，而不是文本对话。**

- 文本对话保持**免费 / 低门槛** —— 用于养成使用习惯、积累留存
- 多模态作为**付费转化点** —— 用户先用顺了，再为出图付费

**护栏要求（比文本更严格）**：

1. 每日出图 / 出视频的**硬性张数上限**
2. 视频生成**默认关闭**，需显式开启并单独配额
3. 生成结果**落盘复用**，相同参数不重复生成

## 9. 验证标准

### 9.1 定位是否成立

> **能找到 10 个一人公司用户，他们每周主动使用 2 次以上，并且会抱怨"今天怎么这么慢"。**

"抱怨"比"称赞"更能说明产品成立 —— 称赞是礼貌，抱怨是依赖。

### 9.2 差异化必须回答的问题

个人用户面前已有：豆包 / Kimi / 元宝（免费）、ChatGPT / Claude（最强）、Coze / 扣子（可建 Agent，免费）。

> **本产品给个人用户提供的、以上这些给不了的东西是什么？**

答不上来，就只是"又一个能创建 Agent 的网站"。

## 10. 演进路径

```
阶段 1：学习项目（当前）
  自己就是用户，先把技能层跑通，选定 2 个岗位
  
阶段 2：给自己用
  验证技能换装 + 自主循环，跑通多 Agent 协作（调研员）
  
阶段 3：邀请制小范围（20 人以内）
  真实用户反馈，验证定位与成本模型
  → 目标不是 1000 个用户，是 20 个愿意说话的用户
  
阶段 4：小范围开放
  差异化问题有答案后，再考虑扩大
```

**每阶段都必须有真实使用者。** 没有外部反馈源时，定位一定会漂移。

## 11. 决策记录

| 决策 | 结论 | 理由 |
|------|------|------|
| 产品形态 | 应用，不是框架 | 框架抽象需要大量使用者反馈才能收敛，单人项目易过度设计；应用有明确完成态、反馈快 |
| 目标用户 | 一人公司 / 自由职业者 | 有真实"缺人手"痛感，算得清 ROI，会为工具付费 |
| 不选普通消费者 | ❌ | 没有需要外包的重复劳动，"数字员工"对他们是伪需求 |
| 不选企业定制 | ❌ | 销售周期长、安全审查重、单人难以维护交付 |
| 内部形态 | 技能换装优先，多 Agent 为辅 | 成本低、身份连续、实现成本几乎为零 |
| 用户自建 | 降级为"克隆内置模板 + 改名" | 规避安全 / 成本 / 归因风险，且不产生首批用户 |
| 开放式 | 邀请制 | Agent 平台有变动成本，无限制开放会烧穿 |
| **多模态** | **保留，分期实现**（见 4.4） | 对一人公司是真实需求（商品图 / 封面 / 看懂客户截图），且是最自然的付费点 |
| 多模态实现顺序 | 图片理解 → 图像生成 → TTS → 视频 | 按成本从低到高、价值从高到低排序 |
| 付费点选择 | 优先放在多模态，而非文本 | 文本免费养习惯，多模态转化收费 |
